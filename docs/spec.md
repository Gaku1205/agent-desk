# agent-desk 仕様書

AIと働くときの、人間の待ち時間と見落としを減らす画面。

1人の開発者が、AIに任せた開発（清書 → 実装 → CI → レビュー → 修正 → マージ → 公開）がどこまで進んだかを1画面で追い、AIが止まって人間の判断が要るときだけ、その場で押せるようにする。

2026年10月に、手動で回していた版（`Gaku1205/agent-desk-v1`）を、全自動パイプライン（`docs/pipeline.md`）の上で作り直したもの。

## 前提

- 使う人：開発者本人だけ（MVP）。GitHubでログインし、許可リストに入っている人だけ入れる。後で誰でも使えるように広げる前提で作る
- 対象のパイプライン：`docs/pipeline.md`（`Gaku1205/ai-dev-template` と同じ形）。要点：
  - `ai:plan` → 企画AIが清書して `ai:implement` を付ける
  - `ai:implement` → 実装AIがブランチ `claude/issue-<番号>-...` に実装し、PRを自動で作る
  - CIが通ると `ai:review` が付いてレビューAIが確認。指摘なしなら自動でマージ、指摘やCI失敗はAIが2回まで直す
  - 自動で進められないときは `ai:stuck` が付いて止まる。`ai:hold` のPRはマージだけ人間が押す
  - マージされるとVercelが本番に公開し、結果をマージコミットのコミットステータスに書き込む。Vercel以外の公開先（AWS App Runner・GitHub Releases の exe・Expo）は、パイプラインが context `deploy/<種類>`（`deploy/aws-apprunner`・`deploy/github-release`・`deploy/expo`）で書く（pending → success／failure・error。success の `target_url` は公開先、failure・error の `target_url` はActionsの実行のページ。`description` は日本語の説明）
  - 監視するリポジトリが全部このパイプラインを入れているとは限らない（`PIPELINE_TOKEN` が無いリポジトリでは、PR作成とマージは人間がする）
- データベースは持たない。表示する情報は毎回GitHubのREST APIから取る
- 技術：Next.js（App Router）＋TypeScript、認証はAuth.js（next-auth v5）のGitHubプロバイダ、テストはVitest

## 設定（環境変数）

| 名前 | 内容 |
| --- | --- |
| `AUTH_GITHUB_ID` / `AUTH_GITHUB_SECRET` | GitHub OAuth Appのキー |
| `AUTH_SECRET` | Auth.jsの暗号化キー |
| `ALLOWED_GITHUB_LOGINS` | ログインを許可するGitHubユーザー名（カンマ区切り） |
| `WATCHED_REPOS` | 監視するリポジトリ（`owner/repo` のカンマ区切り）。設定画面で保存した物があれば、そちらを使う |
| `SETTINGS_REPO` | 設定画面の保存先のリポジトリ（`owner/repo`。ふつうは agent-desk 自身）。無ければ設定画面の「監視するリポジトリ」は見るだけで変えられない |

読み取りは `src/lib/config.ts` の関数を使う（`getWatchedRepos`、`getAllowedLogins`）。

### ログインで頼む権限（OAuthのスコープ）

ログインを始めるとき（ログインボタンを押したとき）だけ、`WATCHED_REPOS` と `SETTINGS_REPO`（あれば）のリポジトリが公開かどうかで決める（`src/lib/loginScope.ts`）。人間の設定は増やさない。

- 全部公開 → `read:user public_repo`
- 1つでも非公開、公開か分からない、または監視リポジトリが0件 → `read:user repo`
- 公開かどうかは、トークン無しの `GET https://api.github.com/repos/{owner}/{repo}` の `private` で調べる。公開と分かった結果はサーバーのメモリに約1時間覚える。調べられなかったとき（通信失敗・404・403・`private` が読めない等）は「公開か不明」として `repo` にし、失敗は覚えない
- 設定画面で保存したリポジトリ（Variable）はログイン前に読めないので、判定には使わない。設定画面で非公開リポジトリを足したら、環境変数も合わせて直す
- すでにログイン済みのセッションのトークンは作り直さない（次にログインしたときから効く）

## 状態の判定

画面の中心は「各Issueが今どの段階にいて、誰の番か」。判定は純粋関数として `src/lib/status.ts` に置き、テストを書く。

| 段階 | 判定条件（上から順に評価） | 誰の番 |
| --- | --- | --- |
| 止まった | Issueか紐づくPRに `ai:stuck` がある（閉じたIssueは除く） | 人間 |
| やり直し待ち | Issueか紐づくPRに `ai:retry` があり、閉じたIssueでなく、紐づくPRが未マージ（`ai:stuck` が無いとき。あれば上の「止まった」が優先）。`ai:implement`・CI中・レビュー中などの進行中の段階より優先 | なし |
| 公開済み | 紐づくPRがマージ済みで、マージコミットの公開ステータスが（context ごとの最新で）全部 success。または、マージコミットの公開が failure・error でも、あとの公開が成功している（下の「あとの公開が成功」）。または公開ステータスが無いままマージから30分以上たった。または、公開が無いリポジトリで公開ステータスが無い（マージ直後でも。下の「公開が無いリポジトリ」） | なし |
| 公開中／公開失敗 | 紐づくPRがマージ済みで、公開ステータスのどれかが failure・error（公開失敗）、それ以外でどれかが pending（公開中）。公開ステータスが無く、マージから30分たっていないときも公開中（公開が無いリポジトリを除く）。failure・error でも、あとの公開が成功していれば公開済み（上の行） | なし／人間 |
| 修正中 | 紐づくPRがopenで、パイプラインの「直して」の依頼（`<!-- auto-fix -->` を含むコメント）があり、その依頼に書かれたコミット（`<!-- auto-fix-sha: … -->`）がPRの先頭コミットのまま（AIがまだpushしていない） | AI |
| レビュー中 | 紐づくPRがopenで、`ai:review` ラベルがあり、Claude Reviewのチェックが「`skipped` 以外の結果で完了」したものがまだ無い（チェックが無い・実行中・`skipped` のみ） | AI |
| マージ待ち | 紐づくPRがopenで、GitHub ActionsのCIチェック（Claude Review以外）が1つ以上あり、チェックが全部 success | 下を参照 |
| CI中／CI失敗 | 紐づくPRがopenで、CIが実行中／失敗。GitHub ActionsのCIチェックがまだ1つも無いとき（PRを作った直後、Vercelのチェックだけ先に付いている間）もCI中。CIの数にはClaude Reviewのチェックを入れない | AI／AI（自動で直す） |
| PR作成待ち | PRはないが、実装AIの完了コメントがある（`claude/issue-<番号>-` ブランチがある） | 人間 |
| AI作業中 | `ai:implement` ラベルがあり、完了コメントもPRもない | AI |
| 企画中 | `ai:plan` ラベルがある | AI |
| 順番待ち | `ai:queue` ラベルがある | なし |
| 保留 | `ai:skip` ラベルがある（`ai:plan`・`ai:implement` が付いていれば、そちらが先）。閉じたIssueは出さない | 人間 |
| 未着手 | 上のどれでもない | 人間 |

「公開が無いリポジトリ」：そのリポジトリの、マージから30分以上たった直近のPR（マージ時刻の新しい順に最大5件）のマージコミットに、公開ステータスがどれも無い。Vercelをつないでいないリポジトリで、マージのたびに30分「公開中」が続くのを避けるため、ここでは公開ステータスが無いPRをマージ時点で「公開済み」にする（「公開状況は不明」は出さない）。1件でも公開ステータスが付いているPRがあるリポジトリは、今までどおり。30分以上前にマージされたPRが0件のときは判断材料が無いので「公開が無い」とはしない（今までどおり30分まで「公開中」）。新しいデータの取得はせず、取得済みの各PRの公開ステータスで判定する。判定は `src/lib/status.ts` の `hasNoDeploys`、結果は `deployState` に渡す。

「公開ステータス」の判定：context が `Vercel` で始まる物**または** `deploy/` で始まる物（判定は `src/lib/deployStatus.ts` の `isDeployStatus` 1つにまとめる）。1つのコミットに複数あるとき（App Runner と Releases など）は、context ごとに `updated_at` が最新の物を取り、まとめる：どれかが failure・error → 公開失敗／それ以外でどれかが pending → 公開中／全部 success → 公開済み。

「あとの公開が成功」：マージコミットの公開が failure・error でも、その context が、同じリポジトリの「main の最後に公開が成功した時刻」（context ごとに持つ）で、そのPRのマージ時刻より後に**同じ context で**成功していれば、その context は解決ずみ（そのPRの変更は本番に含まれているので）。全部の失敗が解決ずみなら公開済みにする（公開済みの表示は「公開状況は不明」にしない）。後のコミットの公開は、それ以前のコミットの内容も含むため。別の context の success では解決しない（App Runner が失敗したまま Releases だけが後で成功しても、App Runner の失敗は残る）。その時刻が無い、またはマージより前のときは、今までどおり「公開に失敗」。判定は `src/lib/status.ts` の `deployState`。

「main の最後に公開が成功した時刻」は、main の直近のコミット（新しい順に最大10件）の公開ステータス（`Vercel` で始まる、または `deploy/` で始まるcontext）から、context ごとに、success がある一番新しいコミットの、その success の `updated_at` の最新で決める。一番新しいコミットの公開がまだ途中（pending）でも、1つ前のコミットが success ならその時刻を使うので、マージの直後に解決ずみの古い失敗がよみがえらない。説明（`description`）が「Canceled by Ignored Build Step」（前後の空白を除いた完全一致）の success は、公開を飛ばしたコミット（パイプラインの更新だけのコミット）なので、公開の成功に数えない。これは Vercel の context だけの扱い（`deploy/` の context には適用しない）（`src/lib/status.ts` の `latestSuccessDeployAt`・`latestSuccessDeployByContext`）。新しい順に見て、見えた公開の context が全部、数えられる success を見つけた時点でやめる（Vercel だけのリポジトリは、今までどおり success のある最初のコミットで止まる）。10件のうちに無い context は「無い」。取得の回数は増やさない。
取得は `GET /repos/{owner}/{repo}/commits?sha=main&per_page=10` と、各コミットの `GET /repos/{owner}/{repo}/commits/{sha}/status?per_page=100`（リポジトリごとに1回。回数制限のため、URLに時刻など毎回変わる値は入れず、ETag を効かせる）。コミット一覧・ステータスの取得が1つでも失敗したときは、そのリポジトリで前回うまく取れた値を使い、古い失敗を戻さない（前回の値が無いときだけ null）。前回の値はサーバーのメモリに覚える（キーはトークンのハッシュ＋リポジトリ、件数に上限あり、再起動で消えてよい）。`fetchMainDeployedAt`（`src/lib/github/fetch.ts`）。

一緒に持つ情報（バーと説明文に使う）：
- 「清書した」：Issueの本文に、企画AIが残す `> 元のメモ：` がある
- 「修正した」：紐づくPRに、パイプラインの「直して」の依頼が1つ以上ある。その数（1〜2）も持つ
- 「修正の確認中」：修正したPRで、先頭コミットが最後の依頼より新しく、まだマージ待ちになっていない（CI中・CI失敗・レビュー中）。バーは「修正」の位置のまま

止まった：`ai:stuck` を無視して表の残りで判定した段階を「止まる前の段階」として一緒に持つ（進み具合のバーの位置に使う）。

やり直し待ち：使用量の上限などでAIが止まると、パイプラインが `ai:retry` を付け、30分以上あけて自動でやり直す（10回まで。`docs/pipeline.md`）。人間は何もしなくてよいので、誰の番は「なし」で、操作のボタンも無い。「止まった」と同じく、`ai:retry` を無視して表の残りで判定した段階を「やり直し待ちになる前の段階」として一緒に持つ（進み具合のバーの位置に使う）。
- やり直しの回数と理由：パイプラインがIssueかPRに書く記録のコメント（`<!-- auto-retry -->` を含み、`🔁 …（やり直し n/10回）。` の次の行が `理由：…`。`.github/scripts/pipeline-lib.sh` の `write_retry_record`）のうち最新の物から読む。読めたら理由の横に「n/10回」を出す。記録が無い・読めないときは回数を出さない（理由も無ければ「AIが止まりました」）

マージ待ちの「誰の番」：
- PRに `ai:hold` がある → 人間（マージを押す）
- レビューが「指摘なし」で終わっていない（レビューしていない・指摘あり） → AI（パイプラインがレビューに回すか、直させる）
- それ以外 → AI（パイプラインが自動でマージする直前）

「レビューが指摘なしで終わった」：PRのコメントのうち、`claude[bot]` が書いた「`## Code review`」で始まる最新のコメントに `No issues found` が含まれる。

パイプラインが動いていないリポジトリの未着手：
- 「パイプラインが動いていない」：`.github/workflows/pipeline.yml` が無い（`GET /repos/{owner}/{repo}/actions/workflows/pipeline.yml/runs?per_page=1` が 404）、またはそのワークフローの実行が1度も無い（`total_count` が 0）。Secretsの有無は、読むのに管理者の権限が要るので使わない
- 確かめられないとき（404 以外のエラー・形が違う）は「動いている」とも「動いていない」とも決めず、今までどおり表示する
- 判定は `src/lib/pipelineState.ts` の純粋関数。リポジトリごとに取得時にAPIを1回呼ぶ
- 動いていないリポジトリの**未着手**のIssueだけ、「あなたの番」の説明文を「パイプライン未設定です。Secretsを登録してください」にし、「おまかせ」「実装を依頼」は出さない（サーバー側でも受け付けない）。段階・誰の番・パイプライン表の短い説明・ほかの段階の表示は変えない
- 設定画面の「パイプラインあり／なし」（ワークフローの有無だけ）は変えない

見張り役が止まっているリポジトリ：
- 「見張り役」：パイプラインの `.github/workflows/watchdog.yml`。止まると `ai:retry` のやり直しや見落としの拾い上げが動かなくなる（公開リポジトリで60日コミットが無い、Actions を止めた、ワークフローが壊れた、などで止まる）
- 取得：リポジトリごとに `GET /repos/{owner}/{repo}/actions/workflows/watchdog.yml/runs?per_page=1` を1回呼ぶ。実行が1件あれば、その `created_at`（実行の開始時刻。成功・失敗は問わない）を「最後の実行の時刻」とする
- 404（`watchdog.yml` が無い）→「無い」。実行が0件、404 以外のエラー、形が違う →「分からない」。「無い」「分からない」のときは何も出さない（パイプラインを入れていないリポジトリでは出さない）
- 判定：最後の実行から3時間以上（ちょうど3時間を含む）たっていたら「止まっている」。経過時間 N は時間単位で切り捨てる（3時間10分なら3）。3時間未満は「注意なし」。最後の実行の時刻が今より未来、または読めないときも「注意なし」
- 判定は `src/lib/watchdogState.ts` の純粋関数 `judgeWatchdog`（入力：最後の実行の時刻または「無い」「分からない」・今の時刻。出力：「注意なし」か「止まっている（経過した時間）」）。取得に失敗しても、ほかのデータの表示は落とさない
- 出す場所と文言：ホームとリポジトリのページの、ヘッダーの下・「あなたの番」の上。止まっているリポジトリごとに「見張り役が {N} 時間動いていません。Actions が止まっていないか確認してください」。ホームはリポジトリ名を前に付けて1行ずつ、リポジトリのページはそのリポジトリの分だけ。止まっていなければ場所ごと出さない。見た目は `docs/design.md`
- 通知・設定項目・再起動の操作は無い。見張り役以外のワークフローの死活監視もしない

PR作成待ちは、パイプラインが入っていれば数秒でPRになるので、ふつうは見えない。パイプラインの無いリポジトリや、PR作成が失敗したときに人間の番として出る。

- 「紐づくPR」：本文に `Closes #<番号>`（大文字小文字は問わない、Fixes/Resolvesも可）を含むか、ブランチ名が `claude/issue-<番号>-` で始まるPR
- 「公開ステータス」：マージコミットのコミットステータス（`GET /repos/{owner}/{repo}/commits/{sha}/status`）のうち、context が `Vercel` で始まる、または `deploy/` で始まるもの。VercelはGitHubのDeploymentではなく、ここに結果を書く（2026年10月25日に実データで確認）。`deploy/<種類>` はパイプラインが書く
- 公開失敗の理由：公開失敗の行では、context ごとの最新が failure・error のものの `description`（Vercelが失敗の理由を書く）を理由として出す。失敗しているのが Vercel の1つだけなら `description` だけ。それ以外（`deploy/` の context が失敗しているとき）は、`{種類}：{説明}` を1行ずつ（種類は context の `deploy/` の後ろ。Vercel は「Vercel」）。`description` が空の物は出さず、出す物が無ければ理由は出さない（「理由を見る」も出さない）。「rate limited — retry in N hours」の形（N の単位は分・時間・日）は「利用上限に達しました。あとN時間で再開します」のように日本語にし、それ以外は `description` をそのまま出す。Nは `description` の数字をそのまま使う。出す場所はパイプライン表の公開失敗の行だけ（理由の取り出しは `src/lib/deployFailure.ts`）
- 公開先のリンク：公開済みの行で、context ごとの最新が success かつ `target_url` が `https://` で始まる物は、文字のリンク `開く ↗`（新しいタブ）を出す。複数あれば種類の名前つきで並べる（`App Runner ↗` `Releases ↗` `Expo ↗`。それ以外の種類は context の `deploy/` の後ろをそのまま）。`target_url` が無い・`https://` で始まらないときは出さない（`src/lib/deployStatus.ts` の `deployLinks`）
- 公開ステータスが無いまま30分以上たったもの（Vercelをつなぐ前にマージしたものなど）は「公開済み」に入れ、カードに「公開状況は不明」と出す
- 「GitHub ActionsのCIチェック」：チェックランのうち、作ったアプリが `github-actions` のもの（APIの `app.slug`）で、Claude Reviewのチェック（名前が `review`）を除いたもの。Vercelのチェック（`Vercel Preview Comments` など）は数に入れるが、これだけでは「CIが通った」とみなさない
- 「実装AIの完了コメント」：`claude[bot]` のコメントで `Claude finished` を含むもの
- 閉じたIssueは、紐づくPRがマージ済みなら表示する（公開済みまでを追うため）。それ以外の閉じたIssueは表示しない
- 「誰の番が人間」のものは「あなたの番」に出す。止まった物がいちばん上
- 止まった物の説明文の理由は、次の2つのうち `createdAt` が新しい方を使う。どちらも無ければ「自動で進められず止まりました」
  - パイプラインがPRに書いた最新の「⏸ 自動で進めるのを止めました：{理由}」の理由
  - 清書AIの「お願いのコメント」の理由。Issueのコメントのうち、作者が `claude[bot]` で、本文に `<!-- human-request -->` を含む最新の物が「お願いのコメント」（清書AIが「人間にしかできない作業」と判断したときに、パイプラインが1行目にこの印を付け、2行目に要点の1文を書く）。理由は、印の行より後の最初の空でない行（前後の空白を除く）で、空なら無いものとする。作者が `claude[bot]` 以外のコメントは、印があっても使わない
  - 理由の末尾に `。` があれば、「。確認して…」とつなげるときに重ならないよう1つにする（下の原因の取り出しのあとの文に対して行う）
- `ai:hold` のマージ待ち（人間の番）の説明文は、PRの本文の「お願い」を使う。見出し（`#` 1〜6個で始まる行）の文字に「人間にお願いしたいこと」を含む節を探し、無ければ「人間が手で確認すべきこと」を含む節を探す（それぞれ最初に見つかった節）。節の中身は、見出しの次の行から次の見出しの手前まで。空の行を除き、行頭の `- `・`* `・`1. ` の形の印と前後の空白を取る。残った行が無い、または最初の行が「なし」「特になし」「無し」なら、お願いは無いものとする（節が見つかったあとは、もう一方の節は探さない）。取り出しは `src/lib/humanRequest.ts` の純粋関数で、取得するデータは増やさない
- 止まった理由・やり直しの理由（パイプラインの `failure_reason`）は、文の末尾が `（原因：{原因}。ログ：{URL}）` の形のことがある。原因の中に `（）` が入れ子で入るので、末尾から見て `。ログ：` の位置で分け、`{ text: 説明, cause: 原因 | null, logUrl: URL | null }` に取り出す（`src/lib/failureReason.ts` の純粋関数。形が合わなければ `{ text: 元の文, cause: null, logUrl: null }`）。URLは `https://github.com/{owner}/{repo}/actions/runs/{数字}` で、`{owner}/{repo}` がその行のリポジトリ（大文字小文字は区別しない）と一致するときだけ `logUrl` にする。それ以外（別のサイト・別のリポジトリ）は `logUrl: null` で、URLは表示しない
- 画面には理由の代わりに `{説明}（{原因}）`（原因が無ければ `{説明}`）を出し、URLは文に入れない。「あなたの番」の行では `logUrl` があるときだけ `ログを開く ↗` のリンクを出す。パイプライン表・待機中のパイプラインの理由からも、URLは外す（リンクはここには出さない）。Actionsのログ本文はAPIで取らない

## 画面

見た目（色・文字・アイコン・文言・動き）はすべて `docs/design.md` に従う。

ログインしていなければ、どのURLでもログインボタンだけを出す。ページは2種類（構成と見た目は `docs/design.md`）。

| ページ | URL | 中身 |
| --- | --- | --- |
| ホーム | `/` | あなたの番（全リポジトリ・PCは2列）＋待機中のパイプライン（全リポジトリ）＋実行中のパイプライン（全リポジトリ）＋最近の出来事 |
| リポジトリのページ | `/repos/{owner}/{repo}` | あなたの番（そのリポジトリだけ）＋パイプライン |

- 全ページの左にサイドバー（ホームと監視リポジトリへのリンク、それぞれの「あなたの番」の件数と「実行中のパイプライン」の件数。待機中の数は足さない（順番待ち・やり直し待ちは、どちらの数にも入れない）。実行中の数え方はホームの「実行中のパイプライン」の表と同じ＝`isRunningStage`、取れなかったリポジトリは数えない。ホームの件数は表の行数と一致する）
- ページの上のヘッダー（ページ名・スマホのメニューボタン）は、スクロールしても画面の上に見え続ける（PC・スマホとも）
- `WATCHED_REPOS` に無いリポジトリのURLは 404

### あなたの番

人間の判断待ちのIssueだけを、待っている時間が長い順に並べる。ホームは全リポジトリ、リポジトリのページはそのリポジトリだけ。1件ごとに次を出す。

- リポジトリ名、Issue番号とタイトル（GitHubへのリンク）
- 何をすればいいかの説明文と、進み具合のバー
- その場で押せるボタン（下の「操作」）

0件のときは「今はAIの番です」と出す。

PCでは、ウィンドウの幅を変えても崩れないようにする（ホーム・リポジトリのページ共通。見た目の数値は `docs/design.md` の「あなたの番」と「進み具合のバー」）。

- タイトルはどの幅でも1行。入らなければ「…」で切り、行に乗せた間は電光掲示板のように流す。説明文は2行まで
- 進み具合のバーは文字の列の幅いっぱいに伸ばす。段階名は8つ並べて重ならない幅のときだけ全部出し、足りないときは今の段階の名前だけ出す
- 1件の行の幅に応じて並べ方を変える（広い：横1段／中くらい：番号と待ち時間を上の段に、ボタンを右端に縦に／狭い：ボタンを文字の列の下に）。ボタンや文字がはみ出したり重なったりしない

### パイプライン（リポジトリのページ）

そのリポジトリの直近14日のIssue（表示の条件は「状態の判定」のとおり）を、1件1行の表で出す。列はパイプラインの8段階（清書 / 実装 / PR / CI / レビュー / 修正 / マージ / 公開）で、今の段階までバーが伸びる。まだ終わっていない行が上（新しい順）、公開済みの行はその下。公開済みは最初は出さず、表の一番下から5件ずつ出せる。段階が変わっても並び順は変えない。

### 待機中のパイプライン（ホーム）

全監視リポジトリのうち、AIも人間も今は手を動かしていない作業、つまり段階が順番待ち（`ai:queue`）かやり直し待ち（`ai:retry`。使用量の上限の待ちも含む）の物だけを、パイプライン表と同じ形で出す。「あなたの番」と「実行中のパイプライン」の間に置く。これらの物は「実行中のパイプライン」には出さず、こちらにだけ出す（同じ物を2か所に出さない）。

- 並び順：待っている時間が長い順。待ち時間の起点はIssueの `updatedAt`（ラベルを付けた時刻は取っていないための代わり）なので、`updatedAt` の古い順。同じ時刻ならIssue番号の小さい順、それでも同じならリポジトリ名の順。取れなかったリポジトリは飛ばす
- 0件なら「待っている作業はありません」
- サイドバーの件数には含めない（新しい数も足さない）。実行中の数は、もともと待機中を含まないので変わらない
- 行の中身は「実行中のパイプライン」と同じ。見た目は `docs/design.md`

### 実行中のパイプライン（ホーム）

全監視リポジトリのうち、いまAIの番で動いている作業（企画中・AI作業中・CI中・レビュー中・修正中・公開中）だけを、パイプライン表と同じ形で出す。あなたの番・順番待ち・公開済み・止まった物は出さない。Issueの番号が大きい順。0件なら「いま動いているパイプラインはありません」。見た目は `docs/design.md`。

### 最近の出来事（ホーム）

全監視リポジトリで直近3日に起きたことを、新しい順に日ごとにまとめて出す（最大50件）。出来事の種類と文言は `docs/design.md` の「出来事の一覧」。

出来事と、その時刻の取り方：

| 出来事 | 時刻 |
| --- | --- |
| `ai:implement` が付いた／`ai:review` が付いた | Issueのイベント（`GET /repos/{owner}/{repo}/issues/events`、`event` が `labeled`、`label.name` が一致）の `created_at`。PRに付いた `ai:review` は、そのPRに紐づくIssueの出来事にする |
| 実装AIが完了した／エラーで止まった | `claude[bot]` のコメント（完了コメント／エラーコメント）の `createdAt` |
| PRができた | 紐づくPRの `createdAt` |
| CIが全部通った／失敗した | PRの先頭コミットのチェック（Claude Reviewを除く）が全部完了したとき、いちばん遅い `completed_at`。失敗は、失敗したチェックの `completed_at` |
| レビューAIが終わった | Claude Reviewのチェック（`skipped` 以外で完了）の `completed_at` |
| マージされた | PRの `mergedAt` |
| 公開された／公開に失敗した | 公開ステータス（`Vercel` または `deploy/` で始まるcontext）の `updated_at`（success／failure・error のとき） |

- 出来事は、画面に出すIssue・PRと同じ取得データから作る。増えるAPI呼び出しは、リポジトリごとにIssueのイベント1回（`per_page=100`）だけにする
- 出来事を作る処理は `src/lib/` の純粋関数にまとめ、テストする（入力：取得済みのIssue・PR・コメント・チェック・ステータス・イベントと「今」の時刻。出力：新しい順の出来事の配列）

### 更新

- 自動で取り直す間隔は、動いている作業があるかと、GitHubの回数制限の残りで変える（タブが非表示のときは止める）。判定は `src/lib/refresh.ts` の `getAutoRefreshPlan`（入力：作業の有無・残り・回復する時刻・今の時刻。出力：間隔、または「自動では取り直さない」と再開する時刻）

| 残り | 自動で取り直す間隔 |
| --- | --- |
| 1,500以上（または不明） | AIの番の作業（企画中・AI作業中・CI中・レビュー中・修正中・公開中など）が1つでもあれば10秒ごと、無ければ30秒ごと |
| 500以上1,500未満 | 60秒ごと |
| 500未満 | 回復する時刻まで自動では取り直さない（手動の「更新」ボタンは使える） |

- 回数制限（1時間5,000回）はオーナーのアカウント全体で共有で、パイプライン（`PIPELINE_TOKEN`）も同じ枠を使う。ダッシュボードが使い切るとパイプラインのマージなども止まるので、残りが少ないときは自動の取り直しを控えて、パイプラインの分を残す
- 残りは、GitHubの返事の `X-RateLimit-Remaining`、回復する時刻は `X-RateLimit-Reset`（UNIX秒）。304の返事にも付くので読む。書き込み（`send`）の返事も覚える。サーバーのメモリに、トークンのハッシュごとに最新の物を覚える（トークンそのものはキーにしない）。読む・覚えるのは `src/lib/github/client.ts`
- 回復する時刻を過ぎたら、覚えている残りは古いので使わず、普段の間隔に戻す。まだ一度も返事を受けていない（不明）ときも普段の間隔
- 取り直しのたびにサーバーが間隔を決め直し、画面（`AppShell`）に渡す。渡すのは間隔（ミリ秒、または止めるとき `null`）と再開する時刻だけで、GitHubのトークンは渡さない
- 「回復するまで止める」間は、同期の下に「回数制限の残りが少ないため、自動更新を止めています（HH:MM に再開）」と出す（見た目は `docs/design.md`）。回復する時刻を過ぎて、次に取り直せたら消える
- レート制限（`rate_limited`）で取れなかったときのエラーの文言は、回復する時刻が分かれば「GitHubのレート制限に達しました。HH:MM（日本時間）ごろに回復します」。`HH:MM` は返事の `X-RateLimit-Reset` を日本時間にして秒を落とした物（`src/lib/refresh.ts` の `formatResetTime`）。時刻が分からないときは「GitHubのレート制限に達しました。しばらくしてからもう一度試してください」

- GitHubへの問い合わせは、前回の返事の `ETag` を `If-None-Match` に付けて送る。変わっていなければ 304 が返り、GitHubの回数制限に数えられない。304 のときは前回の中身を使う（サーバーのメモリに、トークンとURLごとに覚えておく。トークンそのものはキーにせず、ハッシュにする）
- 手動の「更新」ボタン（サイドバーの下）。キーボードのショートカットは無し
- 同期の時刻を出す（サイドバーの下）。出すのは「最後に取り直した時刻」（日本時間 `HH:MM:SS`）。現在時刻では進めない。取り直しが終わると、その取り直しの時刻に変わる。判定は `src/lib/refresh.ts` の `getDisplayedSyncTime`

### 設定（`/settings`）

サイドバーの下（同期・更新の上）に「設定」へのリンクを置く。保存にデータベースは使わず、GitHubのActionsの Variables（リポジトリの設定値。公開リポジトリでも外からは見えない）と、ブラウザを使う。

#### 監視するリポジトリ

- 保存先：`SETTINGS_REPO` の Variable `AGENT_DESK_WATCHED_REPOS`（`owner/repo` のカンマ区切り）。読み取りは `GET /repos/{SETTINGS_REPO}/actions/variables/AGENT_DESK_WATCHED_REPOS`、保存は無ければ `POST`、あれば `PATCH`
- この Variable があれば、画面全体の「監視するリポジトリ」はこれを使う。無ければ環境変数 `WATCHED_REPOS`
- 画面：いまの一覧（1行ずつ、右に「外す」）と、追加の欄（ログイン中のユーザーが読めるリポジトリ `GET /user/repos?per_page=100&sort=pushed` から選ぶ）。「保存」で書き込む
- 各リポジトリに、全自動パイプラインが入っているか（`.github/workflows/pipeline.yml` があるか）を「パイプラインあり／なし」で添える
- 0件では保存できない。`owner/repo` の形でない物、ユーザーが読めないリポジトリは受け付けない

#### 通知

- 通知の種類（縦）×監視しているリポジトリ（横）の表で、鳴らす通知をチェックボックスで選ぶ。保存は1回で、変わったリポジトリの分だけ書き込む。種類と初期値は `.github/scripts/notify.sh`（止まった・質問・ai:hold のマージ待ち・人間の操作待ち・公開された・公開失敗＝初期オン、自動でマージした・CI失敗＝初期オフ）
- 保存先：そのリポジトリの Variable `NOTIFY_EVENTS`（種類のカンマ区切り）。無ければ初期値として表示する
- パイプラインが入っていないリポジトリは、選べない（「パイプラインなし」と出す）
- 通知の届け先（ntfyのトピック）は秘密の値なので、ここには出さない

#### アニメーション

- 「アニメーション」：`端末の設定に従う`（初期）／`オン`／`オフ` の3つから選ぶ
- 保存先：そのブラウザ（`localStorage`。PCとスマホで別々）。読み書きは try/catch で囲み、使えなければ「端末の設定に従う」
- `オフ` のときは、`prefers-reduced-motion: reduce` のときと同じ見た目にする（回る・明滅・移動・拡大を止める）。`オン` のときは端末の設定にかかわらず動かす
- `<html>` に `data-motion="reduce"` / `data-motion="full"` を付けて、CSSはこれと `prefers-reduced-motion` の両方を見る

#### 設定の操作の決まり

- 保存はすべてサーバー側で、ログイン中のユーザーのトークンで行う。許可リストのユーザーだけ
- Variables を書くには、そのリポジトリの管理者である必要がある。失敗したら理由を画面に出す（「このリポジトリの設定を変える権限がありません」など）
- 書き込む値は、決まった形（リポジトリ名の並び・通知の種類の並び）だけを受け付ける

### デモ（`/demo`）

ログインしなくても、サンプルのデータで画面を見て触れるページ。就活などで、GitHubのアカウントが無い人にも見てもらうため。

- URL：`/demo`（ホーム）、`/demo/repos/{owner}/{repo}`（リポジトリのページ）、`/demo/settings`（設定）。ログインしていなくても開ける
- ログイン画面に「ログインせずにデモを見る」のリンクを置く
- データ：`src/lib/demo/` に置いたサンプル。架空のリポジトリ2つ（`demo/todo-app`・`demo/landing-page`）に、全部の段階（企画中・順番待ち・保留・AI作業中・CI中・CI失敗・レビュー中・修正中・修正の確認中・マージ待ち・止まった・やり直し待ち・公開中・公開済み など）と、最近の出来事、順番待ちの理由、並列動作を含める。時刻は「今」からの相対で作る
- GitHub には一切問い合わせない。トークンも使わない
- 画面のいちばん上に帯：「デモ：サンプルのデータです。ボタンを押しても実際には何も起きません」＋「GitHubで見る ↗」（このアプリのリポジトリへのリンク）＋「ログイン」
- ボタン（おまかせ・実装を依頼・再開・始める・PRを作る・レビューを依頼・マージ・設定の保存）は押せるが、実際には何もせず、「デモでは実際には動きません」と短く出す
- **再生**：帯に「再生 ▶」ボタン。押すと、サンプルの1件（メモから始めた物）が、清書 → 実装 → PR → CI → レビュー → 修正 → マージ → 公開 と、4秒ごとに次の段階へ進む。行の枠・バー・最近の出来事・あなたの番が、本物と同じように変わる。最後まで行ったら止まり、「もう一度」で最初から
- 自動更新はしない（再生の間だけ画面が変わる）
- 本物の画面と同じ部品を使う（デモ専用の見た目を作らない）。違うのはデータの出どころだけ

## 操作

すべてサーバー側で実行する（ブラウザにGitHubのトークンを渡さない）。成功したら画面を取り直す。

| ボタン | 出る段階 | やること |
| --- | --- | --- |
| おまかせ | 未着手 | Issueに `ai:plan` ラベルを付ける（企画AIが清書して、あとは全自動） |
| 実装を依頼 | 未着手 | Issueに `ai:implement` ラベルを付ける（Issueがもう詳しく書けているとき） |
| 再開 | 止まった | `ai:stuck` を外す。人間が対応したあと押す |
| 始める | 保留 | `ai:skip` を外す。外すと、パイプラインが自動で企画に回す（画面は `ai:plan` を付けない） |
| PRを作る | PR作成待ち | `claude/issue-<番号>-...` ブランチから main へのPRを作る。タイトルはIssueタイトル、本文は `Closes #<番号>` |
| レビューを依頼 | マージ待ちで `ai:hold` があり、まだレビューしていない | PRに `ai:review` ラベルを付ける |
| マージ | マージ待ち | 確認ダイアログで「マージする」を押したらPRをマージする。押した時点でマージできない状態に変わっていたら（CIが始まった・レビュー中になったなど）、エラーを出さずにダイアログを閉じて画面をすぐ取り直す（行の段階が変わり、ボタンは消える） |

- 操作のAPIは、ログイン中かつ許可リストのユーザーで、対象リポジトリが `WATCHED_REPOS` に入っているときだけ受け付ける
- 失敗したら、理由を画面に出す

## セキュリティ

- GitHubのトークンはサーバー側（Auth.jsのセッション）だけで扱い、クライアントのコードやレスポンスに含めない
- 許可リスト外のユーザーはログインさせない
- 監視リポジトリ以外への操作は拒否する
- OAuthのスコープは、監視リポジトリ（`WATCHED_REPOS`・`SETTINGS_REPO`）が全部公開なら `read:user public_repo`、そうでなければPrivateリポジトリの読み書きのため `read:user repo`（「ログインで頼む権限」の節。後でGitHub Appに置き換えるのが改善候補）
