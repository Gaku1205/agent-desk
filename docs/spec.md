# agent-desk 仕様書

AIと働くときの、人間の待ち時間と見落としを減らす画面。

1人の開発者が、AIに任せた開発（清書 → 実装 → CI → レビュー → 修正 → マージ → 公開）がどこまで進んだかを1画面で追い、AIが止まって人間の判断が要るときだけ、その場で押せるようにする。

2026年10月に、手動で回していた版（`Gaku1205/agent-desk-v1`）を、全自動パイプライン（`docs/pipeline.md`）の上で作り直したもの。

## 前提

- 使う人：開発者本人だけ（MVP）。GitHubでログインし、許可リストに入っている人だけ入れる。後で誰でも使えるように広げる前提で作る
- 対象のパイプライン：`docs/pipeline.md`（`Gaku1205/ai-dev-template` と同じ形）。要点：
  - `ai:plan` → 企画AIが清書して `ai:implement` を付ける
  - `ai:implement` → 実装AIがブランチ `claude/issue-<番号>-...` に実装し、PRを自動で作る
  - CIが通ると `ai:review` が付いてレビューAIが確認。指摘なしなら自動でマージ、指摘やCI失敗はAIが2回まで直す
  - 自動で進められないときは `ai:stuck` が付いて止まる。`ai:hold` のPRはマージだけ人間が押す
  - マージされるとVercelが本番に公開し、結果をマージコミットのコミットステータスに書き込む
  - 監視するリポジトリが全部このパイプラインを入れているとは限らない（`PIPELINE_TOKEN` が無いリポジトリでは、PR作成とマージは人間がする）
- データベースは持たない。表示する情報は毎回GitHubのREST APIから取る
- 技術：Next.js（App Router）＋TypeScript、認証はAuth.js（next-auth v5）のGitHubプロバイダ、テストはVitest

## 設定（環境変数）

| 名前 | 内容 |
| --- | --- |
| `AUTH_GITHUB_ID` / `AUTH_GITHUB_SECRET` | GitHub OAuth Appのキー |
| `AUTH_SECRET` | Auth.jsの暗号化キー |
| `ALLOWED_GITHUB_LOGINS` | ログインを許可するGitHubユーザー名（カンマ区切り） |
| `WATCHED_REPOS` | 監視するリポジトリ（`owner/repo` のカンマ区切り）。設定画面で保存した物があれば、そちらを使う |
| `SETTINGS_REPO` | 設定画面の保存先のリポジトリ（`owner/repo`。ふつうは agent-desk 自身）。無ければ設定画面の「監視するリポジトリ」は見るだけで変えられない |

読み取りは `src/lib/config.ts` の関数を使う（`getWatchedRepos`、`getAllowedLogins`）。

## 状態の判定

画面の中心は「各Issueが今どの段階にいて、誰の番か」。判定は純粋関数として `src/lib/status.ts` に置き、テストを書く。

| 段階 | 判定条件（上から順に評価） | 誰の番 |
| --- | --- | --- |
| 止まった | Issueか紐づくPRに `ai:stuck` がある（閉じたIssueは除く） | 人間 |
| やり直し待ち | Issueか紐づくPRに `ai:retry` があり、閉じたIssueでなく、紐づくPRが未マージ（`ai:stuck` が無いとき。あれば上の「止まった」が優先）。`ai:implement`・CI中・レビュー中などの進行中の段階より優先 | なし |
| 公開済み | 紐づくPRがマージ済みで、マージコミットの公開ステータスが success。または公開ステータスが無いままマージから30分以上たった | なし |
| 公開中／公開失敗 | 紐づくPRがマージ済みで、公開ステータスが pending／failure・error。公開ステータスが無く、マージから30分たっていないときも公開中 | なし／人間 |
| 修正中 | 紐づくPRがopenで、パイプラインの「直して」の依頼（`<!-- auto-fix -->` を含むコメント）があり、その依頼に書かれたコミット（`<!-- auto-fix-sha: … -->`）がPRの先頭コミットのまま（AIがまだpushしていない） | AI |
| レビュー中 | 紐づくPRがopenで、`ai:review` ラベルがあり、Claude Reviewのチェックが「`skipped` 以外の結果で完了」したものがまだ無い（チェックが無い・実行中・`skipped` のみ） | AI |
| マージ待ち | 紐づくPRがopenで、GitHub ActionsのCIチェック（Claude Review以外）が1つ以上あり、チェックが全部 success | 下を参照 |
| CI中／CI失敗 | 紐づくPRがopenで、CIが実行中／失敗。GitHub ActionsのCIチェックがまだ1つも無いとき（PRを作った直後、Vercelのチェックだけ先に付いている間）もCI中。CIの数にはClaude Reviewのチェックを入れない | AI／AI（自動で直す） |
| PR作成待ち | PRはないが、実装AIの完了コメントがある（`claude/issue-<番号>-` ブランチがある） | 人間 |
| AI作業中 | `ai:implement` ラベルがあり、完了コメントもPRもない | AI |
| 企画中 | `ai:plan` ラベルがある | AI |
| 順番待ち | `ai:queue` ラベルがある | なし |
| 保留 | `ai:skip` ラベルがある（`ai:plan`・`ai:implement` が付いていれば、そちらが先）。閉じたIssueは出さない | 人間 |
| 未着手 | 上のどれでもない | 人間 |

一緒に持つ情報（バーと説明文に使う）：
- 「清書した」：Issueの本文に、企画AIが残す `> 元のメモ：` がある
- 「修正した」：紐づくPRに、パイプラインの「直して」の依頼が1つ以上ある。その数（1〜2）も持つ
- 「修正の確認中」：修正したPRで、先頭コミットが最後の依頼より新しく、まだマージ待ちになっていない（CI中・CI失敗・レビュー中）。バーは「修正」の位置のまま

止まった：`ai:stuck` を無視して表の残りで判定した段階を「止まる前の段階」として一緒に持つ（進み具合のバーの位置に使う）。

やり直し待ち：使用量の上限などでAIが止まると、パイプラインが `ai:retry` を付け、30分以上あけて自動でやり直す（10回まで。`docs/pipeline.md`）。人間は何もしなくてよいので、誰の番は「なし」で、操作のボタンも無い。「止まった」と同じく、`ai:retry` を無視して表の残りで判定した段階を「やり直し待ちになる前の段階」として一緒に持つ（進み具合のバーの位置に使う）。
- やり直しの回数と理由：パイプラインがIssueかPRに書く記録のコメント（`<!-- auto-retry -->` を含み、`🔁 …（やり直し n/10回）。` の次の行が `理由：…`。`.github/scripts/pipeline-lib.sh` の `write_retry_record`）のうち最新の物から読む。読めたら理由の横に「n/10回」を出す。記録が無い・読めないときは回数を出さない（理由も無ければ「AIが止まりました」）

マージ待ちの「誰の番」：
- PRに `ai:hold` がある → 人間（マージを押す）
- レビューが「指摘なし」で終わっていない（レビューしていない・指摘あり） → AI（パイプラインがレビューに回すか、直させる）
- それ以外 → AI（パイプラインが自動でマージする直前）

「レビューが指摘なしで終わった」：PRのコメントのうち、`claude[bot]` が書いた「`## Code review`」で始まる最新のコメントに `No issues found` が含まれる。

PR作成待ちは、パイプラインが入っていれば数秒でPRになるので、ふつうは見えない。パイプラインの無いリポジトリや、PR作成が失敗したときに人間の番として出る。

- 「紐づくPR」：本文に `Closes #<番号>`（大文字小文字は問わない、Fixes/Resolvesも可）を含むか、ブランチ名が `claude/issue-<番号>-` で始まるPR
- 「公開ステータス」：マージコミットのコミットステータス（`GET /repos/{owner}/{repo}/commits/{sha}/status`）のうち、context が `Vercel` で始まるもの。VercelはGitHubのDeploymentではなく、ここに結果を書く（2026年10月25日に実データで確認）
- 公開失敗の理由：公開失敗の行では、公開ステータスのうち failure・error のものの `description`（Vercelが失敗の理由を書く）を理由として出す。複数あるときは `updated_at` が最新のもの。`description` が空なら理由は出さない（「理由を見る」も出さない）。「rate limited — retry in N hours」の形（N の単位は分・時間・日）は「利用上限に達しました。あとN時間で再開します」のように日本語にし、それ以外は `description` をそのまま出す。Nは `description` の数字をそのまま使う。出す場所はパイプライン表の公開失敗の行だけ（理由の取り出しは `src/lib/deployFailure.ts`）
- 公開ステータスが無いまま30分以上たったもの（Vercelをつなぐ前にマージしたものなど）は「公開済み」に入れ、カードに「公開状況は不明」と出す
- 「GitHub ActionsのCIチェック」：チェックランのうち、作ったアプリが `github-actions` のもの（APIの `app.slug`）で、Claude Reviewのチェック（名前が `review`）を除いたもの。Vercelのチェック（`Vercel Preview Comments` など）は数に入れるが、これだけでは「CIが通った」とみなさない
- 「実装AIの完了コメント」：`claude[bot]` のコメントで `Claude finished` を含むもの
- 閉じたIssueは、紐づくPRがマージ済みなら表示する（公開済みまでを追うため）。それ以外の閉じたIssueは表示しない
- 「誰の番が人間」のものは「あなたの番」に出す。止まった物がいちばん上
- 止まった物の説明文は、パイプラインがPRに書いた最新の「⏸ 自動で進めるのを止めました：{理由}」の理由を使う（無ければ「自動で進められず止まりました」）

## 画面

見た目（色・文字・アイコン・文言・動き）はすべて `docs/design.md` に従う。

ログインしていなければ、どのURLでもログインボタンだけを出す。ページは2種類（構成と見た目は `docs/design.md`）。

| ページ | URL | 中身 |
| --- | --- | --- |
| ホーム | `/` | あなたの番（全リポジトリ・PCは2列）＋実行中のパイプライン（全リポジトリ）＋最近の出来事 |
| リポジトリのページ | `/repos/{owner}/{repo}` | あなたの番（そのリポジトリだけ）＋パイプライン |

- 全ページの左にサイドバー（ホームと監視リポジトリへのリンク、それぞれの「あなたの番」の件数）
- ページの上のヘッダー（ページ名・スマホのメニューボタン）は、スクロールしても画面の上に見え続ける（PC・スマホとも）
- `WATCHED_REPOS` に無いリポジトリのURLは 404

### あなたの番

人間の判断待ちのIssueだけを、待っている時間が長い順に並べる。ホームは全リポジトリ、リポジトリのページはそのリポジトリだけ。1件ごとに次を出す。

- リポジトリ名、Issue番号とタイトル（GitHubへのリンク）
- 何をすればいいかの説明文と、進み具合のバー
- その場で押せるボタン（下の「操作」）

0件のときは「今はAIの番です」と出す。

PCでは、ウィンドウの幅を変えても崩れないようにする（ホーム・リポジトリのページ共通。見た目の数値は `docs/design.md` の「あなたの番」と「進み具合のバー」）。

- タイトルはどの幅でも1行。入らなければ「…」で切り、行に乗せた間は電光掲示板のように流す。説明文は2行まで
- 進み具合のバーは文字の列の幅いっぱいに伸ばす。段階名は8つ並べて重ならない幅のときだけ全部出し、足りないときは今の段階の名前だけ出す
- 1件の行の幅に応じて並べ方を変える（広い：横1段／中くらい：番号と待ち時間を上の段に、ボタンを右端に縦に／狭い：ボタンを文字の列の下に）。ボタンや文字がはみ出したり重なったりしない

### パイプライン（リポジトリのページ）

そのリポジトリの直近14日のIssue（表示の条件は「状態の判定」のとおり）を、1件1行の表で出す。列はパイプラインの8段階（清書 / 実装 / PR / CI / レビュー / 修正 / マージ / 公開）で、今の段階までバーが伸びる。まだ終わっていない行が上（新しい順）、公開済みの行はその下。公開済みは最初は出さず、表の一番下から5件ずつ出せる。段階が変わっても並び順は変えない。

### 実行中のパイプライン（ホーム）

全監視リポジトリのうち、いまAIの番で動いている作業（企画中・AI作業中・CI中・レビュー中・修正中・公開中）だけを、パイプライン表と同じ形で出す。あなたの番・順番待ち・公開済み・止まった物は出さない。Issueの番号が大きい順。0件なら「いま動いているパイプラインはありません」。見た目は `docs/design.md`。

### 最近の出来事（ホーム）

全監視リポジトリで直近3日に起きたことを、新しい順に日ごとにまとめて出す（最大50件）。出来事の種類と文言は `docs/design.md` の「出来事の一覧」。

出来事と、その時刻の取り方：

| 出来事 | 時刻 |
| --- | --- |
| `ai:implement` が付いた／`ai:review` が付いた | Issueのイベント（`GET /repos/{owner}/{repo}/issues/events`、`event` が `labeled`、`label.name` が一致）の `created_at`。PRに付いた `ai:review` は、そのPRに紐づくIssueの出来事にする |
| 実装AIが完了した／エラーで止まった | `claude[bot]` のコメント（完了コメント／エラーコメント）の `createdAt` |
| PRができた | 紐づくPRの `createdAt` |
| CIが全部通った／失敗した | PRの先頭コミットのチェック（Claude Reviewを除く）が全部完了したとき、いちばん遅い `completed_at`。失敗は、失敗したチェックの `completed_at` |
| レビューAIが終わった | Claude Reviewのチェック（`skipped` 以外で完了）の `completed_at` |
| マージされた | PRの `mergedAt` |
| 公開された／公開に失敗した | 公開ステータス（`Vercel` で始まるcontext）の `updated_at`（success／failure・error のとき） |

- 出来事は、画面に出すIssue・PRと同じ取得データから作る。増えるAPI呼び出しは、リポジトリごとにIssueのイベント1回（`per_page=100`）だけにする
- 出来事を作る処理は `src/lib/` の純粋関数にまとめ、テストする（入力：取得済みのIssue・PR・コメント・チェック・ステータス・イベントと「今」の時刻。出力：新しい順の出来事の配列）

### 更新

- 自動で取り直す間隔は、動いている作業があるかで変える（タブが非表示のときは止める）
  - AIの番の作業（企画中・AI作業中・CI中・レビュー中・修正中・公開中など）が1つでもある：10秒ごと
  - 無い：60秒ごと
- GitHubへの問い合わせは、前回の返事の `ETag` を `If-None-Match` に付けて送る。変わっていなければ 304 が返り、GitHubの回数制限に数えられない。304 のときは前回の中身を使う（サーバーのメモリに、トークンとURLごとに覚えておく。トークンそのものはキーにせず、ハッシュにする）
- 手動の「更新」ボタン（サイドバーの下）。キーボードのショートカットは無し
- 最後に更新した時刻を出す（サイドバーの下）

### 設定（`/settings`）

サイドバーの下（同期・更新の上）に「設定」へのリンクを置く。保存にデータベースは使わず、GitHubのActionsの Variables（リポジトリの設定値。公開リポジトリでも外からは見えない）と、ブラウザを使う。

#### 監視するリポジトリ

- 保存先：`SETTINGS_REPO` の Variable `AGENT_DESK_WATCHED_REPOS`（`owner/repo` のカンマ区切り）。読み取りは `GET /repos/{SETTINGS_REPO}/actions/variables/AGENT_DESK_WATCHED_REPOS`、保存は無ければ `POST`、あれば `PATCH`
- この Variable があれば、画面全体の「監視するリポジトリ」はこれを使う。無ければ環境変数 `WATCHED_REPOS`
- 画面：いまの一覧（1行ずつ、右に「外す」）と、追加の欄（ログイン中のユーザーが読めるリポジトリ `GET /user/repos?per_page=100&sort=pushed` から選ぶ）。「保存」で書き込む
- 各リポジトリに、全自動パイプラインが入っているか（`.github/workflows/pipeline.yml` があるか）を「パイプラインあり／なし」で添える
- 0件では保存できない。`owner/repo` の形でない物、ユーザーが読めないリポジトリは受け付けない

#### 通知

- 通知の種類（縦）×監視しているリポジトリ（横）の表で、鳴らす通知をチェックボックスで選ぶ。保存は1回で、変わったリポジトリの分だけ書き込む。種類と初期値は `.github/scripts/notify.sh`（止まった・質問・ai:hold のマージ待ち・人間の操作待ち・公開された・公開失敗＝初期オン、自動でマージした・CI失敗＝初期オフ）
- 保存先：そのリポジトリの Variable `NOTIFY_EVENTS`（種類のカンマ区切り）。無ければ初期値として表示する
- パイプラインが入っていないリポジトリは、選べない（「パイプラインなし」と出す）
- 通知の届け先（ntfyのトピック）は秘密の値なので、ここには出さない

#### アニメーション

- 「アニメーション」：`端末の設定に従う`（初期）／`オン`／`オフ` の3つから選ぶ
- 保存先：そのブラウザ（`localStorage`。PCとスマホで別々）。読み書きは try/catch で囲み、使えなければ「端末の設定に従う」
- `オフ` のときは、`prefers-reduced-motion: reduce` のときと同じ見た目にする（回る・明滅・移動・拡大を止める）。`オン` のときは端末の設定にかかわらず動かす
- `<html>` に `data-motion="reduce"` / `data-motion="full"` を付けて、CSSはこれと `prefers-reduced-motion` の両方を見る

#### 設定の操作の決まり

- 保存はすべてサーバー側で、ログイン中のユーザーのトークンで行う。許可リストのユーザーだけ
- Variables を書くには、そのリポジトリの管理者である必要がある。失敗したら理由を画面に出す（「このリポジトリの設定を変える権限がありません」など）
- 書き込む値は、決まった形（リポジトリ名の並び・通知の種類の並び）だけを受け付ける

### デモ（`/demo`）

ログインしなくても、サンプルのデータで画面を見て触れるページ。就活などで、GitHubのアカウントが無い人にも見てもらうため。

- URL：`/demo`（ホーム）、`/demo/repos/{owner}/{repo}`（リポジトリのページ）、`/demo/settings`（設定）。ログインしていなくても開ける
- ログイン画面に「ログインせずにデモを見る」のリンクを置く
- データ：`src/lib/demo/` に置いたサンプル。架空のリポジトリ2つ（`demo/todo-app`・`demo/landing-page`）に、全部の段階（企画中・順番待ち・保留・AI作業中・CI中・CI失敗・レビュー中・修正中・修正の確認中・マージ待ち・止まった・やり直し待ち・公開中・公開済み など）と、最近の出来事、順番待ちの理由、並列動作を含める。時刻は「今」からの相対で作る
- GitHub には一切問い合わせない。トークンも使わない
- 画面のいちばん上に帯：「デモ：サンプルのデータです。ボタンを押しても実際には何も起きません」＋「GitHubで見る ↗」（このアプリのリポジトリへのリンク）＋「ログイン」
- ボタン（おまかせ・実装を依頼・再開・始める・PRを作る・レビューを依頼・マージ・設定の保存）は押せるが、実際には何もせず、「デモでは実際には動きません」と短く出す
- **再生**：帯に「再生 ▶」ボタン。押すと、サンプルの1件（メモから始めた物）が、清書 → 実装 → PR → CI → レビュー → 修正 → マージ → 公開 と、4秒ごとに次の段階へ進む。行の枠・バー・最近の出来事・あなたの番が、本物と同じように変わる。最後まで行ったら止まり、「もう一度」で最初から
- 自動更新はしない（再生の間だけ画面が変わる）
- 本物の画面と同じ部品を使う（デモ専用の見た目を作らない）。違うのはデータの出どころだけ

## 操作

すべてサーバー側で実行する（ブラウザにGitHubのトークンを渡さない）。成功したら画面を取り直す。

| ボタン | 出る段階 | やること |
| --- | --- | --- |
| おまかせ | 未着手 | Issueに `ai:plan` ラベルを付ける（企画AIが清書して、あとは全自動） |
| 実装を依頼 | 未着手 | Issueに `ai:implement` ラベルを付ける（Issueがもう詳しく書けているとき） |
| 再開 | 止まった | `ai:stuck` を外す。人間が対応したあと押す |
| 始める | 保留 | `ai:skip` を外す。外すと、パイプラインが自動で企画に回す（画面は `ai:plan` を付けない） |
| PRを作る | PR作成待ち | `claude/issue-<番号>-...` ブランチから main へのPRを作る。タイトルはIssueタイトル、本文は `Closes #<番号>` |
| レビューを依頼 | マージ待ちで `ai:hold` があり、まだレビューしていない | PRに `ai:review` ラベルを付ける |
| マージ | マージ待ち | 確認ダイアログで「マージする」を押したらPRをマージする。押した時点でマージできない状態に変わっていたら（CIが始まった・レビュー中になったなど）、エラーを出さずにダイアログを閉じて画面をすぐ取り直す（行の段階が変わり、ボタンは消える） |

- 操作のAPIは、ログイン中かつ許可リストのユーザーで、対象リポジトリが `WATCHED_REPOS` に入っているときだけ受け付ける
- 失敗したら、理由を画面に出す

## セキュリティ

- GitHubのトークンはサーバー側（Auth.jsのセッション）だけで扱い、クライアントのコードやレスポンスに含めない
- 許可リスト外のユーザーはログインさせない
- 監視リポジトリ以外への操作は拒否する
- OAuthのスコープは、Privateリポジトリの読み書きのため `repo` を使う（後でGitHub Appに置き換えるのが改善候補）
