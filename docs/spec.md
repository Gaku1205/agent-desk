# agent-desk 仕様書

AIと働くときの、人間の待ち時間と見落としを減らす画面。

1人の開発者が、AIに任せた開発（清書 → 実装 → CI → レビュー → 修正 → マージ → 公開）がどこまで進んだかを1画面で追い、AIが止まって人間の判断が要るときだけ、その場で押せるようにする。

2026年10月に、手動で回していた版（`Gaku1205/agent-desk-v1`）を、全自動パイプライン（`docs/pipeline.md`）の上で作り直したもの。

## 前提

- 使う人：開発者本人だけ（MVP）。GitHubでログインし、許可リストに入っている人だけ入れる。後で誰でも使えるように広げる前提で作る
- 対象のパイプライン：`docs/pipeline.md`（`Gaku1205/ai-dev-template` と同じ形）。要点：
  - `ai:plan` → 企画AIが清書して `ai:implement` を付ける
  - `ai:implement` → 実装AIがブランチ `claude/issue-<番号>-...` に実装し、PRを自動で作る
  - CIが通ると `ai:review` が付いてレビューAIが確認。指摘なしなら自動でマージ、指摘やCI失敗はAIが3回まで直す（普通のモデルで2回＋最後に opus で1回。下の「修正の上限」）
  - 自動で進められないときは `ai:stuck` が付いて止まる。`ai:hold` のPRはマージだけ人間が押す
  - マージされるとVercelが本番に公開し、結果をマージコミットのコミットステータスに書き込む。Vercel以外の公開先（AWS App Runner・GitHub Releases の exe・Expo）は、パイプラインが context `deploy/<種類>`（`deploy/aws-apprunner`・`deploy/github-release`・`deploy/expo`）で書く（pending → success／failure・error。success の `target_url` は公開先、failure・error の `target_url` はActionsの実行のページ。`description` は日本語の説明）
  - 監視するリポジトリが全部このパイプラインを入れているとは限らない（`PIPELINE_TOKEN` が無いリポジトリでは、PR作成とマージは人間がする）
- データベースは持たない。表示する情報は毎回GitHubのAPIから取る（ほとんどはGraphQLでまとめて取る。「データの取得」）
- 技術：Next.js（App Router）＋TypeScript、認証はAuth.js（next-auth v5）のGitHubプロバイダ、テストはVitest

## 設定（環境変数）

| 名前 | 内容 |
| --- | --- |
| `AUTH_GITHUB_ID` / `AUTH_GITHUB_SECRET` | GitHub OAuth Appのキー |
| `AUTH_SECRET` | Auth.jsの暗号化キー |
| `ALLOWED_GITHUB_LOGINS` | ログインを許可するGitHubユーザー名（カンマ区切り） |
| `PIPELINE_APP_ID` / `PIPELINE_APP_PRIVATE_KEY` | パイプラインの GitHub App（`gaku-ai-pipeline`）の App ID と秘密鍵（PEM の中身）。パイプラインの Secret と同じ名前・同じ値。あれば同期の読み取りを App の鍵で行う（「読み取りの鍵」）。無くても今までどおり動く |
| `WATCHED_REPOS` | 監視するリポジトリ（`owner/repo` のカンマ区切り）。設定画面で保存した物があれば、そちらを使う |
| `SETTINGS_REPO` | 設定画面の保存先のリポジトリ（`owner/repo`。ふつうは agent-desk 自身）。無ければ設定画面の「監視するリポジトリ」は見るだけで変えられない |

読み取りは `src/lib/config.ts` の関数を使う（`getWatchedRepos`、`getAllowedLogins`）。

### ログインで頼む権限（OAuthのスコープ）

ログインを始めるとき（ログインボタンを押したとき）だけ、`WATCHED_REPOS` と `SETTINGS_REPO`（あれば）のリポジトリが公開かどうかで決める（`src/lib/loginScope.ts`）。人間の設定は増やさない。

- 全部公開 → `read:user public_repo`
- 1つでも非公開、公開か分からない、または監視リポジトリが0件 → `read:user repo`
- 公開かどうかは、トークン無しの `GET https://api.github.com/repos/{owner}/{repo}` の `private` で調べる。公開と分かった結果はサーバーのメモリに約1時間覚える。調べられなかったとき（通信失敗・404・403・`private` が読めない等）は「公開か不明」として `repo` にし、失敗は覚えない
- 設定画面で保存したリポジトリ（Variable）はログイン前に読めないので、判定には使わない。設定画面で非公開リポジトリを足したら、環境変数も合わせて直す
- すでにログイン済みのセッションのトークンは作り直さない（次にログインしたときから効く）

### ログインの拒否・エラーの画面（`/auth-error`）

ログインに失敗したときは、Auth.js 既定の英語のページ（`/api/auth/error`）ではなく、自前の日本語の画面 `/auth-error` を出す（`src/lib/auth.ts` の `pages: { error: "/auth-error" }`）。ログインは必要ない画面（開けるのはログイン前の人）。

- `error` クエリで文言を分ける（`src/lib/authError.ts` の純粋関数 `getAuthErrorMessage`。入力：`error` の値（無い・配列・知らない値もある）。出力：画面に出す1行）
  - `AccessDenied`（許可リストに入っていない）→ `このアカウントでは使えません。agent-desk はオーナー専用です`
  - それ以外（設定ミス・通信の失敗・`error` が無い）→ `ログインできませんでした。もう一度お試しください`
- トークン・秘密・エラーの内部の詳細（クエリの値そのもの）は画面に出さない。上の2つの文言のどちらかだけを出す
- `ログイン画面へ戻る` のリンクで `/` へ戻れる
- ログイン画面には、先に `このページはオーナー専用です` の一言を出す（許可されていない人が、権限を許可する前に気づけるように）。許可リストを先に調べて断る作りには変えない（挙動は今までどおり）

## 状態の判定

画面の中心は「各Issueが今どの段階にいて、誰の番か」。判定は純粋関数として `src/lib/status.ts` に置き、テストを書く。

パイプラインが自動で作る保守のIssue（「AIの許可が足りない：…」など）は、オーナーが押す物が無くノイズになるので、下の表を評価する前に除き、画面に出さない（「あなたの番」・「いまの様子」・左のバーの数・Slots & Queue の Your turn・出来事・操作の対象のどれにも入らない）。次のどれかに当てはまるIssueで、開閉は問わない：ラベル `pipeline` がある／本文に `<!-- pipeline-maintenance -->` がある／題名が `AIの許可が足りない：`（全角コロン）で始まる（印が付く前の物）。判定は `src/lib/pipelineIssue.ts` の `isPipelineMaintenanceIssue`、除くのは `shouldShowIssue`（`src/lib/status.ts`）。`ai:skip` が付いていても保留にしない。上に当てはまらない普通の保留は今までどおり。取得するデータは増やさない（本文・ラベルは今も取っている）。

| 段階 | 判定条件（上から順に評価） | 誰の番 |
| --- | --- | --- |
| 止まった | Issueか紐づくPRに `ai:stuck` がある（閉じたIssueは除く）。ただし、紐づくPRが「マージしてよいPR」（下）なら、`ai:stuck` があっても止まったにせず、PRの方を優先して「マージ待ち（`ai:hold`・人間の番）」にする（2026年11月17日、Issue #401） | 人間 |
| やり直し待ち | Issueか紐づくPRに `ai:retry` があり、閉じたIssueでなく、紐づくPRが未マージ（`ai:stuck` が無いとき。あれば上の「止まった」が優先）。`ai:implement`・CI中・レビュー中などの進行中の段階より優先。ただし、最新のやり直しの記録より後に先へ進んだ印（PRの作成・更新、CIの完了、修正依頼、実装AIの作業中のコメント）があれば、やり直し待ちにせず、そのときの段階（下の説明） | なし |
| 公開済み | 紐づくPRがマージ済みで、マージコミットの公開ステータスが（context ごとの最新で）全部 success。または、マージコミットの公開が failure・error でも、あとの公開が成功している（下の「あとの公開が成功」）。または、マージコミットに（数えられる）公開ステータスが無くても、マージより後に main の公開が成功している（下の「あとの公開が成功」。「公開状況は不明」にしない）。または公開ステータスが無いままマージから30分以上たった。または、公開が無いリポジトリで公開ステータスが無い（マージ直後でも。下の「公開が無いリポジトリ」） | なし |
| 公開中／公開失敗 | 紐づくPRがマージ済みで、公開ステータスのどれかが failure・error（公開失敗）、それ以外でどれかが pending（公開中）。公開ステータスが無く、あとの公開の成功も無いまま、マージから30分たっていないときも公開中（公開が無いリポジトリを除く）。failure・error でも、あとの公開が成功していれば公開済み（上の行） | なし／人間 |
| 修正中 | 紐づくPRがopenで、パイプラインの「直して」の依頼（`<!-- auto-fix -->` を含むコメント）があり、その依頼に書かれたコミット（`<!-- auto-fix-sha: … -->`）がPRの先頭コミットのまま（AIがまだpushしていない） | AI |
| レビュー中 | 紐づくPRがopenで、`ai:review` ラベルがあり、Claude Reviewのチェックが「`skipped` 以外の結果で完了」したものがまだ無い（チェックが無い・実行中・`skipped` のみ） | AI |
| マージ待ち | 紐づくPRがopenで、GitHub ActionsのCIチェック（Claude Review以外）が1つ以上あり、チェックが全部 success | 下を参照 |
| CI中／CI失敗 | 紐づくPRがopenで、CIが実行中／失敗。GitHub ActionsのCIチェックがまだ1つも無いとき（PRを作った直後、Vercelのチェックだけ先に付いている間）もCI中。CIの数にはClaude Reviewのチェックを入れない | AI／AI（自動で直す） |
| PR作成待ち | PRはないが、実装AIの完了コメントがあり（`claude/issue-<番号>-` ブランチがある）、`ai:plan`・`ai:mocks`・`ai:queue`・`ai:blocked` のどれも付いていない（これらが付いているときは、古い完了コメントがあっても、そのラベルの段階。パイプラインがやり直しを始めた印のため。`ai:implement` が付いているとき、質問・工場の相談のときは今までどおり）。パイプラインが動いているリポジトリで、最後の結果が完了コメントでもエラーのコメントでも（エラーで終わってもブランチがあればパイプラインはPRを作る）、実装AIが終わってから**15分未満**の間は「PRを作成中」（猶予。15分たってもPRが無いとき・時刻が読めないときは今までどおり人間の番で、エラーなら `implementError`・`PRを作る`。下の「パイプラインが自動で進める間の猶予」）。`ai:implement` が付いていて、最後の結果のコメントより後に作られた実装AIの「作業中のコメント」があるときは、やり直しの実装が動いているので、PR作成待ちにせず下の「AI作業中」（下の「実装AIの完了コメント」の箇条書き） | 人間（猶予の間は AI） |
| AI作業中 | `ai:implement` ラベルがあり、完了コメントもPRもない。または、PRが無く `ai:implement` があり、最後の結果のコメント（完了・エラー）より後に作られた作業中のコメントがある（やり直しの実装が動いている） | AI |
| 工場の相談 | 開いているIssueに `factory:wait` ラベルがあり、工場のいちばん新しい相談のコメントのあとに、オーナーのコメントがまだ無い。オーナーのコメントがあれば（答えを送ったら）企画中（下の「工場の相談」）。ほかの人のコメントは数えない | 人間 |
| 質問 | 開いているIssueに `ai:question` ラベルがあり、いちばん新しい質問のコメントのあとに、オーナーのコメントがまだ無い（`ai:plan` が付いていても、こちらが先）。オーナーのコメントがあれば（答えを送ったら）企画中。ほかの人のコメントは数えない | 人間 |
| 質問（保留のまま残った質問） | 開いているIssueに `ai:skip` があり（`ai:question` は無くてもよい）、質問のコメントがあって、いちばん新しい質問のコメントのあとにオーナーのコメントがまだ無い。`ai:plan`・`ai:mocks`・`ai:queue`・`ai:blocked`・`ai:implement`・`ai:stuck` などが付いていれば、そちらが先（下の「保留」の行より先）。オーナーのコメントがあれば保留のまま | 人間 |
| 企画中 | `ai:plan` か `ai:mocks` ラベルがある（`ai:mocks` は、作る前に画面案のAIがざっくり画面を作っている間。企画AIが `ai:plan` を外して付けるので、見ないと未着手＝人間の番になってしまう。画面案ができると `ai:question` に替わり、下の「質問」になる） | AI |
| 順番待ち | `ai:queue` か `ai:blocked` がある | なし |
| 保留 | `ai:skip` ラベルがある（`ai:plan`・`ai:mocks`・`ai:implement` が付いていれば、そちらが先）。ただし答えていない質問のコメントが残っていれば、上の「質問」の行（保留のまま残った質問）になる。閉じたIssueは出さない | 人間 |
| 未着手 | 上のどれでもない。パイプラインが動いているリポジトリで、Issueを作ってから**10分未満**の間は「受付中」（猶予。下の「パイプラインが自動で進める間の猶予」） | 人間（猶予の間は AI） |

「公開が無いリポジトリ」：そのリポジトリの、マージから30分以上たった直近のPR（マージ時刻の新しい順に最大5件）のマージコミットに、公開ステータスがどれも無い。Vercelをつないでいないリポジトリで、マージのたびに30分「公開中」が続くのを避けるため、ここでは公開ステータスが無いPRをマージ時点で「公開済み」にする（「公開状況は不明」は出さない）。1件でも公開ステータスが付いているPRがあるリポジトリは、今までどおり。30分以上前にマージされたPRが0件のときは判断材料が無いので「公開が無い」とはしない（今までどおり30分まで「公開中」）。新しいデータの取得はせず、取得済みの各PRの公開ステータスで判定する。判定は `src/lib/status.ts` の `hasNoDeploys`、結果は `deployState` に渡す。

「公開ステータス」の判定：context が `Vercel` で始まる物**または** `deploy/` で始まる物（判定は `src/lib/deployStatus.ts` の `isDeployStatus` 1つにまとめる）。1つのコミットに複数あるとき（App Runner と Releases など）は、context ごとに `updated_at` が最新の物を取り、まとめる：どれかが failure・error → 公開失敗／それ以外でどれかが pending → 公開中／全部 success → 公開済み。

「あとの公開が成功」：マージコミットの公開が failure・error でも、その context が、同じリポジトリの「main の最後に公開が成功した時刻」（context ごとに持つ）で、そのPRのマージ時刻より後に**同じ context で**成功していれば、その context は解決ずみ（そのPRの変更は本番に含まれているので）。全部の失敗が解決ずみなら公開済みにする（公開済みの表示は「公開状況は不明」にしない）。後のコミットの公開は、それ以前のコミットの内容も含むため。別の context の success では解決しない（App Runner が失敗したまま Releases だけが後で成功しても、App Runner の失敗は残る）。その時刻が無い、またはマージより前のときは、今までどおり「公開に失敗」。判定は `src/lib/status.ts` の `deployState`。

マージコミットに（数えられる）公開ステータスが無いときも同じ考えで、いずれかの context の「main の最後に公開が成功した時刻」がマージ時刻より後なら公開済み（`unknown: false`）にする。公開は `deploy-vercel.yml` がまとめて1回だけ行うので、途中のマージには状態が付かないため。その時刻が無い・マージ時刻と同じか前なら、今までどおり（30分たてば公開済み（公開状況は不明）／それまでは公開中／公開が無いリポジトリは公開済み）。

「数えられる公開ステータス」：context ごとの最新のうち、「飛ばした物」（Vercel の context で、`description` が「Canceled by Ignored Build Step」の success。`isCountedDeploySuccess`）を除いたもの。飛ばした物の success しか無いコミットは、公開ステータスが無いのと同じ扱い（`deployState` の「公開ステータスがある」判定、出来事の `deployFootprint`、`hasNoDeploys` の「公開ステータスが付いているか」すべて。`src/lib/deployStatus.ts` の `latestCountedPerContext`）。failure・error・pending は今までどおり数える。

「main の最後に公開が成功した時刻」は、main の直近のコミット（新しい順に最大30件）の公開ステータス（`Vercel` で始まる、または `deploy/` で始まるcontext）から、context ごとに、success がある一番新しいコミットの、その success の `updated_at` の最新で決める。一番新しいコミットの公開がまだ途中（pending）でも、1つ前のコミットが success ならその時刻を使うので、マージの直後に解決ずみの古い失敗がよみがえらない。説明（`description`）が「Canceled by Ignored Build Step」（前後の空白を除いた完全一致）の success は、公開を飛ばしたコミット（パイプラインの更新だけのコミット）なので、公開の成功に数えない。これは Vercel の context だけの扱い（`deploy/` の context には適用しない）（`src/lib/status.ts` の `latestSuccessDeployAt`・`latestSuccessDeployByContext`）。新しい順に見て、見えた公開の context が全部、数えられる success を見つけた時点でやめる（Vercel だけのリポジトリは、今までどおり success のある最初のコミットで止まる）。30件のうちに無い context は、前回見つけた成功があればそれを使い（前回見つけた成功は、context ごとに新しい方を残す。`mergeMainDeployed`）、無ければ「無い」。「main の最後に公開が成功した時刻」の全体の時刻は、合わせた context ごとの時刻の最新にする。取得の回数は増やさない（見る件数が増えるだけ）。
取得は、同期の GraphQL の問い合わせ（「データの取得」）の中で、`ref(qualifiedName: "refs/heads/main")` の直近30コミット（`history(first: 30)`）の `status { contexts }` を一緒に取る（別の呼び出しは増やさない）。main が取れなかったとき（ブランチが無い・形が違う）は、そのリポジトリで前回うまく取れた値を使い、古い失敗を戻さない（前回の値が無いときだけ null）。前回の値はサーバーのメモリに覚える（キーはトークンのハッシュ＋リポジトリ、件数に上限あり、再起動で消えてよい）。`fetchMainDeployedAt`（`src/lib/github/fetch.ts`）。

一緒に持つ情報（説明文と、今の段階の名前（`src/lib/progress.ts` の `getProgress`）に使う）：
- 「清書した」：Issueの本文に、企画AIが残す `> 元のメモ：` がある
- 「修正した」：紐づくPRに、パイプラインの「直して」の依頼が1つ以上ある。その数（1〜2）も持つ
- 「修正の確認中」：修正したPRで、先頭コミットが最後の依頼より新しく、まだマージ待ちになっていない（CI中・CI失敗・レビュー中）。今の段階の名前は「修正」のまま

止まった：`ai:stuck` を無視して表の残りで判定した段階を「止まる前の段階」として一緒に持つ（今の段階の名前に使う）。

やり直し待ち：使用量の上限などでAIが止まると、パイプラインが `ai:retry` を付け、30分以上あけて自動でやり直す（10回まで。`docs/pipeline.md`）。人間は何もしなくてよいので、誰の番は「なし」で、操作のボタンも無い。「止まった」と同じく、`ai:retry` を無視して表の残りで判定した段階を「やり直し待ちになる前の段階」として一緒に持つ（今の段階の名前に使う）。ただし、最新のやり直しの記録（`<!-- auto-retry -->` のコメント。回数が読める物）より**後**に、先へ進んだ印があるときは、`ai:retry` が残っていても（パイプラインが外すまで十数分かかる）やり直し待ちにせず、そのときの段階を出す。印は、紐づくPRの作成・更新（新しいコミット）、CIチェックの完了、PRの修正依頼コメント、実装AIの作業中のコメント。記録と同じ時刻は進んだ扱いにしない。印が無いとき・記録が無い／読めないときは今までどおりやり直し待ち（`src/lib/status.ts` の `hasProgressedSince`）。
- やり直しの回数と理由：パイプラインがIssueかPRに書く記録のコメント（`<!-- auto-retry -->` を含み、`🔁 …（やり直し n/10回）。` の次の行が `理由：…`。`.github/scripts/pipeline-lib.sh` の `write_retry_record`）のうち最新の物から読む。読めたら理由の横に「n/10回」を出す。記録が無い・読めないときは回数を出さない（理由も無ければ「AIが止まりました」）

マージ待ちの「誰の番」：
- PRに `ai:hold` がある → 人間（マージを押す）
- レビューが「指摘なし」で終わっていない（レビューしていない・指摘あり） → AI（パイプラインがレビューに回すか、直させる）
- それ以外 → AI（パイプラインが自動でマージする直前）

企画AIの質問（`ai:question`）：
- 企画AIが、決めてもらわないと清書できないことを、Issueのコメントで聞く。パイプラインがIssueに `ai:question` を付ける。人がIssueにコメントすると、パイプラインが自動で続き（企画）を始める
- 「質問のコメント」：そのIssueのコメントのうち、1行目（前の空白を除く）が質問の印 `<!-- ai-question -->` の物（`<!-- ai:question -->`・`<!-- question -->` も同じ扱い。大文字小文字は問わない）で、作者がパイプラインかオーナーの物だけ。ほかの人の物は無視する（偽の質問や画像を出さない）。「パイプライン」は、作者の名前が `…[bot]` で終わる物（`claude[bot]`・`github-actions[bot]`・パイプラインの App のボット。GraphQL の Bot にも `[bot]` を付ける）。「オーナー」は、そのリポジトリの `owner`（`owner/repo` の `owner`。組織のリポジトリでもその名前。大文字小文字は区別しない）。複数あれば、いちばん新しい物だけを使う
- 質問：`**Q1. …**`（`**Q1.** …` も可）の行。選択肢：その下の `- A. …` の行（`*`・`A)`・`A：` も可。次の質問・見出し・画面案の印まで）。`（おすすめ）`（半角の括弧も可）が付いた選択肢がおすすめで、表示の文からは外す。選択肢の無い質問もある
- 画面案：同じコメントに画面案の印 `<!-- ai-mocks: issue-N/rR -->`（画面案を置く `.github/scripts/mocks-publish.sh` が書く形。`: …` が無い `<!-- ai-mocks -->`・`<!-- mockups -->` も同じ扱い）があれば、その後ろの `<img src>` を画面案として読む。`A`・`B` の見出しの行（`### A. 明るい`・`**A案**` など）の後ろの画像がその案。見出しが無い画像は、前半を A、後半を B にする。`alt` か同じ行に「スマホ」「モバイル」「mobile」「phone」「SP」があればスマホの画像、無ければ PC の画像。URL は `https://` か、同じサイトの `/` で始まるパス（デモ）だけを使い、ほか（`http://`・`javascript:`・`//` で始まる物など）は出さない。URLはそのまま `<img>` に使う（こちらでは取り込まない）
- 読み取りと答えの文の組み立ては `src/lib/question.ts` の純粋関数（`parseQuestionComment`・`isQuestionAnswered`・`composeAnswer`）。取得するデータは増やさない（コメントは同期の問い合わせで取っている）
- 答えの文（`composeAnswer`）：選んだ画面案の文字（`A`）、選んだ選択肢（`Q1はB（明るい）`。その質問に自分で書いた文があれば `Q1はB（明るい）：もう少し青く`、選ばずに書いただけなら `Q1：もう少し青く`）を、この順に `。` でつなぐ。書いた文の末尾の `。` は外す。「ほかに伝えたいこと」は空行をあけて最後に付ける。例：`A。Q1はB（明るい）`。何も選ばず・書いていなければ空で、送らない
- 待ち時間の起点は、質問のコメントの時刻（無ければ `ai:question` が付いた時刻）
- 保留（`ai:skip`）のIssueに、答えていない質問のコメントが残っているときも、`ai:question` が無くても同じ「質問」の段階にして、同じ答える欄を出す（種類の札は `Question`）。答えを送ると `ai:skip` を外して `ai:plan` を付ける（「操作」の `答えを送る`）。答えていない質問が無い保留は、今までどおり「保留」

工場の相談（`factory:wait`）：
- テンプレートの工場（`factory-talk.yml`。`docs/pipeline.md` の「相談してから作る」）が、案・見た目の方向・ざっくり画面・最終確認の4つの段階で、Issueのコメントに選択肢と質問を書き、`factory:wait` を付けて返事を待つ。オーナーがコメントすると、工場が `factory:wait` を外して次の段階を作る
- 「工場の相談のコメント」：そのIssueのコメントのうち、作者が `github-actions[bot]`（パイプライン。質問のコメントと同じく、ほかの人の物は無視する）で、本文に印 `<!-- factory-talk:v1:BASE64 -->` がある物。複数あれば、いちばん新しい物だけを使う。BASE64 の中身は、UTF-8 の JSON（工場の `state`。形は ai-dev-template の `.github/scripts/factory-talk.py`）。読めない（BASE64・JSON・オブジェクトでない）物は無いものとする。うまく作れなかった・読み取れなかったときのコメント（1行目が `🤔`・`⚠️` で始まる）にも同じ印が付くので、その1行目（印と `🤔`・`⚠️` を除いた文）を「工場からのお知らせ」として選択肢の上に出す
- `state` から読む物：`stage`（`ideas` 案・`looks` 見た目の方向・`mocks` ざっくり画面・`confirm` 最終確認）、その段階の選択肢、質問 `ask.questions`（各 `{ q, options, recommend }`。`recommend` は `options` の何番目（0から）がおすすめか）、`assets`（段階ごとの画像の置き場）
  - 案（`ideas`）：`ideas` の各 `{ name, stack, title, pitch, who, novel, paid, screen }`。選ぶ値は番号（1から）の文字（`"2"`）
  - 見た目の方向（`looks`）：`looks` の各 `{ n, title, idea, colors, fonts }`。画像は1枚（`look-{n}-1440.png`）。選ぶ値は `n` の文字（`"1"`）
  - ざっくり画面（`mocks`）：`mocks` の各 `{ key, title, note }`（`key` は `a`・`b`）。画像は PC（`mock-{key}-1440.png`）とスマホ（`mock-{key}-390.png`）。選ぶ値は `key`（`"a"`）
  - 最終確認（`confirm`）：`confirm` の `{ name, stack, description, free, paid, price, pages }`、決まった事 `answers`（各 `{ q, a }`）、選んだ画面 `mock`（画像は `mocks` の置き場の `mock-{mock}-1440.png`・`-390.png`）。選ぶのは「作る」か「直す」
  - `stage` がこの4つでない・選択肢が読めないときは、選択肢を出さず「答えを書く」の欄だけを出す（書いた文をそのままコメントにする。印は付けない）
- 画像の URL：工場のコメントの `<img>` のうち、`alt` が決まった形（見た目の方向 `方向{n}`、画面 `{A|B} PC`・`{A|B} スマホ`、最終確認 `選んだ画面`・`選んだ画面 スマホ`）の物の `src` を使う。無ければ `assets` から `https://raw.githubusercontent.com/{owner}/{repo}/factory-talk/{assets[段階]}/{ファイル名}` を作る（最終確認は `assets.mocks`）。どちらも「企画AIの質問」の画像と同じく、`https://` か同じサイトの `/` で始まるパスだけを使う。`assets` の値は英数字・`-`・`_`・`.`・`/` だけで、`..` を含まない物だけを使う
- 答えの送り方：画面で選んだ・書いた物から、人が読める文と、その下（空行のあと）に印 `<!-- factory-answer:BASE64 -->` を付けたコメントを組み立てて送る。BASE64 の中身は UTF-8 の JSON `{"action":"pick"|"redo"|"go","choice":"2"|"a"|null,"answers":[{"q":"質問の文","a":"答えの文"}],"note":"注文（無ければ空）"}`（工場はこの印があれば、AIを通さずにそのまま読む）
  - 1つ選んだ：`action` は `pick`、`choice` は選んだ値。人が読める文の頭は `案2を選ぶ`／`見た目の方向1を選ぶ`／`画面Aを選ぶ`
  - 「全部ちがう」（案・見た目の方向・画面）：`action` は `redo`、`choice` は null、`note` はどう変えてほしいか（書かないと送れない）。文の頭は `全部ちがう：{note}`
  - 最終確認の「作る」：`action` は `go`。文の頭は `作る`。「直す」：`action` は `redo`、`note` は直してほしい内容（書かないと送れない）。文の頭は `直す：{note}`
  - 質問の答え：選んだ選択肢の文（自分で書いた文があれば `{選択肢}：{書いた文}`、書いただけなら書いた文）を、`answers` に `{ q: 質問の文, a: 答え }` で入れ、人が読める文には `Q1：スマホが中心` の形で、頭の後ろに `。` でつなぐ
  - 「ほかに伝えたいこと」（1つ選んだ・作るときだけ。全部ちがう・直すは、書いた文が注文）：`note` に入れ、人が読める文の最後に空行をあけて付ける
  - 書いた文の末尾の `。` は外す。注文は400文字、質問の答えは200文字まで（工場が切る長さ）。例：`案2を選ぶ。Q1：スマホが中心` ＋ 空行 ＋ `<!-- factory-answer:… -->`
  - 何も選んでいない（全部ちがう・直すで何も書いていない）ときは空で、送らない
- 読み取りと組み立ては `src/lib/factoryTalk.ts` の純粋関数（`parseFactoryTalk`・`isFactoryAnswered`・`composeFactoryAnswer`・`parseFactoryAnswer`）。取得するデータは増やさない（コメントは同期の問い合わせで取っている）
- 送るのは「答えを送る」（「操作」の表）。工場の返事は、オーナー（リポジトリの持ち主）のコメントだけを読む
- 答えを送ったあと、工場が `factory:wait` を外すまでの間は企画中（AIの番）。外したあとは、今までどおり（`新サービス：` のIssueなら、ラベルが無い未着手として「あなたの番」に出さない）
- 待ち時間の起点は、工場の相談のコメントの時刻（無ければ `factory:wait` が付いた時刻）

パイプラインが自動で進める間の猶予（PR作成待ち・未着手）：
- PRの作成も、最初の「おまかせ」（受付が `ai:plan` を付ける）も、パイプラインが入っていれば自動で起きる。実装のジョブが確認コマンドなどを終えてから進行役がPRを作るので、完了コメントからPRができるまで数分かかる。その間に人間が押す物は無いので、「あなたの番」にも、その件数にも入れない
- 対象は「パイプラインが動いている」リポジトリだけ（`pipeline` が `running`）。動いていない・分からない・未設定のリポジトリは対象外で、今までどおり人間の番
- **PR作成待ち**：実装AIの最後の結果が完了コメントまたはエラーのコメントで、実装AIが終わった時刻（完了コメントの `updatedAt`。無ければ `createdAt`。下の「実装AIの完了コメント」）から**15分未満**の間は、段階はPR作成待ちのまま、誰の番を「AI」にする（種類の札・短い説明は「PRを作成中」）。ちょうど15分で猶予は終わる。コメントの `createdAt` は実装を始めた時刻なので、そこから数えると、15分より長い実装では、終わった時点でもう猶予が切れていて、パイプラインがPRを作る前に `PRを作る` が出てしまう。15分たってもPRが無いとき、完了コメントの時刻が読めないときは、今までどおり人間の番（`PRを作る` が出る。エラーのコメントなら `implementError` も true のまま）。エラーで終わっても、今のパイプラインはブランチがあればPRを作るので、エラー直後の15分未満も猶予にする（猶予の間は `implementError` が true でも「PRを作成中」を優先し、猶予が切れたらエラー表示）
- **未着手**：Issueの `createdAt` から**10分未満**の間は、段階は未着手のまま、誰の番を「AI」にする（短い説明は「受付中」）。ちょうど10分で猶予は終わる。10分たっても `ai:` ラベルが付かないときは、今までどおり人間の番（`おまかせ` が出る）。`新サービス：` のIssue（工場が受け持つ）は猶予にせず、今までどおり
- 猶予の間は「動いている」件数（`isRunningStage`）に数え、今の段階の名前（PR作成待ち＝PR、未着手＝清書）以外は変えない。「あなたの番」に出さず、ボタン（`PRを作る`・`おまかせ`・`実装を依頼`）も出さない（サーバー側でも受け付けない）。「いまの様子」（会話）に、パイプラインの番の文（`パイプラインがPRを作っています` など）で出す
- 時間の判定は、サーバーの「今」（`now`。デモは `DEMO_NOW`）で行う。判定は `src/lib/status.ts`（`isWithinGrace`・`PULL_GRACE_MS`・`INTAKE_GRACE_MS`、結果は `IssueStatus.grace`）。猶予の時間は設定で変えられない

- 「紐づくPR」：本文に `Closes #<番号>`（大文字小文字は問わない、Fixes/Resolvesも可）を含むか、ブランチ名が `claude/issue-<番号>-` で始まるPR
- 「公開ステータス」：マージコミットのコミットステータス（GraphQL の `mergeCommit { status { contexts } }`。context ごとの最新）のうち、context が `Vercel` で始まる、または `deploy/` で始まるもの。VercelはGitHubのDeploymentではなく、ここに結果を書く（2026年10月25日に実データで確認）。`deploy/<種類>` はパイプラインが書く
- 公開失敗の理由：公開失敗の行では、context ごとの最新が failure・error のものの `description`（Vercelが失敗の理由を書く）を理由として出す。失敗しているのが Vercel の1つだけなら `description` だけ。それ以外（`deploy/` の context が失敗しているとき）は、`{種類}：{説明}` を1行ずつ（種類は context の `deploy/` の後ろ。Vercel は「Vercel」）。`description` が空の物は出さず、出す物が無ければ理由は出さない。「rate limited — retry in N hours」の形（N の単位は分・時間・日）は「利用上限に達しました。あとN時間で再開します」のように日本語にし、それ以外は `description` をそのまま出す。Nは `description` の数字をそのまま使う。出す場所は「あなたの番」の公開失敗の1件の、説明文の下だけ（`TurnItem` の `note`。理由の取り出しは `src/lib/deployFailure.ts`）
- 公開先のリンク：「いまの様子」（会話）の公開済みのメッセージで、context ごとの最新が success かつ `target_url` が `https://` で始まる物は、文字のリンク `開く ↗`（新しいタブ）を出す。複数あれば種類の名前つきで並べる（`App Runner ↗` `Releases ↗` `Expo ↗`。それ以外の種類は context の `deploy/` の後ろをそのまま）。`target_url` が無い・`https://` で始まらないときは出さない（`src/lib/deployStatus.ts` の `deployLinks`）
- 公開ステータスが無いまま30分以上たったもの（Vercelをつなぐ前にマージしたものなど）は「公開済み」に入れ、会話の文に「公開状況は分かりません」と出す
- 「GitHub ActionsのCIチェック」：チェックランのうち、作ったアプリが `github-actions` のもの（APIの `app.slug`）で、Claude Reviewのチェック（名前が `review`）を除いたもの。Vercelのチェック（`Vercel Preview Comments` など）は数に入れるが、これだけでは「CIが通った」とみなさない
- 「実装AIの完了コメント」：`claude[bot]` のコメントで `Claude finished` を含むもの
  - AIのアクションは、作業の始めにコメント（`Claude Code is working…`）を書き、終わったときに同じコメントを完了（`Claude finished …`）・エラー（`Claude encountered an error …`）の文に書き換える。だから結果のコメントの `createdAt` は「始めた時刻」で、「終わった時刻」は `updatedAt`（無ければ `createdAt`。`src/lib/status.ts` の `implementFinishedAt`）。PR作成待ちの猶予・待ち時間の起点・出来事の時刻は、終わった時刻を使う（2026年11月16日の agent-desk #300 は、作成 01:38:39・書き換え 01:49:59 で、11分ずれていた）
  - 「作業中のコメント」：`claude[bot]` のコメントで `Claude Code is working` を含み、まだ結果の文に書き換わっていないもの（`isImplementWorkingComment`）。やり直し・再開で `ai:implement` が付け直されると、前の結果のコメントは残ったまま、新しい実行が新しい作業中のコメントを書く。最後の結果のコメントより後に作られた（`createdAt` が新しい）作業中のコメントがあり、`ai:implement` が付いている間は、AI作業中にする（前のエラーコメントを見て、動いている最中に「AIがエラーで止まりました」と `PRを作る` を出さない）
- 閉じたIssueは、紐づくPRがマージ済みなら表示する（公開済みまでを追うため）。それ以外の閉じたIssueは表示しない
- 「誰の番が人間」のものは「あなたの番」に出す。止まった物がいちばん先（それ以外は「いまの様子」（会話）に出す）
- 止まった物の説明文の理由は、次の2つのうち `createdAt` が新しい方を使う。どちらも無ければ「自動で進められず止まりました」
  - パイプラインがPRに書いた最新の「⏸ 自動で進めるのを止めました：{理由}」の理由
  - 清書AIの「お願いのコメント」の理由。Issueのコメントのうち、作者が `claude[bot]` で、本文に `<!-- human-request -->` を含む最新の物が「お願いのコメント」（清書AIが「人間にしかできない作業」と判断したときに、パイプラインが1行目にこの印を付け、2行目に要点の1文を書く）。理由は、印の行より後の最初の空でない行（前後の空白を除く）で、空なら無いものとする。作者が `claude[bot]` 以外のコメントは、印があっても使わない
  - 理由の末尾に `。` があれば、「。確認して…」とつなげるときに重ならないよう1つにする（下の原因の取り出しのあとの文に対して行う）
- `ai:hold` のマージ待ち（人間の番）の説明文は、PRの本文の「お願い」を使う。見出し（`#` 1〜6個で始まる行）の文字に「人間にお願いしたいこと」を含む節を探し、無ければ「人間が手で確認すべきこと」を含む節を探す（それぞれ最初に見つかった節）。節の中身は、見出しの次の行から次の見出しの手前まで。空の行を除き、行頭の `- `・`* `・`1. ` の形の印と前後の空白を取る。残った行が無い、または最初の行が「なし」「特になし」「無し」なら、お願いは無いものとする（節が見つかったあとは、もう一方の節は探さない）。取り出しは `src/lib/humanRequest.ts` の純粋関数で、取得するデータは増やさない
- **止めている印**（Issue #394。`ai:hold` のマージ待ちが、ほかの順番待ち `ai:queue` を止めているしるし）：パイプラインが、止めている `ai:hold` のPRに `<!-- hold-blocking: #12,#15 -->` のコメントを付ける（待つ Issue が変わると更新される）。PRのコメントのうち、作者が `…[bot]`（人でない）で、本文に `<!-- hold-blocking: … -->` を含む最新の物（`createdAt` が新しい方）から、`#` の後ろの数字を全部取る（同じ番号は1つ）。最新の印が空・数字が読めない物は、印が無いものとする（古い印には戻らない）。印が無いPRは今までどおり。作者が人のコメントは、印があっても使わない。読むのは `src/lib/holdBlocking.ts` の純粋関数 `parseHoldBlocking` で、取得するデータは増やさず、追加のAPI呼び出しもしない
  - 印のあるマージ待ち（`ai:hold`・人間の番）の1件には、説明文の下の補足（`TurnItem.note`）に `マージすると #12（題名）・#15（題名）が動き出します` を1行出す（1つなら `マージすると #12（題名）が動き出します`）。題名はそのリポジトリの Issue から引き、見つからない番号は `#12` だけにする（`holdBlockingNote`）。名札は付けない。「あなたの番」の並びは、下の「あなたの番（真ん中の1件）」
- 止まった理由・やり直しの理由（パイプラインの `failure_reason`）は、文の末尾が `（原因：{原因}。ログ：{URL}）` の形のことがある。原因の中に `（）` が入れ子で入るので、末尾から見て `。ログ：` の位置で分け、`{ text: 説明, cause: 原因 | null, logUrl: URL | null }` に取り出す（`src/lib/failureReason.ts` の純粋関数。形が合わなければ `{ text: 元の文, cause: null, logUrl: null }`）。URLは `https://github.com/{owner}/{repo}/actions/runs/{数字}` で、`{owner}/{repo}` がその行のリポジトリ（大文字小文字は区別しない）と一致するときだけ `logUrl` にする。それ以外（別のサイト・別のリポジトリ）は `logUrl: null` で、URLは表示しない
- 画面には理由の代わりに `{説明}（{原因}）`（原因が無ければ `{説明}`）を出し、URLは文に入れない。「あなたの番」の1件と「いまの様子」（会話）のメッセージでは `logUrl` があるときだけ `ログを開く ↗` のリンクを出す。Actionsのログ本文はAPIで取らない

  - 押した時点で段階が変わっていて何もしなかったとき（`ok: false` かつ `changed: true`）：結果は出さず、エラーも出さず、今までどおりすぐ片づけて画面を取り直す（マージしていないのに「マージしました」と出さないため）
  - 成功（`ok: true`）：行の中身（説明文・補足・答える欄・ボタン）を、その場で結果に置き換える。種類の札・番号・題名は残す。結果は、緑のチェックと `〜しました`（`role="status"` で読み上げる）。マージは続けて `PR #番号 ↗`（GitHub の PR へのリンク）と、止めていた物があれば `#12 が動き出します`（`TurnItem.blocking`。無ければ出さない）。最後に `閉じる`
  - 結果は2.4秒見せ、行を150msのフェードで消してから、今までの「片づける」（`inert`・次の1件へ替える・8秒の戻し）に進む。`閉じる` を押せば、フェードせずすぐ片づける
  - `ほかに N件` は、結果を出し始めた時点で1つ減らす。次の1件（一覧なら繰り上がり）が出るのは、結果が消えたあと。結果を見せている間に取り直しで行のデータが消えても、結果は押した時点の中身のまま最後まで見せる（`src/lib/operationResult.ts` の `withHeldRows`。押してから片づけるまで、Desk がその行の中身を預かる）
  - フォーカス：成功したときフォーカスが行の中にあれば `閉じる` へ移す。結果が消えるときは、今の片づけと同じ決まり（次の1件の最初のボタン、無ければ見出し）で移す
  - 失敗（`ok: false` かつ `changed: false`）：ボタンを元の文字（`マージする` など）に戻し、説明文を戻し、理由を今までどおり行の下に出す
  - マージ待ちの一覧の行も同じ：その行だけが `マージ中…` → `マージしました` に変わり、2.4秒後に消えて次の行が繰り上がる。ほかの行は動かさない

### PCの3ペイン（幅900px以上）

ホームとリポジトリのページ（デモも同じ）が3ペイン。`/repos` は左のバーと中央の1本の列だけ（右の列と入力欄は無い）。設定・Issueを書く・ログイン・見つからないページは今までどおり1本の列。スマホ（幅899px以下）は、左の一覧と進捗図の列は出さない（1本の列のまま）。ただし下のIssueを追加する入力欄は、スマホでも同じ部品を出す。

- **左：リポジトリの一覧**。上端の帯の札（**動きのあるリポジトリだけ**［あなたの番かAIの番が1件以上。今開いているリポジトリは 0・0 でも。Issue #451。「すべてのリポジトリ」の節］と、最後に `すべてのリポジトリ`。件数の点と数も同じ）を縦に並べた物。押すと、そのリポジトリのページへ移る（今の切り替えと同じ動き）。この画面では上端の帯の札は出さない（同じ物を2か所に置かない）。リポジトリが多くても、スクロールするのは小見出しと札の一覧（上の段）だけで、`新サービス`・並列の状態のボタン・ユーザー名のボタン（下の段）はスクロールせず、いつも左のバーの下端に見える（バーごとスクロールしない。2026年11月18日、Issue #439）。隠れた札があるときだけ、上下の境目に細い線が出て、いちばん下までスクロールすると消える

#### 進捗図

1つのIssueが、上から下へ、どの工程まで進んだかの図。PCの3ペインの右の列に出す。

- 描くIssue（`src/lib/flowTarget.ts` の純粋関数 `pickFlowTarget`）：
  - 「いまの様子」の行を選んでいれば、その1件（動いていない行・公開済みの行でも）
  - 選んでいなければ、「あなたの番」に出ている1件（片づけて次の1件に替わったら、その1件）。無ければ、「いまの様子」で動いている（`isRunningStage`）物のうち、いちばん新しい出来事がある（並びのいちばん下に近い）1件。どちらも無ければ、図の場所に `いま動いている作業はありません` を出す
- 図の対象を選ぶ（PCだけ）：「いまの様子」の行を押す（行のどこでも。リンク・ボタンと、文字を選んでいるときは除く）か、行の番号（`todo-app#21`）のボタンにフォーカスして Enter。選んだ行は見て分かる（見た目は `docs/design.md` の「いまの様子」）。同じ行をもう一度選ぶと選びを外し、今まで通りの1件に戻る（`toggleFlowSelection`）。選んだ行が取り直しで消えたら、選んでいない扱い。選びはその画面にいる間だけ覚える（ページを移ったら外れる）。スマホは右の列が無いので、この「選ぶ」は使わない（次の「スマホ」）
- 工程は7つで、この順に上から下：企画・デザイン・実装・CI・レビュー・修正・公開。1工程＝1行
- 各行：工程のアイコン、工程名、その下にモデル名（記録が無ければ `不明`）と所要時間（`不明 · 3分12秒`。出せなければモデル名だけ）、右端に開始時刻（`10:01`、日本時間。出せなければ出さない。行の高さは変えない）と状態の印（成功＝チェック、失敗＝×、進行中＝回る印、待ち＝`…`）。モデル名・所要時間・開始時刻は、次の「モデル名と所要時間」で読む
- 工程の状態の決め方は `src/lib/flow.ts` の純粋関数 `getFlow`（入力：`IssueStatus`。出力：7つの工程の状態と、今の位置）。止まった・やり直し待ちは、その前の段階で位置を決める
  - 今の位置（`at`）と、その工程の状態：

  | 段階 | 今の位置 | 状態 |
  | --- | --- | --- |
  | 未着手・順番待ち・保留・質問・工場の相談 | 企画 | 待ち（猶予の受付中は進行中） |
  | 企画中 | 企画 | 進行中 |
  | AI作業中 | 実装 | 進行中 |
  | PR作成待ち | 実装 | 成功（PRを作成中は進行中。エラーで止まった直後の猶予の間も進行中、猶予が切れた実装AIのエラーは失敗） |
  | CI中／CI失敗 | CI | 進行中／失敗 |
  | レビュー中 | レビュー | 進行中 |
  | 修正中 | 修正 | 進行中 |
  | 修正の確認中（修正したあとのCI中・CI失敗・レビュー中） | 修正 | 進行中（CI失敗なら失敗） |
  | マージ待ち（レビューが指摘なしで終わっていない） | レビュー | 待ち |
  | マージ待ち（ほか） | レビュー（修正したなら修正） | 成功 |

##### モデル名と所要時間

ai-dev-template がIssueに残す「進捗ログ」のコメント（形式は `docs/pipeline.md` の「進捗ログ」）から読む。

- 探す：描くIssueのコメントのうち、先頭の行（前の空白を除く）が `<!-- ai-step-log -->` の最初の1つ。コメントは `GET /repos/{owner}/{repo}/issues/{番号}/comments?per_page=100`（最大5ページ）で取る（REST。トークンはサーバー側だけ）。`src/lib/github/stepLog.ts`
- 読む行：`<!-- ai-step {JSON} -->` の行。`src/lib/stepLog.ts` の純粋関数 `parseStepLog`。`step`（`plan` / `mocks` / `implement` / `ci` / `review` / `fix` / `deploy`）・`model`（文字列か `null`）・`started`（時刻）・`finished`（時刻か `null`。項目そのものは必須）・`result`（`running` / `success` / `failure`）が揃った行だけ使い、壊れた JSON・知らない `step`・欠けた項目・時刻が読めない行は読み飛ばす。同じ工程の行が複数あれば最後の行を使う
- 工程の対応：企画＝`plan`、デザイン＝`mocks`、実装＝`implement`、CI＝`ci`、レビュー＝`review`、修正＝`fix`、公開＝`deploy`。CI失敗時の分岐の「修正 n回目 / 3」の行のモデル名（読み上げ）は、修正の記録のモデル名（所要時間は出さない）。開始時刻は、いちばん下（n回目）の行にだけ、修正の記録の開始時刻を出す（前の回の記録は残らないため）
- 開始時刻：`started` を日本時間の `10:01` にする（`formatEventTime`）
- モデル名：`model` の文字列をそのまま出す（`opus` など）。`null`（`ci`・`deploy`）・記録が無い工程は `不明`
- 所要時間：`finished - started` を短い日本語にする（`formatDuration`）。1分未満：`45秒`、1分以上：`3分12秒`（秒が0なら `3分`）、1時間以上：`1時間5分`。進行中（`finished` が `null`）は、読み込んだ時点（サーバーの今）までの経過時間。負になるときは出さない

- コメントが取れない（API エラー・権限）・コメントが無い・1行も読めないときは、記録が無い扱い（全部 `不明`、所要時間なし）にして、図は出す。エラーの文は出さない
- デモ（`/demo`）は、デモのデータの進捗ログのコメント（下の「デモ」）から読む（GitHub には問い合わせない）。記録が無い工程は、モデル名を `不明` と出さず、モデル名の欄を出さない（`hideUnknownModels`）。本物のデータでは、記録が無い工程・進捗ログはあるが記録が無い工程は、今までどおり `不明`

##### CI失敗時の分岐

CIが失敗したとき、CIの行の下に字下げした枠が開き、中に「修正 1回目 / 3」から「修正 n回目 / 3」までを1回ずつ縦に並べる。枠の左の縦の線が、修正からCIに戻る線（縦の図に合わせた表し方。2026年11月16日、Issue #300）。CIが失敗していないIssueの図は変えない（枠も線も出さない）。

- 前の回（1〜n−1回目）は成功（直し終えている）、n回目は下の表の「修正ブロック」の状態

- 分母は 3（Issue #290）。修正の回数は「修正した」の数（紐づくPRの「直して」の依頼の数）を使う
- **修正の上限**（Issue #411）：自動で直す回数の上限は3（普通のモデルで2回＋最後に opus で1回。パイプラインの `request_fix_or_stop`）。画面のどこでも同じ数を使う（「いまの様子」の「AIが直しています（n/3 回目）」・「あなたの番」「いまの様子」の説明・最近の出来事の「修正を依頼 n/3」・この図の「修正 n回目 / 3」・止まった理由）。3回目も「3/3」と出し、「2/2」にしない。上限は、紐づくPRの最新の修正依頼コメントの `（自動の依頼 n/N）` の N から読む（`src/lib/status.ts` の `readFixLimit`・`autoFixLimit`）。読めなければ（コメントが無い・形が違う・N が1未満）3。定数は `src/lib/flowBranch.ts` の `FIX_MAX` の1か所（`MAX_AUTO_FIX` はこれと同じ値）。修正した回数（`fixCount`）は、依頼コメントの数をこの上限までにした数
- 判定は `src/lib/flowBranch.ts` の純粋関数 `getFlowBranch`（入力：CIの結果（まだ・実行中・失敗・通った）と修正の回数。出力：枠を出すか（null なら出さない）・n・修正ブロックの状態・枝の状態・戻る線を出すか）。`getFlow` の結果の `branch` に入る。CIの結果は段階から決める：CI中＝実行中、CI失敗・修正中＝失敗、レビュー中・マージ待ち・公開＝通った、それより前＝まだ（止まった・やり直し待ちは止まる前の段階）

| 場合 | 枠 | n | 修正ブロック | 戻る線 | 枝 |
| --- | --- | --- | --- | --- | --- |
| CI失敗（修正0回） | 出す | 1 | 進行中 | 出す | 進行中の枝 |
| 修正の依頼が出て直している間（k回目） | 出す | k | 進行中 | 出す | 進行中の枝 |
| 直したあとにCIがまた失敗（k回直した） | 出す | k+1 | 進行中 | 出す | 進行中の枝 |
| 直したあとのCI中（k回直した） | 出す | k | 成功 | 出す | 進行中の枝 |
| 3回直してもCIが失敗 | 出す | 3 | 失敗（ここで止まる。新しい動きは足さない） | 出す | 進行中の枝 |
| CIが通った（1回以上直した） | 出す | 直した回数 | 成功 | 出す | 通らなかった枝（グレー） |
| CIが通った（直していない）・CIがまだ・CI中で直していない | 出さない | － | － | － | － |

- n は 1〜3 に収める。止まったときは修正ブロックを失敗にする
- 通らなかった枝：CIが通ったあと、枠（失敗したCIと修正）と戻る線をグレーにする。進行中の枝は通常の色
- 読み上げ：枠は `role="group"` で `CI失敗時の修正`（グレーのときは `（通らなかった枝）` を付ける）、修正の各行は `修正 1回目 / 3　進行中　モデル 不明` のように文字で言う（開始時刻があれば `　開始 11:14` を続ける）
- スマホ（幅899px以下）は進捗図を出さないので変わらない

  3. どちらも無ければ何も出さない
- **CI失敗のあと自動で直している間は動いている表示にする**（2026年11月17日、Issue #402）：段階がCI失敗（`ciFailed`）のうち、パイプラインがこれから自動で直す間（`ai:stuck` でなく、修正の回数が上限の 3 に達していない）は、× でなく動いている表示にする：ランプは動作中（緑）、状態の印は回る印、話し手は `AI`、文は `AIが直しています（n回目/3）`（n は右の進捗図の「CI失敗時の分岐」の n。`getFlowBranch` と同じ）。修正の依頼が出る前の短い間も同じ（右の図が「修正 1回目 進行中」としているため）。× にするのは、本当に止まったとき（`ai:stuck`＝止まった段階、または修正の上限までCIが失敗）だけで、文は `CIが失敗しました。修正の上限に達しました`。「あなたの番」には出さない（今までどおりAIの番）。他の段階の表示は変えない。判定は `src/lib/ciFailureState.ts` の純粋関数 `ciFailureState`（入力：段階・`ai:stuck` か・修正の回数。出力：動いている（n）／止まった／CI失敗でなければ null）で、テストを書く
- 理由（順番待ちの理由・やり直し待ちの理由）は、今の様子の文の下に、最初は折りたたんで `理由を見る` のボタンだけ出す（Issue #403）。押す（Enter／Space も）と開いて理由を出し（ボタンは `理由を閉じる` になり、もう一度押すと閉じる。`aria-expanded`）、やり直しの理由にこのリポジトリのログのURLがあれば `ログを開く ↗`、公開済みで公開先があれば `開く ↗`（複数なら `App Runner ↗` など種類の名前つき）を続ける。このボタンを押しても、行の進捗図の選択・開閉は動かない。開いた状態はその画面にいる間だけ覚え（ページを移ったら閉じる）、取り直しで消えた行の分は捨てる
- **順番待ちは1つのまとまり**（2026年11月17日、Issue #405）：段階が順番待ち（`queued`＝`ai:queue`・`ai:blocked`）の行は、動いている作業の行とは分け、1つのまとまり `順番待ち N件` にする。まとまりは動いている作業の行より上（見出しとお知らせの直下）に置き、最初は畳んで `順番待ち 9件（次：#136）` の1行だけ出す（`次：` は始まる順の先頭の1件。2つ以上のリポジトリを出しているときは `次：todo-app#136`）。押す（Enter／Space も。`aria-expanded`）と開き、もう一度押すと閉じる。開いた状態はその画面にいる間だけ覚える。0件のときはまとまりを出さない。見出しの件数（`9件`）は、順番待ちも含めた全部の数のまま
  - 開くと、始まる順に1行ずつ：番号（2つ以上のリポジトリを出しているときは `todo-app#21`）・題名（Issue へのリンク）・リポジトリ名・何の後か（`#135 の後`。理由に `#番号` があるとき＝`queueAfterNumber`。取れなければ出さない）。待っている理由の文は、ほかの行と同じ `理由を見る` で折りたたむ。行を押したときの進捗図の選択・開閉は、ほかの行と同じ
  - 「始まる順」は、リポジトリごとのランプの待ち順（「ランプ」の `assignLamps`：急ぎ `priority:high` の `ai:queue` → ほかの `ai:queue` → `ai:blocked`、それぞれ番号の小さい順＝行の `· 2番目`）。リポジトリが違えば、リポジトリの並び（ホームの左の一覧と同じ順）
  - 分け方・並べ方は `src/lib/queueGroup.ts` の純粋関数 `splitQueue`（入力：メッセージの配列・リポジトリの順。出力：順番待ちの行（始まる順）と、それ以外の行）で、テストを書く。デモ（`/demo`）も同じ
- 並び（順番待ち以外の動いている作業）：上が古く、下が新しい（会話アプリと同じ向き。Issue #318）。直近3日に出来事が無い物がいちばん上（番号の小さい順）、その下に出来事がある物を、いちばん新しい出来事が古い順に並べる。新しい物は下に足される（`compareMessages`）。そのさらに下に「あなたの番」が続く
- **公開済みは「過去の欄」（古い会話）として、中央のいちばん上に日ごとに並べる**（2026年11月17日、Issue #367。開閉の `公開済み N件 ▾` は無くした）。「公開済み」は今の段階（`src/lib/status.ts` の `deployed`）で決める（マージ済み・閉じた物を含む）。公開失敗（人間の番）・公開中は、ここには入れず今までどおり
  - **置き場所と並び**：中央の列のいちばん上、動いている作業（「いまの様子」の見出し）の上。古い順（上が古い）。同じ日の中は時刻の古い順（同じ時刻はキー順）。間に髪の毛ほどの線を入れて「いまの様子」と分ける。0件なら欄ごと出さない
  - **日の見出し**：`今日`・`昨日`・それより前は `11月15日`。同じ日の物はその下に続ける。日の区切りと時刻は日本時間（UTC+9。サーバーと画面で同じ結果にするため）
  - **1件は1行**：しるし（完了のチェック）・題名（長ければ「…」）・`リポジトリ#番号`（2つ以上のリポジトリを出しているときは `tochi-rirekisho#1`、1つだけなら `#1`）・公開した時刻（`09:20`。日の見出しの下なので日付は付けない）。公開した時刻は `ChatMessage.doneAt`＝その件の最新の出来事の時刻（`latestAt`）、無ければ紐づくPRのマージ時刻。どちらも無い物は出さない。押すと、PCは右の進捗図にその件を出し（「いまの様子」の行を押したときと同じ）、スマホはその行の下に進捗図を開く（「スマホ」の決まりと同じ）
  - **監視に追加したお知らせも混ぜる**（オーナーの追加）：自動で監視に足したリポジトリ（設定の「新しいサービスを自動で足す」）を、1件1行（`＋ tochi-rirekisho を監視に追加`・追加した時刻）で、追加した日の見出しの下に、公開済みと時刻順に並べる。押せない。「いまの様子」の上にまとめて出すのはやめた。古いお知らせの消し方は今までどおり（足してから24時間たった物、監視をやめたリポジトリの物は出さない。`buildAddedNotices`）
  - **読み足し**：最初に出すのは直近5件（新しい方から）。中央の列を上の端までスクロールする（上へ動いて、ページの位置が0に着いたとき。開いた直後には読み足さない）と、さらに10件ずつ読み足す。読み足したとき、見ていた位置が動かないよう、足した分の高さだけ位置を戻す。キーボード・読み上げ用に、いちばん上に `さらに前を読む` のボタンを置く（押すと同じく10件）。全部出したら、そのボタンの代わりに `ここまで` を1行出す。読み足した件数は、その画面にいる間だけ覚える
  - 出せるのは、今の取得でわかっている公開済みだけ（取得する範囲・期間は変えない）
  - 開いたとき・リポジトリを切り替えたときの位置は、下の「開いたときの位置と、追従」のまま（中身が多ければ最新が見える位置）。過去の欄は最初の5件までなので、最新（動いている作業・あなたの番）が最初の1画面に見える
  - 日ごとのまとめ・並び順・5件と10件ずつの区切りは `src/lib/pastLog.ts` の純粋関数（`buildPastItems`・`groupByDay`・`visibleCount`・`visiblePast`）で、テストを書く
- いちばん上に、お知らせ（あるときだけ）：見張り役が止まっているリポジトリ（「見張り役が止まっているリポジトリ」）と、取れなかったリポジトリ（`owner/repo：理由`）。自動で監視に足したリポジトリのお知らせは、ここには出さず、上の過去の欄に混ぜる
- 0件のとき：`動いている作業はありません`
- リポジトリのページでは、見出しの横に `todo-app だけ` と `GitHubで開く ↗`（デモの架空のリポジトリでは出さない）
- メッセージを作る処理は `src/lib/conversation.ts` の純粋関数 `buildConversation`（入力：取得済みのリポジトリのデータ・出来事・「今」。出力：メッセージの並び）で、テストを書く。今の様子の文は同じファイルの `chatLine`。出来事のまとめ（並び順と時間に使う、いちばん新しい出来事の時刻）は今までどおり `src/lib/eventGroups.ts` の `groupTrails`。公開済みかどうかは、`src/lib/events.ts` の `repoTrailEvents` が `EventIssue` に今の段階（`stage`）を足して渡す（段階の判定は変えない）

#### 開いたときの位置と、追従（Issue #318）

ページ全体のスクロールで、いちばん下を基準にする。

- 中央の列の中身は上から詰めて置く。足りない分は下に余白で残し、中身を下へ寄せない（上に空いた帯を作らない。PC・スマホ。入力欄は今までどおり中央の下端に付く）
- 画面を開いたとき・リポジトリを切り替えたときの位置（PC・スマホ。即座に送る）：
  - 中身が画面の高さ（上端の帯と入力欄を除く）に収まるときは、上から（位置は動かさない）
  - 中身が画面より多いときは、今までどおり最新（いちばん下）が見える位置
  - ただし「あなたの番」の1件に答える欄（工場の相談・質問）があるときは、その1件の上端（種類の札と題名）が上端の帯のすぐ下に来る位置で始め、最初の選択肢（キー操作の決まりで Tab が止まる物＝選ばれている物、無ければ先頭）にフォーカスを置く。答える欄がある1件が複数あるときは、大きく出ている1件（選ばれている1件）が対象。ボタンだけの段階は、上の2つのまま
- 新しい出来事は下に足される。利用者が上にさかのぼって読んでいる間（いちばん下から80pxより離れている）は、取り直しが来ても読んでいる位置を動かさない。いちばん下にいる間（80px以内）だけ、新しい物に追従して下へ即座に移す。ただし答える欄の中にフォーカスがある（読んでいる・書いている途中）ときは、いちばん下にいても位置を動かさない。さかのぼり中に新しい出来事が増えても、新着の知らせは出さない
- 判定は `src/lib/followScroll.ts` の純粋関数：`isNearBottom`（入力：ページの高さ・今の位置・画面の高さ。しきい値は80px）、`openPosition`（開いたときの位置。入力：ページの高さ・画面の高さ・答える欄があるか。出力：`top`／`answer`／`bottom`）、`shouldFollow`（追従するか）

#### ランプ

「いまの様子」の各メッセージ（パイプラインの行。「パイプライン · agent-desk#290」など。話し手を問わず全部）の左に、いま動いているのか・止まっているのかを示すランプ（左の細い線の色）を出す。ホーム・リポジトリのページ（デモも同じ）、スマホ・PC の両方。2026年11月16日、Issue #295 のオーナーの指示で足した（見た目は `docs/design.md` の「ランプ」）。

- 種類：`running`（緑の線＝動作中）／`needsHuman`（赤の線＝人間の手が必要）／`waiting`（紫の線＝順番待ち。待ち順つき。1行目の最後に `· 2番目`）／`none`（無彩色の線）
- 判定は `src/lib/lamp.ts` の純粋関数 `judgeLamp`（入力：Issue と紐づくPR（`findLinkedPull`）のラベル、お願いのコメントがあるか、その Issue・PR に関わる Actions の実行（実行中か待機中があるか・最後の更新の時刻。取れなかったら null）、Issue・PR の最後の更新の時刻、終わった物か、今の時刻。出力：種類）。上から順に見る：
  1. 関わる実行が実行中（`in_progress`）か待機中（`queued`）→ 緑（過去にエラーで止まっていても、お願いのコメントがあっても、いま動いていれば緑。最新の状態を優先）
  2. 終わった物（閉じた Issue・紐づくPRがマージ済み。公開中・公開済みなど）→ 何も出さない
  3. `ai:retry`（自動のやり直しの待ち時間）→ 緑
  4. `ai:stuck`・`ai:question`・`ai:hold` がある、またはお願いのコメント（`<!-- human-request -->`。作者が `claude[bot]`）があり、そのあとに人（作者が `…[bot]` でない）のコメントがまだ無い → 赤
  5. 進行中のラベル（`ai:plan`・`ai:implement`・`ai:review`）があるのに、最後に動いた時刻から**10分以上**（ちょうど10分を含む）たった →「止まっているかも」で赤。最後に動いた時刻は、関わる実行の `updated_at` の最新と、Issue・PR の `updatedAt` のうち新しい方（ラベルを付けた直後を止まっているとしないため）。実行が取れなかったときはこの判定をしない
  6. `ai:queue`・`ai:blocked` → 紫の線
  7. どれでもない → 何も出さない（無彩色の線のまま）
- **ラベルだけでは緑にしない**（`ai:implement` などが付いていても、関わる実行が動いていなければ緑にならない。`ai:retry` だけは例外）
- 紫の線の待ち順（`· 2番目` の数字）：そのリポジトリの、紫になった物の中での位置（1 が次に動く）。`ai:queue` のうち急ぎ（`priority:high`）が付いた物の番号の小さい順、次にほかの `ai:queue` の番号の小さい順、その後に `ai:blocked` の番号の小さい順（`assignLamps`）。パイプラインが順番待ちから始める順（`docs/pipeline.md` の「順番待ちの進め方」：先頭は `priority:high`、その中は番号の小さい順）に合わせる。`ai:blocked` は待ち先が閉じるまで動かないので、`priority:high` でも前に出さない。触るファイルが重ならない物は並べて始まることがあるので、数字は目安。リポジトリごとに数える（パイプラインの順番待ちはリポジトリごとのため）
- 読み上げとホバーの文言（`lampLabel`）：`動作中`／`人間の手が必要`／`順番待ち 2番目`
- 実行と Issue・PR の結びつけ（`isRelatedRun`）：実行のブランチ（`head_branch`）が `claude/issue-<番号>-` で始まる、紐づくPRのブランチと同じ、実行に紐づくPR（`pull_requests[].number`）が紐づくPR、または実行の題名（`display_title`）に `#<Issue番号>`・`#<PR番号>`（後ろに数字が続かない）がある
- 実行の取得（`src/lib/github/fetch.ts` の `fetchWorkflowRuns`。REST。GraphQL では取れないため）：リポジトリごとに `GET /repos/{owner}/{repo}/actions/runs?status=in_progress&per_page=100`・`?status=queued&per_page=100`（いま動いている物）と `?per_page=100`（最近の実行。最後に動いた時刻を知るため）の3つ。ほかの Actions の runs と同じく5分に1回だけ取り直し、間はサーバーのメモリの前の値を使う（「データの取得」）。ETag も同じ。1つでも取れない・形が違うときは「取れなかった」（null）で、緑にも「止まっているかも」の赤にもしない（ほかのデータの表示は落とさない）
- 「あなたの番」の1件（`TurnRow`）と進捗図には付けない。段階の判定・誰の番・並び順は変えない
- デモ：AIの番の段階（動いている段階と、誰の番が AI の段階。公開中を除く）の Issue ごとに、実行中の実行を1つ作る。`landing-page#16` だけは作らず、「止まっているかも」（赤）の見本にする

#### 出来事と、その時刻

「いまの様子」の並び順と時間（`12分前`）に使う出来事（直近3日、最大50件）と、その時刻の取り方（足あととしては「いまの様子」に出さない。Issue #347）：

| 出来事 | 時刻 |
| --- | --- |
| `ai:implement` が付いた／`ai:review` が付いた | Issue・PRのラベルの付け外しのイベント（GraphQL の `timelineItems` の `LabeledEvent`、ラベル名が一致）の `createdAt`。PRに付いた `ai:review` は、そのPRに紐づくIssueの出来事にする |
| 実装AIが完了した／エラーで止まった | `claude[bot]` のコメント（完了コメント／エラーコメント）の終わった時刻（`updatedAt`。無ければ `createdAt`。「実装AIの完了コメント」） |
| PRができた | 紐づくPRの `createdAt` |
| CIが全部通った／失敗した | PRの先頭コミットのチェック（Claude Reviewを除く）が全部完了したとき、いちばん遅い `completed_at`。失敗は、失敗したチェックの `completed_at` |
| レビューAIが終わった | Claude Reviewのチェック（`skipped` 以外で完了）の `completed_at` |
| マージされた | PRの `mergedAt` |
| 公開された／公開に失敗した | マージコミットの公開ステータス（`Vercel` または `deploy/` で始まるcontext）の `updated_at`（success／failure・error のとき）。ただし段階の判定と同じく、あとの公開も見る（下の箇条書き） |

- 公開の足あとは「あとの公開が成功」（「段階」の表の下）と同じ考えで出す。判定は `src/lib/events.ts` の `deployFootprint`
  - マージコミットの公開が failure・error でも、同じ context で、マージより後に main の公開が成功していれば、「公開に失敗」は出さず、その成功の時刻で「本番に公開」を出す
  - マージコミットに公開ステータスが無くても（公開をまとめたので、途中のマージには付かない）、マージより後に main の公開が成功していれば、context を問わず最新の成功の時刻で「本番に公開」を出す
  - Vercel の `Canceled by Ignored Build Step`（飛ばした物。state は success になる）は公開した物に数えない（`isCountedDeploySuccess`。main の成功の時刻を作るのと同じ扱い）。マージコミットに飛ばした物の success しか無いときは、公開ステータスが無いときと同じ扱い（上の箇条書き）で、あとの公開が成功していなければ「本番に公開」は出さない（失敗も出さない）
  - 成功の時刻がマージ時刻と同じか前なら「あとの公開」に数えない。あとの公開が無い・まだ失敗のままなら、今までどおり「公開に失敗」。マージコミットの公開が途中（pending）のままなら何も出さない

- 出来事は、画面に出すIssue・PRと同じ取得データから作る。ラベルの付け外しのイベントも同じ GraphQL の問い合わせで一緒に取り、API呼び出しは増やさない（「データの取得」）
- 出来事を作る処理は `src/lib/` の純粋関数にまとめ、テストする（入力：取得済みのIssue・PR・コメント・チェック・ステータス・イベントと「今」の時刻。出力：新しい順の出来事の配列）

| 500以上1,500未満 | 60秒ごと |
| 500未満 | 回復する時刻まで自動では取り直さない（手動の「更新」ボタンは使える） |

- ログインした人のトークンの回数制限（1時間5,000回）はオーナーのアカウント全体で共有で、パイプライン（`PIPELINE_TOKEN`）やほかのツール（Claude のセッションの `gh` など）も同じ枠を使う。ダッシュボードが使い切るとパイプラインのマージなども止まるので、残りが少ないときは自動の取り直しを控えて、パイプラインの分を残す。同期の読み取りを App の鍵で行っているリポジトリは、別の枠（インストールごと。リポジトリ数で増え、最大1時間12,500回）を使う（「読み取りの鍵」）。自動の取り直しの間隔は、使っている鍵の残りのうち**いちばん少ない物**で決める
- 残りは、GitHubの返事の `X-RateLimit-Remaining`、回復する時刻は `X-RateLimit-Reset`（UNIX秒）。304の返事にも付くので読む。書き込み（`send`）の返事も覚える。サーバーのメモリに、トークンのハッシュごとに最新の物を覚える（トークンそのものはキーにしない）。読む・覚えるのは `src/lib/github/client.ts`
- GraphQL の回数制限（1時間5,000点。REST とは別の枠）も同じように覚える。問い合わせに `rateLimit { cost remaining resetAt }` を入れて読み（`resetAt` はUNIX秒にする）、読めなければ返事の `X-RateLimit-Remaining`・`X-RateLimit-Reset` を使う。鍵ごとに REST と GraphQL を別に覚え、残りの表示（止めている間の文言）と自動の取り直しの間隔は、REST と GraphQL の残りのうち**少ない方**（鍵が複数あれば全部のうちいちばん少ない物）で決める（`src/lib/github/rateLimit.ts` の `getRateLimits`、`src/lib/github/appToken.ts` の `getReadRateLimit`）。GraphQL の制限に当たったとき（`errors` の `type` が `RATE_LIMITED`、または 403・429）のエラーの文言は、REST と同じ
- 回復する時刻を過ぎたら、覚えている残りは古いので使わず、普段の間隔に戻す。まだ一度も返事を受けていない（不明）ときも普段の間隔
- 取り直しのたびにサーバーが間隔を決め直し、画面（`AppShell`）に渡す。渡すのは間隔（ミリ秒、または止めるとき `null`）と再開する時刻、Webhook で取り直すリポジトリ（`owner/repo`）とそれぞれの「データに反映済みの印」、今までどおりの間隔が要るかだけで、GitHubのトークンは渡さない
- スマホのメニュー（`TopBar.tsx` の `MenuSheet`。デモも同じ）は、開いている間は裏に出ないシートとして動く（`role="dialog"`・`aria-modal="true"`）。並びは、リポジトリの札のあと、新サービス、Issueを書く、設定、（デモでは GitHubで見る・ログイン）、ログアウト（ユーザー名つき）、同期の順（2026年11月16日、Issue #312）
  - 閉じ込め：開いている間、メニューの外（帯のほかの部分・ページの中身）に `inert` を付け（付け先は `useMenuState` の `menuOpen` から決める）、Tab / Shift+Tab を押してもメニューの外へ出ない。閉じている間のメニュー自身も `inert`（中のリンクにフォーカスが入らない）
  - 札・`設定` を押したとき：メニューは閉じず、押した札の点（`設定` は歯車）が脈打つ。次の画面が出たら（パスが変わったら）閉じる。今いるページの札・`設定` を押したときだけ、パスが変わらないので、すぐ閉じる（判定は `src/lib/menuFocus.ts` の `shouldCloseMenuOnPick`）。`Esc`・背景で閉じる動きは変わらない
  - フォーカスの戻り：`Esc`・背景・項目で閉じたら、メニューボタンへフォーカスを戻す（`focus({ preventScroll: true })`。ページのスクロール位置は動かさない）。項目を押して別のページへ移ったときも `body` に落とさず、メニューボタンへ戻す。判定は `src/lib/menuFocus.ts` の `shouldRestoreMenuFocus`（入力：直前と今の開閉・フォーカスがメニューの中か・どこにも無いか。出力：戻すか）
  - スクロール：メニューの中（`.pane`）は縦にスクロールでき（`overflow-y: auto`）、端まで行っても裏へ伝わらない（`overscroll-behavior: contain`）。横向きやリポジトリが多いときも、いちばん下の「同期」「ログアウト」まで届く。開いている間は `body` のスクロールを止め、閉じたら元に戻す
- 「回復するまで止める」間は、上端の帯の同期の横（スマホではメニューの中）に「回数制限の残りが少ないため、自動更新を止めています（HH:MM に再開）」と出す（見た目は `docs/design.md`）。回復する時刻を過ぎて、次に取り直せたら消える
- レート制限（`rate_limited`）で取れなかったときのエラーの文言は、回復する時刻が分かれば「GitHubのレート制限に達しました。HH:MM（日本時間）ごろに回復します」。`HH:MM` は返事の `X-RateLimit-Reset` を日本時間にして秒を落とした物（`src/lib/refresh.ts` の `formatResetTime`）。時刻が分からないときは「GitHubのレート制限に達しました。しばらくしてからもう一度試してください」
- App の鍵で読んでいて制限に当たったときだけ、「GitHubのレート制限」のあとに「（パイプラインのApp）」を付ける（どちらの鍵の残りか分かるように）。「GitHubのレート制限（パイプラインのApp）に達しました。HH:MM（日本時間）ごろに回復します」／時刻が分からないとき「GitHubのレート制限（パイプラインのApp）に達しました。しばらくしてからもう一度試してください」。ログインした人のトークンで読んでいるとき、ボタンの操作のときは今までどおりの文言

#### リポジトリのページは中央を先に出す／「同期」は押した印をすぐ出す（Issue #448）

- **リポジトリのページ（`/repos/{owner}/{repo}`）**：中央の中身（そのリポジトリの「あなたの番」と「いまの様子」・取れなかったときの知らせ・見張り役の知らせ）は、**そのリポジトリの取得だけ**で描く。他のリポジトリの取得は待たない。左のバーの件数（`あなたの番`・`AI`）と上端の帯の札の件数は、**読み終えたリポジトリから順に**入れる（2026年11月18日。それまでは全リポジトリを読み終えてから、まとめて入れていた）。まだ届いていないリポジトリの件数は `–` を出す（読み上げは `件数を読み込み中`）。Issueを書く欄のリポジトリの一覧（テンプレートか）、自動で足したお知らせは、全リポジトリを読み終えてから届く物なので、あとから入れる
- 作り方：`(app)/layout.tsx` は全リポジトリの取得を待たずに描く。全リポジトリの取得（`loadTurns`）を待つ物は `LayoutStream`（Suspense の中）が後から流し、`LayoutFeed` が画面の入れ物（自動更新の計画は `AppShell`、件数などは `NavProvider`）に入れる。件数は、layout がリポジトリごとに置く Suspense の中の `RepoStream` が、そのリポジトリの取得（`getRepoResult`）だけを待って流し、`RepoFeed` が `NavProvider` に入れる（数え方は全部の件数と同じ。入れ方は純粋関数 `applyRepoCount`［`src/lib/navCounts.ts`］。全部を読み終えた結果が届いたら、その結果で入れ替える。全部を読み終えた結果より前の描画の件数が遅れて届いても、古いので入れない）。トークンが使えなくなった（401）ときのログインの画面への移動も、この後から流れる側で行う（今までどおり、ログアウトして理由つき）
- GitHub の呼び出しは増やさない：取得は1リポジトリごとに1回（`src/lib/github/fetch.ts` の `getRepoResult`。同じリクエストの中では、ページが1つだけ取る分も、全部取る分（`getRepoResults`）も同じ結果を使い回す）
- **「同期」を押したとき**：押した瞬間（100ms 以内。サーバーの返事を待たない）に、ボタンが `同期中 HH:MM:SS` になり、点が脈打つ。`同期中` は、取り直しの結果（自動更新の計画。全リポジトリを読み終えたとき届く）が画面に届くまで続く。届かなくても30秒で戻す。時刻は最後に取り直せた時刻のまま、届いたら新しい時刻になる
- 反映の順：見ているリポジトリの中央が、読み終えた時点で先に入れ替わる。左のバー・上端の帯の件数は、読み終えたリポジトリから順に入れ替わる（全部を待たない）。まだ読み終えていないリポジトリは前の数のまま（`–` には戻さない）。`同期中` の印・Issueを書く欄の一覧は、今までどおり全部読み終えてから。ホーム・Slots & Queue・Dashboard・すべてのリポジトリの中央は、全リポジトリの結果で作るので、今までどおり全部読み終えてから入れ替わる

### 読み取りの鍵

同期のデータ取得（`getRepoResults` → `src/lib/github/fetch.ts`）だけ、リポジトリごとに鍵を選ぶ。オーナーの回数制限を、ほかのツールと取り合わないため。純粋関数は `src/lib/github/appAuth.ts`、メモリに覚える・GitHubを呼ぶ所は `src/lib/github/appToken.ts`。

- 選び方（`chooseReadSource`。入力：環境変数が使えるか・そのリポジトリの App の鍵があるか・ログインした人のトークンで読めると確かめたか。出力：`app` か `user`）：3つとも揃っているときだけ `app`（App のインストールの鍵）、それ以外は `user`（ログインした人のトークン。今までどおり）
- 環境変数 `PIPELINE_APP_ID` と `PIPELINE_APP_PRIVATE_KEY` の両方が空でなく、秘密鍵が PEM として読めるときだけ使える。どちらかが空・読めないときは「環境変数が無い」と同じ。秘密鍵の改行が `\n` の文字で入っていても読む
- App の鍵の取り方：JWT（RS256。`iss` は App ID、`iat` は今より60秒前、`exp` は今から9分後＝10分以内）を Node の `crypto` で作る（`buildAppJwt`）→ `GET /repos/{owner}/{repo}/installation` でインストールを調べる → `POST /app/installations/{id}/access_tokens` で1時間の鍵を取る。鍵は期限の5分前までサーバーのメモリに覚えて、インストールごとに使い回す（`shouldReuseInstallationToken`。入力：期限と今の時刻。出力：使い回すか）。鍵がまだ無いとき（サーバーが立ち上がった直後）に、同じインストールの鍵を同時に頼まれたら、`access_tokens` は1回だけ呼んで全員が同じ鍵を使う（監視リポジトリの数だけ鍵を取りに行かない。`shareInFlight`。2026年11月18日）。鍵の取得と、下の「安全の確認」（`GET /repos/{owner}/{repo}`）は同時に始める（立ち上がった直後の待ちを1往復へらす。呼ぶ数は変わらない。鍵が取れなかったときだけ、使わない確認が1回残る）。インストールの調べ結果（入っていないことも）は10分覚える
- 鍵の権限：インストールの鍵は読み取りだけで作る。`POST /app/installations/{id}/access_tokens` の本文に `permissions`（`contents`・`issues`・`pull_requests`・`checks`・`statuses`・`actions`・`variables`・`metadata` を `read`。`variables` は Webhook で設定の監視リポジトリ（Actions の変数）を読むのに要る）のうち、そのインストールに与えられている物だけを付ける。インストールの権限は `GET /repos/{owner}/{repo}/installation` の返事の `permissions` で分かる（無い権限を頼むと 422 で鍵が取れないため。`variables` が無い App では外し、設定の監視リポジトリは「分からない（全部使う）」になる）。権限が調べられていないときも `variables` は外す。書き込みの権限は App の鍵で使わない（`repositories` は付けない。鍵はインストール単位で使い回すため）
- 読み直し：App の鍵での取得が `forbidden`（権限がありません）・`not_found`（見つかりません）で失敗したら、そのリポジトリのインストールの記憶（`owner/repo` → インストール ID と、そのインストールの覚えた鍵）を消し、その回のうちに、ログインした人のトークンで1回だけ読み直す（表示は落とさない）。読み直せたらエラーにせず、`readSource` は `user`。読み直しも失敗したら、その読み直しのエラーを出す。`rate_limited` などほかのエラーでは読み直さない。ログインした人の読める確認の記憶は消さない。GraphQL の返事に `data` と `errors` が両方あるときは、今までどおり `errors` を優先してエラーにする（部分的な `data` は使わない）
- 安全の確認：App の鍵で読むのは、ログインした人のトークンで `GET /repos/{owner}/{repo}` が成功したリポジトリだけ。確かめた結果は10分、サーバーのメモリに覚える（キーはトークンのハッシュ＋リポジトリ。読めた・404や403で読めなかった、のどちらも覚える。通信失敗やレート制限は覚えず、そのときは `user`）。ログインできる人は今までどおり `getAllowedLogins` で絞る
- フォールバック：App が入っていない・環境変数が無い・鍵が取れない（通信失敗・エラー）ときは、`user` で読む（落ちない）
- ETag・「前回の値」の記憶と回数制限の残りのキーは、App の鍵では「インストールごと」にする（1時間ごとに鍵が替わっても記憶を失わないため）
- ボタンの操作（おまかせ・マージ・設定の保存など。`src/app/actions.ts`、`src/app/(app)/settings/`）は、今までどおりログインした人のトークンで行う
- App の秘密鍵・インストールの鍵はサーバーだけで使う。クライアントのコンポーネントに渡さず、ログ・エラー文にも出さない
- マージ後に人間がすること：Vercel の agent-desk の環境変数に `PIPELINE_APP_ID`・`PIPELINE_APP_PRIVATE_KEY` を入れて、公開し直す（`README.md` のセットアップ）

- 手動の更新：上端の帯の「同期 HH:MM:SS」を押すと取り直す（スマホではメニューの中）。押したら、監視リポジトリ全部のキャッシュを無視して（サーバーアクション `syncNow` で `updateTag`）すぐ取り直す。更新にキーボードのショートカットは無し
- 同期の時刻を出す（上端の帯）。出すのは「最後に取り直した時刻」（日本時間 `HH:MM:SS`）。現在時刻では進めない。取り直しが終わると、その取り直しの時刻に変わる。判定は `src/lib/refresh.ts` の `getDisplayedSyncTime`

### データの取得

同期（`fetchRepoData`。`src/lib/github/fetch.ts`）は、1リポジトリにつき GitHub の GraphQL（`POST https://api.github.com/graphql`。`fetch` で直接呼び、ライブラリは入れない）を**1回**（ページ送りが要るときだけ増える）呼んでまとめて取る。PRの数に比例して呼び出しが増えないようにするため（REST を1つずつ呼んでいたときは、PRの数だけチェックを呼んで1リポジトリ数十〜200回になり、オーナーの1時間5,000回を使い切った）。問い合わせと、返事を今の型（`src/lib/github/types.ts`）に変える純粋関数は `src/lib/github/graphql.ts`。判定（段階・誰の番・公開状態）は変えない。

- 1回の問い合わせで取る物（`repository(owner, name)` の中）
  - `isTemplate`
  - Issue：`issues(first: 50, filterBy: { since: 直近14日の境目 }, orderBy: { field: UPDATED_AT, direction: DESC })` の番号・題名・本文・状態・ラベル・URL・作成・更新・閉じた時刻、コメント（`comments(last: 100)`。本文・作成と更新の時刻・URL・作者。更新の時刻とURLは「AIが今していること」に使う）、ラベルの付け外し（`timelineItems(last: 50, itemTypes: [LABELED_EVENT, UNLABELED_EVENT])`）
  - 人間待ちの Issue（Issue #356）：開いている Issue のうち、`ai:stuck`・`ai:skip`・`ai:question`・`factory:wait` のどれかが付いている物は、更新日で絞らずに取る。ラベルの絞り込みは「すべて付いている」なので、ラベルごとに `issues(first: 30, states: OPEN, labels: ["ai:stuck"], orderBy: { field: UPDATED_AT, direction: DESC })` を別名（alias）で4つ、同じ問い合わせの中に足す（`since` は付けない。取る項目は上の Issue と同じ）。HTTP の呼び出しは増えない。ページ送りはしない（各30件まで。更新の新しい順）。続きの問い合わせ（`withMain: false`）には入れない
  - PR：`pullRequests(first: 50, orderBy: { field: UPDATED_AT, direction: DESC })` の番号・題名・本文・状態・マージの時刻・ラベル・URL・ブランチ名（`headRefName`）・先頭コミット（`headRefOid`）・作成・更新の時刻、コメント・ラベルの付け外し（Issue と同じ）、先頭コミットのチェック（`commits(last: 1) { nodes { commit { statusCheckRollup { contexts(first: 100) } } } }` の CheckRun の名前・状態・結果・作ったアプリ・完了時刻）、マージコミット（`mergeCommit { oid status { contexts } }` の context・状態・説明・リンク先・時刻）
  - main の直近30コミットの公開ステータス（「main の最後に公開が成功した時刻」）
  - 回数制限：`rateLimit { cost remaining resetAt }`（「更新」）

### Webhook で取り直す

GitHub から「変わった」と知らせてもらい（パイプラインの GitHub App の Webhook）、そのリポジトリだけを取り直す。画面には数秒で出し、GitHub への問い合わせは変わった時だけにする（パイプラインと共有の App の鍵の枠を使い切らないため）。依存パッケージは足さない。判定の純粋関数は `src/lib/webhook.ts`（サーバー）と `src/lib/changeMarks.ts`（画面）、キャッシュは `src/lib/github/repoCache.ts`。

- 受け取る：Route Handler `POST /api/github/webhook`（`src/app/api/github/webhook/route.ts`）。ログインは要らない（署名が認証の代わり。ログインの確かめは `(app)` のレイアウトの中だけで、このパスは止めない）。判定は `decideWebhook`（入力：環境変数の合言葉・署名・イベント・本文・監視リポジトリ。出力：返す番号と、無効にするリポジトリ）
  - 環境変数 `GITHUB_WEBHOOK_SECRET` が無い（空）ときは 404（Webhook を使わない設定）
  - `X-Hub-Signature-256`（`sha256=` ＋本文の HMAC-SHA256 の16進）を、`GITHUB_WEBHOOK_SECRET` で Node の `crypto` を使って確かめる（比べるのは `timingSafeEqual`。`verifyWebhookSignature`）。合わない・無いときは 401
  - 使うイベント（`X-GitHub-Event`）は `issues`・`issue_comment`・`pull_request`・`pull_request_review_comment`・`check_run`・`status`・`workflow_run`・`label` だけ（`isUsedWebhookEvent`）。`check_suite` は使わない（画面のデータは変わらない。チェックの変化は `check_run`、実行の変化は `workflow_run` で来る）。ほか（`ping` など）・本文の `repository.full_name` が無い物は 204 で無視
  - 画面のデータが変わらない知らせも 204 で無視する（`isNoChangeWebhook`。入力：イベントと本文。出力：無視するか。2026年11月18日）：`workflow_run` のうち、実行が作られただけの物（`action` が `requested`）と、何もせず飛ばされた実行の完了（`action` が `completed` で `workflow_run.conclusion` が `skipped`）。パイプラインは、コメントやほかの実行の完了のたびに「条件に合わないので飛ばす」実行を何本も作り（実行の3〜5割）、そのたびに取り直すと GraphQL の枠を使うため。動き出し（`in_progress`）と、飛ばされていない完了（成功・失敗・取り消し）は使う。ほかのイベント・形が読めない本文は、今までどおり使う（取り直す側に倒す）
  - 監視しているリポジトリ（`isWatchedRepo`。大文字・小文字は区別しない）の物だけを使う。監視リポジトリは、環境変数 `WATCHED_REPOS` と、設定の監視リポジトリ（`SETTINGS_REPO` の Variable `AGENT_DESK_WATCHED_REPOS`。ログインした人がいないので App の鍵で読み、最大5分キャッシュに覚える。設定を保存したらタグ `watched-repos` を無効にして覚え直す）を合わせた物。設定の保存先があるのに読めない（App が入っていない・権限が無い）ときは、分からないので使う側に倒す（印を進めるだけで害は無い）。監視していない物は 204
  - 使う物は、タグ `repo:<owner>/<repo>`（小文字）を `revalidateTag(タグ, { expire: 0 })` で無効にして 202 を返す。本文の中身は保存しない・ログに出さない
  - 使う物のうち、**急ぎの知らせ**（段階・誰の番が変わりうる物。2026年11月18日）は、タグ `urgent:<owner>/<repo>`（小文字）も一緒に無効にする（判定は `isUrgentWebhook`。入力：イベントと本文。出力：急ぎか。下の「取り直しの持ち分」が、急ぎの知らせを先に出すのに使う）
    - `issues`：`action` が `edited`（題名・本文の書き換え）以外（できた・閉じた・開き直した・ラベルの付け外しなど）
    - `pull_request`：`action` が `opened`・`closed`・`reopened`・`labeled`・`unlabeled`・`ready_for_review`・`converted_to_draft`（コミットの追加＝`synchronize`、題名の書き換えなどは急ぎでない）
    - `issue_comment`：`action` が `created`（質問・答え・進捗の記録）。`edited`・`deleted` は急ぎでない（作業中のコメントは何度も書き換わる）
    - `check_run`：`action` が `completed` で、`check_run.pull_requests` が1件以上あり、`check_run.conclusion` が `skipped`・`neutral` でない（PR のチェックが終わった）
    - `status`：`state` が `pending` でない（公開などのステータスが決まった）
    - ほか（`workflow_run`・`label`・`pull_request_review_comment`、形が読めない本文）は急ぎでない
- 覚えておく：Next.js のキャッシュのタグ（`unstable_cache`。Cache Components の `use cache`・`cacheTag` は画面全体の作りが変わるので使わない。Vercel では、タグの無効化が全部のインスタンスに効く）
  - 「変わった」時刻：リポジトリごとの「最後に変わった時刻」（`changedAt`）を、タグ `repo:<owner>/<repo>` つきで期限なしに覚える。タグが無効になった後に初めて読んだ時刻になり、次に無効になるまで変わらない（Webhook が来ると進む）
  - 「急ぎの知らせが来た」時刻：リポジトリごとの「最後に急ぎの知らせが来た時刻」を、タグ `urgent:<owner>/<repo>` つきで期限なしに覚える（`changedAt` と同じく、タグが無効になった後に初めて読んだ時刻）。まだ取り直しを許していない変化があるときだけ読む（静かな間は読まない）
  - 「手で押す同期・ボタン操作の印」：リポジトリごとに、そのとき（無効にした後に初めて読んだとき）の `changedAt` と時刻を、別のタグ `release:<owner>/<repo>` つきで期限なしに覚える（Webhook のタグは付けないので、Webhook では消えない）。これ以前の変化は、下の「取り直しの持ち分」に関係なく取り直す。無効にするのは手で押す「同期」・ボタン操作だけで、`/api/changes` は書き直さない
  - 「取り直しを許した記録」（2026年11月18日）：下の「取り直しの持ち分」を使った記録（キーはリポジトリと区切りの番号。中身は、許した `changedAt`・そのとき見た「急ぎの知らせが来た時刻」・使った時刻）と、「その `changedAt` はもう許した」という記録（キーはリポジトリと `changedAt`）を、**タグを付けずに、キーだけで**覚える（`keyedRecord`。無ければ作り、あれば、ある物を返す。書き直さない。見るだけのときは、無ければ何も覚えない）。サーバーのメモリには覚えないので、どのインスタンスでも同じ値になる。それまでは「取り直してよい印」をタグ `release:` で無効にして、同じリクエストの中で書き直していたが、Next.js はタグの無効化をリクエストの終わりの時刻で記録するので、その前に書き直した物は「無効にした時刻より古い物」として捨てられ、あける時間（15秒 → 30秒 → 60秒）が次のリクエストに引き継がれないことがあった。タグで無効にする入れ物には、次のリクエストが作り直してよい物（その時刻）だけを置く
  - App の鍵で読むリポジトリの `fetchRepoData` の結果を、キー「リポジトリ（と公開ごとの ID）＋取り直しを許した `changedAt`（`releasedChangedAt`）」で覚える（`cachedRepoData`）。変化ごとに別の入れ物になるので、取得の途中に Webhook が来ても、その変化は次の印で必ず取り直される（キーがリポジトリだけだと、取得の途中の無効化が、保存した瞬間に上書きされて消える）。鍵は入れない（App の鍵で読むのは、ログインした人が読めると確かめた物だけ）。寿命は最大5分（Webhook が届かなかったときの保険）。取ったデータと一緒に、そのデータに反映済みの印（取り直しを許した `changedAt`）を返す
  - 同じインスタンスに、同じ印のデータを読むリクエストが同時に来たとき（取り直しの途中のページ移動・別のタブ）は、取得を1回にまとめる（動いている取得の結果を待つ。`src/lib/inFlight.ts` の `shareInFlight`。終わったら忘れ、覚えるのはキャッシュだけ）

    - `changedAt` が2つ前の区切りの始まりより前（`isSettledChange`。2〜3分より前）：もう片づいているので、そのまま返す（読むのは `changedAt` だけ。静かなリポジトリは、これで済む）

    - 手で押す同期・ボタン操作の印の `changedAt` 以前：そのまま返す（持ち分は使わない）

      - それ以外（急ぎでない知らせだけ＝急ぎの知らせのために1回分を残す、または持ち分が無い）：進めず、前に許した所（記録と、手で押す同期・ボタン操作の印のうち新しい方）を返す。ページもその印のデータを返す（GitHub には問い合わせない）。待つ間に何回変わっても、進められるようになった後の1回にまとまる（最後の知らせも取りこぼさない）
    - 出る速さ：1分以上静かだったリポジトリの最初の変化はすぐ。そのあと変わり続ける間、急ぎでない知らせ（作業中のコメントの書き換えなど）は区切りごと（60秒ごと）。その間も、急ぎの知らせ（質問が来た・止まった・マージされた・CI が終わったなど）は、残してある1回分ですぐ出る。急ぎの知らせに1回分を使った後は、急ぎでない知らせは2回分たまるまで（最長2つ先の区切りまで）待つ。急ぎの知らせが1分に1回より多く続いて持ち分を使い切ったら、急ぎの知らせも区切りごとに1回になる
    - 回数：知らせによる取り直しは「2回 ＋ またいだ区切りの数」までで、どの1時間でも最大62回（前の決まり＝0・15・45・105・165…秒に取り直す、の上限と同じ）。急ぎでない知らせだけなら、どの時点でも前の決まりの回数以下（`src/lib/refetchLimit.test.ts` で比べる）。CI が動いている間に「変わった」が数秒おきに来ても、読み取りの鍵の枠を使い切らない
    - 手で押す「同期」・ボタン操作は、持ち分を使わない（その後の知らせは、今までどおり持ち分で数える）

- 画面（`src/components/AppShell.tsx`、`src/lib/changeMarks.ts` の `startChangeWatch`）
  - サーバーは、App の鍵で読めたリポジトリ（`ok` で、`readSource` が `app` の物）を「Webhook で取り直すリポジトリ」として、そのデータに反映済みの印と一緒に渡す。App の鍵で読もうとして失敗したリポジトリは入れず、今までどおりの間隔で取り直す（一時的なエラーが5分残らないように）。`GITHUB_WEBHOOK_SECRET` が無ければ空（`src/lib/refresh.ts` の `getChangeWatchPlan`）
  - 画面が見えている間（`visibilitychange`。今までどおり）、5秒ごと（AIの番の作業がある間＝自動で取り直す間隔が20秒の間は**2.5秒ごと**。動いている間は早く出すため。`changesPollIntervalMs`。GitHub には問い合わせない）に `/api/changes` を見て、印がデータに反映済みの印より新しいリポジトリがあるときだけ `router.refresh()` する（`isBehindChangeMarks`。サーバーのメモリに頼らず、反映されるまで取り直し続ける）。新しくなければ何もしない。反映済みの印は取り直しのたびに新しくなるので、画面は最新の物を ref で持ち、反映済みの印が新しくなっても見張りは作り直さない（作り直すのは、見るかどうか・見に行く間隔が変わるときだけ）。印を見て頼んだ取り直しの結果（新しい計画）が届くまでは、重ねて頼まない（10秒たっても届かなければ、もう一度頼む。`shouldRequestRefresh`）。非表示から戻ったらすぐ1回見る。回数制限で自動更新を止めている間は見ない
  - `/api/changes` が 404（Webhook を使わない設定）なら見るのをやめ、今までどおりの間隔で取り直す。ほかの失敗は何もせず、次の回で見る
  - Webhook で取り直すリポジトリしか無いときは、決まった間隔の取り直しは5分ごと（キャッシュの寿命と同じ。保険）にする。ログインした人のトークンで読むリポジトリが1つでもあるときは、今までどおりの間隔（上の表）でも取り直す（`getIntervalWhileWatching`）
  - 猶予の切れ目（PR作成待ち15分・未着手10分）は GitHub の出来事ではなく Webhook が来ないので、画面が自分で取り直す。サーバーは、猶予の中にある物（`IssueStatus.grace` が null でない物）の `since + 猶予の長さ` の最小値（`src/lib/graceRefresh.ts` の `nextGraceEnd`。ちょうどその時刻で猶予は終わる）に1秒足した時刻を、取り直しのたびに画面（`AppShell`）へ渡す。猶予の中の物が無ければ渡さず（`null`）、画面は何もしない。画面はその時刻に1回だけ `router.refresh()` する（`startResumeRefresh`。その時刻にタブが非表示なら、表示に戻ったとき）。取り直したあとに新しい時刻が渡されたら、また同じようにする。Webhook で取り直すリポジトリだけのときも、キャッシュのデータに「今」を当てて判定し直すので、猶予が終わった物は「あなたの番」に出る
  - 「同期」の時刻と手で押す「同期」は今までどおり（押したらキャッシュも持ち分も関係なくすぐ取り直す）
  - 同期の横の「速い更新」の点は、実際に使っている取り直しの間隔（5分の保険のときは5分）が20秒のときだけ光らせる（`isFastRefresh`）
- マージ後に人間がすること：合言葉を作って Vercel の環境変数 `GITHUB_WEBHOOK_SECRET` に入れ、App の Webhook を設定する（`README.md` のセットアップ）

### キーボード操作の一覧（`?`）

`?`（`Shift` + `/`）を押すと、キーボードで使える操作の一覧を、画面の中央に重ねて出す（ダイアログ）。覚えていなくても見て思い出せるようにするためのもので、新しいショートカットは足さない。一覧を開く画面上のボタンやメニューの項目も無い（`?` キーだけ）。

- 閉じ方：`Esc`・閉じるボタン・外側（暗い所）を押す・もう一度 `?`。`Esc` で閉じるのは一覧だけで、スマホのメニューやマージの確認は同時には閉じない
- 開かないとき：`input`・`textarea`・`select`・編集できる要素にフォーカスがあるとき、Ctrl・Alt・Meta を押しているとき、日本語入力の変換中、押しっぱなしの繰り返し。判定は `src/lib/keyboardHelp.ts` の純粋関数 `isHelpToggleKey`（入力：押されたキーと修飾キー・変換中か・繰り返しか・フォーカス先。出力：開閉するか）
- フォーカス：開いたら閉じるボタンへ移し、閉じたら開く前の場所へ戻す。開いている間は Tab を押しても後ろの画面にフォーカスは移らない（一覧の中の押せる物は閉じるボタンだけ）。`role="dialog"`・`aria-modal="true"`・`aria-label="キーボード操作の一覧"`
- 使える画面：ログイン済みの画面（ホーム・リポジトリのページ・設定）とデモ（本物と同じ部品なので同じ動き）。ログイン画面では使わない（一覧に載せる操作が無い画面なので）。`window` の `keydown` で受ける（`src/components/KeyboardHelp.tsx`。`AppShell` と `DemoShell` に置く）
- 載せる物は、いま実際にある操作だけ（実装と照らして確かめた物）：
  - `?`：この一覧を開く・閉じる
  - `Tab`：最初の Tab で「本文へ移る」が出て、押すとあなたの番の最初のボタンへ移る（`TopBar.tsx`）
  - `↑` `↓` `←` `→` `Home` `End`：「あなたの番」の残りの一覧で、行を移る（`TurnList.tsx`）
  - `Esc`：スマホのメニュー（`useMenuState`）・マージの確認（`TurnRow.tsx`）を閉じる
- スマホ（キーボードが無い端末）では特に何もしない

### 並列の状態と切り替え

2026年11月17日、Issue #415（設定の「並列」＝#391 の続き）。今の並列の状態を、PCは左のバー・スマホはメニューに出し、押して手ですぐ切り替える。仕組み側は ai-dev-template#122（`PARALLEL_OVERRIDE`）。ホームとリポジトリのページ（左のバーがあるページ）と、スマホのメニューに出す。見た目は `docs/design.md` の「並列の状態のボタン」。

- 出す場所：PCは左のバーのいちばん下（ユーザー名のボタンのすぐ上）、スマホはメニューの `ほか` の項目の下（同期の上）。ログインしていない・`SETTINGS_REPO` が無い・設定が読めないときは出さない
- 形（Issue #440）：ラベル `並列` とオン・オフのトグルスイッチ（`role="switch"`、読み上げの名前は `並列で動かす`）。オン＝並列（昼の上限 `PARALLEL_DAY`）、オフ＝1件ずつ（夜の上限 `PARALLEL_NIGHT`）。行のどこを押しても切り替わる
- 状態の表示：スイッチの横に今の数。オンは `3件まで`（昼の数）、オフは `1件ずつ`（夜の数が1のとき。2以上なら `2件まで`）。上書き中は、それに `手動` を添える。いまの状態は、保存済みの設定（`PARALLEL_DAY`・`PARALLEL_NIGHT`・`PARALLEL_NIGHT_HOURS`）と手の上書き（`PARALLEL_OVERRIDE`）を `SETTINGS_REPO` の Variable から読んで決め、1分ごとに見直す。読み直しは開いたときと5分ごと、切り替えたあとは書いた値をすぐ使う。基準は `Asia/Tokyo`
- 設定で保存したとき（Issue #475）：設定の「並列」の保存（Issue #507 からは、変えて600ms止まったら保存）が成功したら、保存した値（検証済みの `ParallelSettings`）で、左のバー・メニューの状態をすぐ更新する（GitHub は読み直さず、スイッチを押したときと同じく手元の状態を書き換える）。今が昼なら昼の数、夜なら夜の数が出る。手の上書きが効いているときは、上書きはそのまま残り、表示は上書きの上限のまま（上書きを消すと新しい数になる）。同じブラウザの別タブにも `BroadcastChannel`（名前 `agent-desk:parallel-settings`）で保存した設定を送り、受け取った側は形を確かめて（`checkParallelSettings`）から同じ入口で更新する。形が違う物は無視する。`BroadcastChannel` が無い環境では何もせず（エラーにしない）、これまでどおり5分ごとの読み直しで揃う。別タブでスイッチを押した（手の上書きを変えた）ことは届けない。デモは書き込まないので何も変わらない。判定は純粋関数（`applySavedParallelSettings`・`parseSavedParallelMessage`・`describeParallelBarAfterSave`）
- 手の上書き：Variable `PARALLEL_OVERRIDE` に `"night until 2026-11-18T08:00+09:00"`（夜の上限にする）／`"day until …"`（昼の上限にする）。期限は ISO 8601（書くときは日本時間の分まで）。期限を過ぎる・形が違うとパイプラインは無視して時間帯の決まりに戻る（画面も同じに扱う）。効いている上書きは、時間帯の決まりに勝つ
- 押したとき：
  - 上書きが無いとき：今と反対（昼→夜／夜→昼）に切り替える。`PARALLEL_OVERRIDE` を期限つきで、パイプラインのある監視リポジトリ全部に書く。期限は次の時間帯の切り替わり：**夜に切り替えたら夜の終わりまで**（昼のうちなら次の夜の終わりまで）、**昼に切り替えたら次の夜の始まりまで**。夜の時間帯が無ければ、どちらへ切り替えても24時間後。期限はサーバーで決める
  - 上書き中：もう一度押すと、上書きを消して（Variable を削除）時間帯の決まりに戻す
  - 書いている間はボタンを押せない（`aria-busy`）。1つのリポジトリで失敗しても残りには書き、失敗した物は `owner/repo：理由` を ` / ` でつないで、ボタンの下に出す。パイプラインのあるリポジトリが1つも無ければ `パイプラインのある監視リポジトリがありません`
- Server Action（ログイン中かつ許可リストのユーザーだけ）：`loadParallelSnapshot`（読み取り）、`setParallelOverride`（`night`・`day`・`clear` のどれか。それ以外は受け付けない）。`PARALLEL_DAY`・`PARALLEL_NIGHT`・`PARALLEL_NIGHT_HOURS`・`PARALLEL_TZ` には書かない
- 判定は純粋関数（`src/lib/parallel.ts`：`parseParallelOverride`・`formatParallelOverride`・`activeParallelOverride`・`nextPeriodSwitch`・`resolveParallelState`・`planParallelToggle`・`describeParallelBar`）
- 動いている作業を夜に止める・減らすことはしない（パイプラインが次に着手するときの上限が変わるだけ）
- デモ：同じボタンが出る（昼3・夜1・夜の時間帯は1時〜8時の設定。「今」はデモの時刻）。押すと見た目と状態だけ変わり、何も書き込まない（`デモでは実際には動きません` も出さない）。もう一度押すと元に戻る

### 設定（`/settings`）

PCでは左のバーのユーザーのメニュー、スマホではメニューの中に「設定」へのリンクを置く。保存にデータベースは使わず、GitHubのActionsの Variables（リポジトリの設定値。公開リポジトリでも外からは見えない）と、ブラウザを使う。

2026年11月18日、Issue #507 のオーナーの指示で作り直した（見た目は `docs/design.md` の「設定」）。節は `Repositories`（監視するリポジトリ・新しいサービスを自動で足す）・`Parallel`（並列）・`Notifications`（通知）・`Appearance`（テーマ・アニメーション）の4つ。**保存ボタンは無い。変えたらすぐ保存する**（下の「設定の操作の決まり」）。

- 見出しの右に保存の状態（`role="status"`）：まだ何も保存していないときは `変えたらすぐ保存`、保存に成功したら `変えたらすぐ保存 · 20:41 に保存しました`（最後に成功した時刻。日本時間の時:分）。テーマ・アニメーション（ブラウザに保存する物）とデモでは時刻を変えない
- 左の目次（`Repositories`・`Parallel`・`Notifications`・`Appearance`）：押すとその節へ移る。今いる節は、スクロール位置で変わる（`IntersectionObserver`）。`SETTINGS_REPO` が無くて出さない節（`Parallel`）は、目次にも出さない

#### 監視するリポジトリ

- 保存先：`SETTINGS_REPO` の Variable `AGENT_DESK_WATCHED_REPOS`（`owner/repo` のカンマ区切り）。読み取りは `GET /repos/{SETTINGS_REPO}/actions/variables/AGENT_DESK_WATCHED_REPOS`、保存は無ければ `POST`、あれば `PATCH`
- この Variable があれば、画面全体の「監視するリポジトリ」はこれを使う。無ければ環境変数 `WATCHED_REPOS`
- 読んだ値は覚える（2026年11月19日）：画面全体の「監視するリポジトリ」（`loadWatchedRepos`。layout・全部のページ・操作が使う）は、この Variable の値を Next.js のキャッシュ（`unstable_cache`。タグ `watched-repos`。Vercel では全部のインスタンスで同じ物が読める）に覚え、表示のたびには GitHub を読まない（`src/lib/github/repoCache.ts` の `cachedWatchedVariable`）。それまでは、どの表示・ページの移動・取り直し・操作も、最初にこの Variable を GitHub から読み終えるまで何も返せず、URL を開いたときは、その間ずっと真っ白だった
  - キーは保存先（`SETTINGS_REPO`）とログインした人のユーザー名（その人のトークンで読めた値だけを、その人に使う）。値に秘密は無い（`owner/repo` の並び）。Variable が無い（404）ことも覚える。読めなかった（権限なし・通信失敗）ときは覚えず、今までどおり環境変数 `WATCHED_REPOS` を使い、次の表示でまた読む
  - 覚える長さは60秒（`WATCHED_VARIABLE_CACHE_SECONDS`）。過ぎた物は、覚えた値をすぐ返して、裏で読み直す（GitHub の画面などで外から Variable を書き換えた分は、60秒たった後の次の次の表示で出る。裏の読み直しが失敗したら、覚えた値のまま）
  - 捨てるとき：設定で「外す」「追加」を押して書き込んだとき（`saveWatchedRepos` が `updateTag`。書き込んだ直後の表示から新しい一覧）と、同期の中で自動で足したとき（下の「新しいサービスを自動で足す」。描画の途中ではタグを無効にできないので、返事を返し終えてから `after` の中で `revalidateTag`。`forgetWatchedReposAfterResponse`）。どちらも、次の表示で GitHub から読み直す
  - 設定の保存の中の「保存前の一覧」と、自動で足す前の読み直しは、今までどおり GitHub から直接読む（覚えた値は使わない）
- 画面：いまの一覧（1行ずつ、右に「外す」）と、追加の行（ログイン中のユーザーが読めるリポジトリ `GET /user/repos?per_page=100&sort=pushed` から選び、`追加` を押す）。**「外す」「追加」を押したら、すぐ新しい一覧を書き込む**（Issue #507。保存ボタンは無い）。失敗したら一覧を押す前に戻し、理由を一覧の下に出す。節の説明は `監視するリポジトリ · 12件`（件数は今の一覧）
- 一覧は5件まで出し、6件以上のときは残りを畳んで `ほか 7件` と `すべて見る` を出す（押すと全部出し、ボタンは `たたむ` になる）
- 各リポジトリに、全自動パイプラインが入っているか（`.github/workflows/pipeline.yml` があるか）を、ありなら `Pipeline ✓`、なしなら `パイプラインなし` で添える（1リポジトリにつき1回読み、10分覚える。「押した瞬間の反応と、読み込み中」）。追加した直後は調べ終わるまで出さない
- 0件では保存できない：最後の1件の「外す」は受け付けず、`監視するリポジトリを1つ以上選んでください` を出す（一覧は変えない）。`owner/repo` の形でない物、ユーザーが読めないリポジトリは受け付けない
- 追加の欄の一覧が取れなかったとき（GitHubへの問い合わせの失敗）は、「（選べる物がありません）」ではなく、取れなかった理由（`リポジトリの一覧を取れませんでした：` ＋ GitHubのエラーの固定文）を欄の下に出す。取れて0件のときだけ「（選べる物がありません）」
- 保存したとき（2026年11月18日。並列の Issue #475 と同じ形）：「外す」「追加」の保存が成功したら、ページをまたいで残る部品（上端の帯・スマホのメニュー・左のバーの札、Issueを書く欄に渡る一覧の元）のリポジトリの一覧を、保存した一覧ですぐ更新する（設定のページの描き直しを待たない。保存のあとの取り直しでサーバーの一覧が届いたら、そちらに戻す）。札に出すのは今までどおり、動きのあるリポジトリと今開いているリポジトリだけなので、外したリポジトリの札はすぐ消え、足したリポジトリの札は件数が届いてから出る。同じブラウザの別タブにも `BroadcastChannel`（名前 `agent-desk:watched-repos`）で保存した一覧（`owner/repo` の並び）を送り、受け取った側は形を確かめてから（`parseSavedRepos`）同じ入口で札を更新し、中身も取り直す（`router.refresh()`）。形が違う物は無視する。`BroadcastChannel` が無い環境では何もせず（エラーにしない）、次の取り直しで揃う。デモは書き込まないので何も変わらない。判定は純粋関数（`src/lib/savedRepos.ts` の `parseSavedRepos`・`reposToShow`）
- 「外す」の読み上げは `{名前} を外す`。押したら、次の行の「外す」にフォーカスを移す（次の行が無ければ追加の選択欄。選べないときは `追加`）。書いている間は、一覧の「外す」と追加の行を押せない（不透明度0.7）
- 「外した物」を覚える：「外す」「追加」の保存のたびに、保存前の一覧（保存先の Variable を読み直した物。無ければ環境変数 `WATCHED_REPOS`）から消えたリポジトリを、`SETTINGS_REPO` の Variable `AGENT_DESK_REMOVED_REPOS`（`owner/repo` のカンマ区切り）に足す。新しい一覧にある物（手で足し直した物）は、そこから消す（`src/lib/autoAdd.ts` の `updateRemovedRepos`）。覚える物が無くなったら Variable を消す（空の値は書けないため）。覚えた物は、下の「新しいサービスを自動で足す」で足し直さない

#### 新しいサービスを自動で足す

工場（テンプレートの「新サービス：」の Issue。`docs/pipeline.md` の「工場」）が作った新しいリポジトリを、手で追加しなくても監視リストに入れ、ホームに出す。2026年11月16日、Issue #301 で足した。

- 動くのは、監視リストにテンプレートリポジトリ（同期の GraphQL で読む `isTemplate` が true）があるときだけ。無ければ GitHub を何も呼ばず、何も変えない。`SETTINGS_REPO` が無い・ログインしていないときも動かない
- 足す物（`src/lib/autoAdd.ts` の純粋関数 `pickAutoAddRepos`。入力：オン・オフ、ログイン中のユーザー名、いまの監視リスト、監視リストのテンプレート、外した物、ユーザーのリポジトリとそのテンプレート。出力：足すリポジトリ）：GitHub の `template_repository`（GraphQL の `templateRepository`）が監視リストのテンプレートで、持ち主がログイン中のユーザーで、まだ監視しておらず、外した物（`AGENT_DESK_REMOVED_REPOS`）に無い物。大文字小文字は区別しない。オフ・テンプレート無しなら空
- 探し方（`src/lib/github/autoAdd.ts` の `runAutoAdd`。ログインした人のトークンで、`fetch` で直接呼ぶ）：
  1. 設定 `AGENT_DESK_AUTO_ADD` を読む（`GET /repos/{SETTINGS_REPO}/actions/variables/AGENT_DESK_AUTO_ADD`）。`off` なら、ここでやめる
  2. GraphQL を1回：`viewer { repositories(first: 50, ownerAffiliations: OWNER, orderBy: { field: CREATED_AT, direction: DESC }) { nodes { nameWithOwner templateRepository { nameWithOwner } } } }`（作った順に新しい物から50件。テンプレートから作られた物を1つずつ調べる REST は使わない）
  3. 保存先の監視リスト（`AGENT_DESK_WATCHED_REPOS`。無ければ環境変数 `WATCHED_REPOS`）と外した物を読み直す。足す物があれば、監視リストの後ろに足して保存し（今の保存の仕組み。無ければ `POST`、あれば `PATCH`）、足した時刻を `AGENT_DESK_AUTO_ADDED` に残す
- 探すきっかけ：手で押す「同期」（`syncNow`）と、テンプレートの「新サービス：」の Issue が閉じた・動いたとき。後者は、同期の結果のその Issue（開閉を問わない）の番号・状態・更新の時刻を1つの文字列にしてサーバーのメモリに覚え（`factorySignal`）、前と違えば「動いた」とする。Webhook で届いた変化も、取り直した同期で同じように見る。サーバーが起動して初めての同期も、前の値が無いので1回探す
- 調べ直しの下限：前に探してから**5分**（`AUTO_ADD_MIN_INTERVAL_MS`。定数で、設定にはしない）は探し直さない。下限の中できっかけがあったら覚えておき、5分たった後の最初の同期で1回だけ探す（取りこぼさない）。きっかけが無ければ、同期のたびには探さない。判定は純粋関数 `decideAutoAddCheck`（入力：テンプレートの数・きっかけがあったか・前に探した時刻・今。出力：今探すか・待たせるか）。前に探した時刻・きっかけ・前の値はサーバーのメモリ（キーは設定の保存先。再起動で消えてよい）
- 呼ぶ数：探すとき REST 3〜7回（読む3回、足すときだけ書き込みと記録で4回）と GraphQL 1回。5分に1回まで。探さない同期では0回（「呼ぶ数の目安」は変わらない）
- 足したら、その同期の中で、足したリポジトリも取って画面に出す（帯・左の一覧・「いまの様子」。同じリクエストの監視リストにも入れる。`appendLoadedWatchedRepos`）
- 「いまの様子」のお知らせ：足したリポジトリごとに `{リポジトリ名} を監視に追加しました`（`owner/` は省く）と、足した時刻からの時間（`12分前`）を、足してから**24時間**の間、1行だけ出す（`buildAddedNotices`。同じリポジトリは1行。外したら出さない）。足した記録は `AGENT_DESK_AUTO_ADDED`（`owner/repo@ISO時刻` のカンマ区切り。新しい物を後ろに、最大20件）から読む。読むのは監視リストにテンプレートがあるときだけで、読んだ物はサーバーのメモリに5分覚え、その間は読み直さない（自分で足したときは、書いた値をすぐ覚える）。リポジトリのページでは、そのリポジトリの分だけ
- 設定画面の `Auto-add`（`Repositories` の節の白い面の最後の行。スイッチのオン・オフ、初期はオン。Issue #507）：押したらすぐ `AGENT_DESK_AUTO_ADD` に `on` / `off` を保存する（サーバー側の `saveAutoAdd`。ログイン中かつ許可リスト、保存先があるときだけ）。失敗したら元に戻して理由を出す。`SETTINGS_REPO` が無いときは出さない。読めないときは初期のオンとして出す
- 監視リストから自動で外すことはしない。テンプレート以外の自動の検出（組織全体・名前の規則）もしない
- トークンはサーバー側だけで使う（`runAutoAdd` は `loadTurns` の中でだけ呼び、画面に渡すのは足したリポジトリの名前と時刻だけ）
- 読み取りの鍵：足したリポジトリも、同期は今までどおり「読み取りの鍵」で選ぶ。パイプラインの App が「選んだリポジトリだけ」に入っていて、新しいリポジトリに入っていないときは、インストールの確認が 404 になり、ログインした人のトークンで読む（落ちない）
- Webhook：App の Webhook は、App が入っているリポジトリからしか届かない。入っていない新しいリポジトリはログインした人のトークンで読むので、Webhook の見張りには入らず、今までどおりの間隔（20〜30秒）で取り直す。App が「全部のリポジトリ」に入っているときは、足した直後から App の鍵で読める。Webhook が見る監視リスト（最大5分覚える）は、足した表示の返事を返し終えたときに、画面が使う一覧と一緒に捨てる（同じタグ `watched-repos`。2026年11月19日。それまでは、足してから最大5分、新しいリポジトリの Webhook を無視していた）

#### 並列

起きている時は並列でどんどん、寝ている時は1件ずつ進めるための、並列の数の設定（Issue #391）。仕組み側（パイプラインが Actions の変数から並列の上限を決める）は ai-dev-template#122。節の順は `Repositories`・`Parallel`・`Notifications`・`Appearance`（Issue #507）。

- 保存先：パイプラインのある監視リポジトリ**全部**の Actions の Variable：
  - `PARALLEL_DAY`：昼の並列の数（1以上の整数。無ければ既定の3）
  - `PARALLEL_NIGHT`：夜の並列の数（1以上の整数。無ければ1）
  - `PARALLEL_NIGHT_HOURS`：夜の時間帯 `"01-08"`（開始時-終了時。開始を含み終了を含まない。`"22-06"` のように日またぎも可。無ければ夜は無し）
  - `PARALLEL_TZ`（時間帯の基準。既定 `Asia/Tokyo`）と `PARALLEL_OVERRIDE`（手の上書き。「並列の状態と切り替え」の節）には、この画面は書かない・消さない
- 画面（Issue #507）：
  - 今の状態の行：`いまは昼`／`いまは夜`（大きい字）と、`5件まで同時に進めます · 夜（23:00〜7:00）は1件ずつ`（昼）／`1件ずつ進めます · 昼は5件まで`（夜。夜の数が2以上なら `2件まで同時に進めます`）。夜の時間帯が無ければ `5件まで同時に進めます · 夜の時間帯はありません`。右に札 `Day · 5`／`Night · 1`。基準は `Asia/Tokyo`。保存済みの設定で決め、1分ごとに見直す（デモはデモの「今」）。判定は純粋関数（`src/lib/settingsSave.ts` の `describeParallelSummary`。中で `currentPeriod`・`currentParallelLimit` を使う。ai-dev-template の `parallel_limit_decide` と同じ決まりで、時間帯が無ければいつも昼）
  - `Day`・`Night`：`−`・数・`＋` の段階ボタン。1〜10（いまの値が10より大きければ、`＋` は押せず、`−` で1つずつ減らせる）。端では押せない
  - `Night hours`：24時間の帯（1時間ずつのます。夜は薄い紫、昼は薄いインディゴ）。**1回目に押したますの時刻が始まり、2回目に押したますの時刻が終わり**（終わりの時刻は含まない＝2回目のますは昼）。1回目のあとは、そのますに印を付けて `終わりの時刻のますを押してください` を出す（Esc で取り消す）。同じますを2回押すと、受け付けずに `夜の時間帯の開始と終了は、違う時刻にしてください` を行の下に出す。帯の横の `夜なし` で夜の時間帯を消す。帯の下に目盛り `0 6 12 18 24`
- 今の値は `SETTINGS_REPO` の Variable から読む（読めない・無い・不正な値は既定：昼3・夜1・夜の時間帯は無し）。`SETTINGS_REPO` が無い・ログインしていないときは節を出さない
- 値の読み取り・検証（`src/lib/parallel.ts`）：読み取りでは、数は1以上の整数だけ、時間帯は `HH-HH`（各0〜24の整数。開始と終了が同じなら無し）だけを認め、不正な値は既定に戻す。保存では、数は1以上の整数、夜の時間帯は無しか、開始・終了が0〜23の整数で**互いに違う**物だけを受け付ける。同じ時刻は `夜の時間帯の開始と終了は、違う時刻にしてください`。画面とサーバー（`saveParallel`）の両方で確かめる
- 保存（`saveParallel`。ログイン中かつ許可リストのユーザーだけ）：検証してから、監視リポジトリのうちパイプラインのある物全部に書く。既定と同じ値・「無し」の Variable は消す（空の値は書けないため。無ければ何もしない）。1つのリポジトリで失敗しても残りには書き、失敗した物は `owner/repo：理由` を ` / ` でつないで出す（理由は他の保存と同じ固定文。権限が無ければ `このリポジトリの設定を変える権限がありません`）。パイプラインのあるリポジトリが1つも無ければ `パイプラインのある監視リポジトリがありません`
- 変数を環境変数に渡すのは、パイプライン側（ai-dev-template のワークフロー）の仕事。渡されるまで、パイプラインの動きは変わらない
- 保存のしかた（Issue #507）：段階ボタン・帯・`夜なし` を押したら、画面の値はすぐ変え、**最後に押してから600ms止まったら**、そのときの値を1回だけ保存する（続けて押している間は書かない。保存済みと同じ値なら書かない）。判定は純粋関数（`src/lib/settingsSave.ts` の `queueSave`・`dueSave`・`stepCount`・`pickNightHour`）。失敗したら保存済みの値に戻し、理由を押した行の下に出す
- デモ：同じ節が出る（昼3・夜1・夜の時間帯は1時〜8時。左のバーの並列のスイッチのデモと同じ）。600ms止まったら、何も書き込まず `デモでは実際には動きません` を出す（値は画面の上だけで変わる）

#### 通知

- 1行1種類の一覧（Issue #507。リポジトリ×種類の表はやめた）。行は上から `Stuck`（止まって、確認が必要なとき）・`Question`（企画AIから質問があるとき）・`Merge`（マージを押せる・PR作成などを人間がするとき）・`Deploy failed`（公開に失敗したとき）・`Deployed`（本番に公開されたとき）・`Auto-merged`（AIがPRをマージしたとき）・`CI failed`（AIが直す前のCI失敗）。種類と初期値は `.github/scripts/notify.sh`（止まった・質問・ai:hold のマージ待ち・人間の操作待ち・公開された・公開失敗＝初期オン、自動でマージした・CI失敗＝初期オフ）
- `Merge` の行は、`notify.sh` の2つの種類 `hold`（ai:hold のマージ待ち）と `manual`（トークンが無く、人間の操作待ち）をまとめて切り替える（どちらも「人間がマージ・PR作成をする番」の知らせ。片方でも入っていればオンと数える）。ほかの行は1つの種類
- 各行の右にスイッチ（全部のリポジトリに効く）。スイッチがオン＝パイプラインのあるリポジトリのどれか1つでもその種類を鳴らす。オフ→オンで、パイプラインのある全リポジトリに種類を足す。オン→オフで、全部から外す
- オンの行には、スイッチの左に `全部 ▾` のボタン（`aria-expanded`）。押すと行の下に、パイプラインのあるリポジトリの札（`owner/` を省いた名前。押すと切り替わる。`aria-pressed`）が並び、押すとそのリポジトリだけ外せる（もう一度押すと戻る）。一部だけのときボタンは `4 / 12 ▾`（鳴らすリポジトリの数 / パイプラインのあるリポジトリの数）。全部外れたら行はオフになる。パイプラインのないリポジトリは札に出さず、数にも入れない
- 保存：スイッチ・札を押したらすぐ、値が変わったリポジトリだけ、そのリポジトリの Variable `NOTIFY_EVENTS`（種類のカンマ区切り。今までどおり `saveNotifyEvents`）に書く。0種類になるリポジトリが出る変更は、書かずに `通知の種類を1つ以上選んでください` を行の下に出す（`notify.sh` は空を初期値と見るため）。失敗したリポジトリは元の値に戻し、理由を行の下に出す（2つ以上のリポジトリで失敗したときは `owner/repo：理由` を ` / ` でつなぐ）。書いている間は、その行の操作を押せない（不透明度0.7）。どの種類・どのリポジトリに何を書くかは純粋関数（`src/lib/settingsSave.ts` の `NOTIFY_ROWS`・`setNotifyRow`・`setNotifyRepo`・`planNotifyWrites`・`revertNotifyFailures`）
- 保存先：そのリポジトリの Variable `NOTIFY_EVENTS`。無ければ初期値として表示する。パイプラインが入っていないリポジトリには書かない
- パイプラインのあるリポジトリが0件のときは、一覧の代わりに一文（`パイプラインのある監視リポジトリがありません。Repositories で追加すると、ここで通知を選べます`）を出す
- 通知の届け先（ntfyのトピック）は秘密の値なので、ここには出さない

#### テーマ

- `Appearance` の節の `Theme` の行：`OS`（初期。OSに合わせる）／`Light`（白）／`Dark`（黒）の3つの切り替えボタン（`role="radiogroup"`、読み上げの名前 `テーマ`。選んだらすぐ反映。切り替えの置き場所は設定ページだけ。Issue #507）。下の「OSに合わせる」は `OS` のこと
- `OSに合わせる` は `prefers-color-scheme`（OSが黒なら黒、そうでなければ白）に従う。OSの設定が変わったら、画面を開いたままでも追従する
- キー操作は「アニメーション」と同じ（`src/lib/roving.ts` の `rovingNext`）
- 保存先：そのブラウザ（`localStorage` の `agent-desk:theme`。PCとスマホで別々）。読み書きは try/catch で囲み、使えなければ `OSに合わせる`。不正な値も `OSに合わせる`
- `<html>` に `data-theme="light"` / `data-theme="dark"` を付ける（`OSに合わせる` のときは付けない）。CSSはこれと `prefers-color-scheme` を見る

- 選択の判定（保存値＋OSの設定→実際のテーマ）は `src/lib/theme.ts` の `resolveTheme`。色は `docs/design.md` の「色」

#### アニメーション

- `Appearance` の節の `Motion` の行：`OS`（初期。端末の設定に従う）／`On`（オン）／`Off`（オフ）の3つの切り替えボタン（`role="radiogroup"`、読み上げの名前 `アニメーション`。選んだらすぐ反映。Issue #507）。下の「オン」「オフ」は `On`・`Off` のこと
- キー操作：Tab で止まるのは選ばれている1つだけ。←→（と ↑↓）で隣へ動かすと、フォーカスと選択が同時に移る（端では反対の端へ回る。`src/lib/roving.ts` の `rovingNext`）
- 保存先：そのブラウザ（`localStorage`。PCとスマホで別々）。読み書きは try/catch で囲み、使えなければ「端末の設定に従う」

#### 設定の操作の決まり

- 保存はすべてサーバー側で、ログイン中のユーザーのトークンで行う。許可リストのユーザーだけ
- Variables を書くには、そのリポジトリの管理者である必要がある。失敗したら理由を画面に出す（「このリポジトリの設定を変える権限がありません」など）
- 書き込む値は、決まった形（リポジトリ名の並び・通知の種類の並び）だけを受け付ける
- **変えたらすぐ保存する**（Issue #507。保存ボタン・`未保存`・`beforeunload` の確認は無くした）：画面の値は押した瞬間に変え、保存はその場で始める（段階ボタン・帯だけは600ms止まってから）。書いている間は、その行の操作を不透明度0.7にして押せなくする。失敗したら、その行の下に理由を出し（`role="alert"`。理由は今までの固定文）、値を保存済みに戻す。成功したら見出しの右の時刻を変え、行の下の理由は消す
- 変えた1項目から、どの Variable にどの値を書くかは、純粋関数（`src/lib/settingsSave.ts` の `planWatchedReposWrite`・`planAutoAddWrite`・`planParallelWrite`・`planNotifyWrites`）で決める：監視するリポジトリ＝`SETTINGS_REPO` の `AGENT_DESK_WATCHED_REPOS`、`Auto-add`＝`SETTINGS_REPO` の `AGENT_DESK_AUTO_ADD`、並列＝パイプラインのある監視リポジトリ全部の `PARALLEL_DAY`・`PARALLEL_NIGHT`・`PARALLEL_NIGHT_HOURS`、通知＝そのリポジトリの `NOTIFY_EVENTS`
- デモ：画面は同じ。何も書き込まず（見た目と状態だけ変わる）、本物なら書き込む所で `デモでは実際には動きません` を出す（`Auto-add`・テーマ・アニメーションは今までどおり出さない）。見出しの右の時刻は変えない

### Issueを書く（`/new`）

短いメモはホームとリポジトリのページの下の入力欄（幅に関係なく常に出る）から書ける。このページは、長めに落ち着いて書くとき用に残し、スマホのメニューの中の「Issueを書く」から開く（PCにはリンクを置かない）。リンクは、リポジトリのページから開くときは `/new?repo=<owner>/<repo>`（デモは `/demo/new?repo=...`）にして、そのリポジトリを選んだ状態で開く。ホームなど、リポジトリのページでないところからは `/new`（組み立ては `src/lib/issueRepo.ts` の `newIssueHref`）。画面から、監視しているリポジトリにIssueを作る。書くのは1行のメモ（タイトル）と、付けたい画像（スクショなど。省いてよい）。見た目は `docs/design.md` の「Issueを書く」。

- 入力：`リポジトリ`（監視リポジトリから選ぶ。初期は先頭。`/new?repo=owner/repo` ならそのリポジトリ。デモの `/demo/new?repo=...` も同じ）と、`メモ`（1行）。`Issueを作る` を押すと、サーバー側でIssueを作る（`POST /repos/{owner}/{repo}/issues`）。押している間は `作成中…` と出して押せなくする
- 検証（`src/lib/newIssue.ts` の `checkNewIssueTitle`。画面とサーバーの両方で行う）：前後の空白を外し、空は `メモを書いてください`、途中に改行があれば `メモは1行で書いてください`、120文字を超えれば `メモは120文字以内にしてください`
- **画像**（Issue #374。ホーム・リポジトリページの入力欄と `/new` の両方。`NewIssueForm`）：
  - 付け方は3つ：メモの欄への**貼り付け**（クリップボードに画像があれば画像として足す。文字も一緒にあるときは文字の貼り付けをそのまま通す）／入力欄（フォーム全体）への**ドラッグ**／入力欄の横のボタン `画像を付ける` からの**ファイル選択**（PNG・JPEG・WebP・GIF、複数可。スマホではカメラロールが開く）
  - 画像のファイルを入力欄の外や作成中に落としても、ブラウザが画像を開かない（ページに留まり、書きかけのメモは残る）。画像は足さない。文字・リンクのドラッグは今までどおり（何もしない）。受け口は `NewIssueForm` の中に置き、フォームが表示されている間（ホーム・リポジトリのページ・`/new`・`/new/service`）だけ `window` の `dragover` と `drop` で受ける。ファイルのドラッグかどうかは `src/lib/issueImages.ts` の `isFileDrag`
  - 付けた画像は小さく並べて見せ（サムネイル）、1枚ずつ外せる（`画像を外す`）。作成中は外せない。Issueを作れたら全部消す。失敗したら残す（もう一度押せる）
  - `画像を外す` で外したあとのフォーカス（押したボタンは消えるので、`BODY` に飛ばさない）：次の画像の `×` へ。外した画像が最後なら、1つ前の画像の `×`。1枚も残らなければ `画像を付ける` ボタンへ（決め方は `src/lib/imageFocus.ts` の `focusAfterRemove`）
  - 決まり（`src/lib/issueImages.ts`。画面とサーバーの両方で使う）：種類は PNG・JPEG・WebP・GIF（**中身の先頭バイト**で確かめる。拡張子や申告された種類は信じない）、1回に**5枚まで**、**1枚4MBまで**。超えたときの文は `画像は5枚までです`・`画像は1枚4MBまでです`・`画像は PNG・JPEG・WebP・GIF だけです`（メモの欄の下に出す）。超えた画像は足さない。メモは必須のまま（画像だけでは作れない）
  - サーバー：本番（Vercel）の関数は1回の本文が4.5MBまでなので、画像は1枚ずつ、別の Server Action（`uploadNewIssueImage`）に FormData のファイルのまま（base64 にせず）送る。サーバーは中身を読む前に大きさで断り、読んだあと先頭バイトで種類を確かめ直す（正しくなければ `操作の内容が正しくありません`）。本文の上限は `next.config.ts` の `experimental.serverActions.bodySizeLimit`（`5mb`。4MBの画像1枚が通る大きさ）。全部上げ終えたら、`createNewIssue` に上げた画像のURLを渡す。`parseNewIssueInput` は、URLが5つまでで、そのリポジトリの `issue-images` の `images/<年月>/<UUID>.<png|jpg|webp|gif>` の形かを確かめ直す。認可（ログイン中・許可リスト・監視リポジトリ）は両方の呼び出しで行う。失敗して押し直したときは、同じリポジトリに上げ終えた画像は上げ直さない
  - 置き場所：同じリポジトリの専用ブランチ `issue-images`。無ければ、Git Data API で `.gitkeep`（空ファイル）だけを入れた、親の無いコミットから作る（`main` の履歴や中身は持ち込まない）。画像は `images/<西暦年月>/<ランダムな名前>.<拡張子>`（名前は `crypto.randomUUID()`。元のファイル名は使わない）に、Contents API（`PUT /repos/{owner}/{repo}/contents/{path}`）で1枚ずつ入れる。消さずに残す
  - 本文：画像を全部上げてから、Issueを作る。本文は `![スクショ](https://github.com/<owner>/<repo>/raw/issue-images/<パス>)` を1枚1行で並べる（`composeNewIssue`）。`- [x] 全部おまかせ` があれば、その下に空行1つで分けて並べる。題名はメモのまま。非公開のリポジトリでも、リポジトリを見られる人は GitHub にログインしていれば見える
  - 1枚でも上げられなければ、Issueは作らず、固定文 `画像を上げられませんでした。もう一度試してください` を返す（メモと画像は残る。それまでに上げた画像はブランチに残る）
  - パイプラインのAIが画像を見られるようにする分は、この画面の外（Issue #375）
- **ラベルは付けない**。付けるのはパイプラインの受付（`docs/pipeline.md`）で、企画に回す。画面は `ai:plan` などを付けない
- テンプレートリポジトリ（`is_template` が true。サーバーが `GET /repos/{owner}/{repo}` で確かめ直す）に書くときは、タイトルを `新サービス：` ＋メモにする（メモがすでに `新サービス：`・`新サービス:` で始まっていれば重ねない）。入力欄の前に `新サービス：` を出し、`全部おまかせ`（ランプ＋字のオン・オフ。初期はオフ）を出す。オンにしたときだけ、本文に `- [x] 全部おまかせ` を入れる（入れなければ工場が相談から始める。「工場の相談」）。通常のリポジトリでは `全部おまかせ` は出さず、本文は空（組み立ては `composeNewIssue`）
- できたら、`#番号 を作りました` と、そのIssueへのリンク（`開く ↗`）を出し、メモの欄を空にする。画面を取り直すので、ラベルが付くまでの間は、その Issue が「あなたの番」に未着手（おまかせ・実装を依頼）として出ることがある。失敗したら理由を出す（「操作」と同じ固定文）
- 操作の決まり：ログイン中かつ許可リストのユーザーで、対象リポジトリが監視リポジトリのときだけ受け付ける（`createNewIssue`。「操作」と同じ）。トークンはサーバー側だけで使う
- 監視リポジトリが0件のときは、フォームの代わりに一文（`監視するリポジトリがありません。設定で追加すると、ここからIssueを書けます`）を出す
- デモ（`/demo/new`）：GitHub には送らず、選んだリポジトリのサンプルのデータに Issue が増える（ラベルなし＝未着手。番号はそのリポジトリの Issue と PR の番号の最大＋1。`src/lib/demo/ops.ts`）。`できたら` の文は `作りました。あなたの番に出ます`（番号とリンクは出さない）。画像は付けて見せられる（サムネイル・削除）が、GitHub には送らず、作ったデモのIssueにも入れない。デモのテンプレートリポジトリは `demo/landing-page`（`新サービス：`・`全部おまかせ` の見本）。「もう一度 ↺」で消える

### 新しいサービスを作る（`/new/service`）

- 送り先：監視リストのうち `is_template` が true のリポジトリ。1つなら自動で選び（`送り先` として名前を出す）、2つ以上なら選ぶ（`newIssueRepos` の `template`）。ほかのリポジトリには送れない
- 処理は「Issueを書く」のテンプレートのときと同じ：`createNewIssue`・`composeNewIssue`（タイトルは `新サービス：` ＋メモ、`全部おまかせ` オンのときだけ本文に `- [x] 全部おまかせ`）。検証（`checkNewIssueTitle`）・操作の決まり（ログイン中かつ許可リスト、対象は監視リポジトリ、サーバーが `is_template` を確かめ直す）・トークンがサーバー側だけなのも同じ
- 送ったあと：`#番号 を作りました` ＋ `開く ↗` の下に、`工場が新しいリポジトリを作って、公開まで進めます。相談があれば「あなたの番」に出ます`
- 監視リストにテンプレートリポジトリが無いとき：フォームの代わりに一文（`監視リストにテンプレートのリポジトリがありません。設定でテンプレートのリポジトリ（ai-dev-template など）を追加すると、ここから新しいサービスを作れます`）
- 「Issueを書く」（`/new`）・下の入力欄（Issueを作る）の挙動は変えない。区別は文言と置き場所だけ（`/new/service` の見出しの下に「今あるリポジトリに頼むときは、「Issueを書く」から」を添える）
- デモ：`/demo/new/service`。送り先はテンプレートの見本 `demo/landing-page`。GitHub には送らず、サンプルのデータにIssueが増える

### デモ（`/demo`）

ログインしなくても、サンプルのデータで画面を見て触れるページ。就活などで、GitHubのアカウントが無い人にも見てもらうため。

- URL：`/demo`（ホーム）、`/demo/repos/{owner}/{repo}`（リポジトリのページ）、`/demo/repos`（すべてのリポジトリ）、`/demo/dashboard`（Dashboard）、`/demo/lanes`（Slots & Queue）、`/demo/settings`（設定）、`/demo/new`（Issueを書く）、`/demo/new/service`（新しいサービスを作る）。ログインしていなくても開ける
- ログイン画面に「ログインせずにデモを見る」のリンクを置く
- データ：`src/lib/demo/` に置いたサンプル。架空のリポジトリ3つ（`demo/todo-app`・`demo/landing-page`・`demo/notes-api`。最後の1つは公開済みの1件だけで、あなたの番もAIの番も 0・0 ＝左のバーには出ず `/demo/repos` にだけ出る見本）。最初の2つに、全部の段階（企画中・質問（画面案つき。画像は `public/mockups/` の見本）・工場の相談（`新サービス：` のIssue。案の段階から始まり、答えると見た目の方向（画像は `public/factory/` の見本）・画面・最終確認へ進む）・順番待ち・保留・AI作業中・CI中・CI失敗・レビュー中・修正中・修正の確認中・マージ待ち・止まった・やり直し待ち・公開中・公開済み など）と、出来事、順番待ちの理由、並列動作を含める。時刻は「今」からの相対で作る。上端の帯の件数（あなたの番・動いている）は、各リポジトリで、2つの数が同じにならないようにする
- 進捗ログ：デモの各Issueに、進捗図で記録がある工程（今の位置までで、待ちでない工程）だけの進捗ログのコメント（`<!-- ai-step-log -->` と `<!-- ai-step {JSON} -->` の行。形は `src/lib/stepLog.ts`）を入れる（`src/lib/demo/data.ts` の `addStepLogs`。再生で段階が進んでも、そのときの段階に合わせて作る）。進捗図にはモデル名と所要時間が出る。記録が無い工程は「不明」を出さない。止まった例は「AIが3回直してもCIが通りませんでした」で、修正依頼コメントは `（自動の依頼 n/3）` 付き
- マージ待ちの見本：Issueに紐づかない「マージしてよいPR」が1件（`demo/todo-app`）、`ai:stuck` のIssueに紐づく「マージしてよいPR」が1件（同）。後者は「止まった」ではなく「マージ」が出る
- 番号：1つのリポジトリの中で、Issue と PR の番号は重ねない（GitHub と同じく共通の番号。再生の途中の各段階でも）。画面の行の key は `owner/repo#番号` など、重ならない値を使う
- GitHub には一切問い合わせない。トークンも使わない
- 上端の帯に印「デモ（サンプルのデータ）」と「再生 ▶」。「GitHubで見る ↗」（このアプリのリポジトリへのリンク）と「ログイン」はスマホのメニューに置く。PCでは左のバーのいちばん下の `デモ` のメニューに置く（PCの帯には置かない。ログインはワードマークの先のログイン画面から）
- 「あなたの番」のボタン（おまかせ・実装を依頼・再開・始める・PRを作る・レビューを依頼・マージ・答えを送る）は、ブラウザの中のサンプルのデータで**本当に段階を進める**（GitHub には何も送らない）。押した手応えは本物と同じ（押してから0.42秒の間は `〜中…`、そのあと `〜しました` を2.4秒。見せ方は `TurnRow` が本物と同じ部品で出す。0.42秒は `src/lib/demo/ops.ts` の `DEMO_OP_DELAY_MS`）。押してから0.42秒後に、データを操作のあとの形にする（`src/lib/demo/ops.ts` の `applyDemoOps`。本物のパイプラインがすぐにすることも一緒に真似る）：
  - おまかせ：`ai:plan` を付ける（清書中）／実装を依頼：`ai:implement` を付ける（AIが実装中）／始める：`ai:skip` を外し、`ai:plan` を付ける（清書中）
  - 再開：`ai:stuck` を外し、直したコミットでCIをやり直している形にする（修正を確認中）
  - PRを作る：PRを作り、CIが走り出した形にする（CI 実行中）。PRの番号は、そのリポジトリの Issue と PR の番号の最大＋1
  - 答えを送る：組み立てた答えの文を、人（`you`）のコメントとしてIssueに足し、`ai:question` を外して `ai:plan` を付ける（パイプラインが企画を続ける形。清書中）
    - 工場の相談（`factory:wait` の Issue）では、答えの文をコメントに足したあと、工場がすることも真似る：選んだ（`pick`）ら次の段階（案 → 見た目の方向 → 画面 → 最終確認）の、全部ちがう・直す（`redo`）なら同じ段階の作り直しの、工場の相談のコメント（`github-actions[bot]`）を足す（`factory:wait` は付いたまま。行はその場で次の段階の中身に変わる）。`作る`（`go`）なら「作り始めます」のコメントを足して `factory:wait` を外し、Issueを閉じる（いまの様子からも消える）。印が読めない答えは、コメントを足して `factory:wait` を外すだけ
  - レビューを依頼：PRに `ai:review` を付ける（レビューAIが確認中）／マージ：PRをマージし、Issue を閉じ、Vercel の公開を pending にする（本番に公開中）
  - 再生で進む1件（メモから始めた物）のボタンは、再生を1段階進める
  - 「もう一度 ↺」で、押した操作も最初の状態に戻す
- 設定の保存と同期は押せるが、実際には何もせず、「デモでは実際には動きません」と短く出す
- 新しいサービスを自動で足す：工場の相談（`landing-page#19`）で最終確認まで進んで `作る` を送り、Issue が閉じたら、工場が作ったリポジトリ `demo/morning-card`（テンプレート `demo/landing-page` から作られた物）を、本物と同じ `pickAutoAddRepos` で監視に足す（帯・左の一覧・リポジトリのページに出る。最初の Issue `最初の画面を作る` が企画中）。「いまの様子」に `morning-card を監視に追加しました` が出る。設定の「新しいサービスを自動で追加」をオフにしてから閉じると足さない（GitHub には保存せず、ブラウザの中のデモの状態だけを変える。「デモでは実際には動きません」も出さない）。一度足した物は、オフにしても外さない。「もう一度 ↺」で元に戻る（`src/lib/demo/data.ts` の `demoAutoAdd`・`demoAutoAddResult`）
- **再生**：帯の「再生 ▶」を押すと、サンプルの1件（メモから始めた物）が、清書 → 実装 → PR → CI → レビュー → 修正 → マージ → 公開 と、4秒ごとに次の段階へ進む。いまの様子（会話の文・足あと）とあなたの番（1件と `ほかに N件`）が、本物と同じように変わる。最後まで行ったら止まり、「もう一度」で最初から
- 自動更新はしない（再生の間だけ画面が変わる）
- 本物の画面と同じ部品を使う（デモ専用の見た目を作らない）。違うのはデータの出どころだけ

## 操作

すべてサーバー側で実行する（ブラウザにGitHubのトークンを渡さない）。成功したら画面を取り直す。

| ボタン | 出る段階 | やること |
| --- | --- | --- |
| おまかせ | 未着手 | Issueに `ai:plan` ラベルを付ける（企画AIが清書して、あとは全自動） |
| 実装を依頼 | 未着手 | Issueに `ai:implement` ラベルを付ける（Issueがもう詳しく書けているとき） |
| 再開 | 止まった | `ai:stuck` を外す。人間が対応したあと押す |
| 始める | 保留（答えていない質問が無いもの） | `ai:skip` を外す。外すと、パイプラインが自動で企画に回す（画面は `ai:plan` を付けない） |
| PRを作る | PR作成待ち | `claude/issue-<番号>-...` ブランチから main へのPRを作る。タイトルはIssueタイトル、本文は `Closes #<番号>` |
| レビューを依頼 | マージ待ちで `ai:hold` があり、まだレビューしていない | PRに `ai:review` ラベルを付ける |
| 答えを送る | 質問・工場の相談 | 画面で選んだ・書いた答えの文（「企画AIの質問」の `composeAnswer`、工場の相談は「工場の相談」の `composeFactoryAnswer`）を、Issueへのコメントとして書く（`POST /repos/{owner}/{repo}/issues/{番号}/comments`）。ラベルは変えない（コメントすると、パイプライン・工場が自動で続きを始める）。ただし保留（`ai:skip` が付いている）の質問では、コメントを書いたあと、`ai:skip` を外して `ai:plan` を付ける（企画AIが答えを読んで清書する）。サーバーでは、答えの文が空でなく4,000文字以内のときだけ受け付ける。工場の相談で、文に印 `<!-- factory-answer:… -->` があるときは、印が読めて `action` が `pick`・`redo`・`go` のときだけ受け付ける。押している間は `送信中…` |
| マージ | マージ待ち | 「マージ…」を押すと、その行のボタンが「マージする」「やめる」に変わり、説明文の所にCI・レビュー・公開の結果を3行（印・名前・結果の3列にそろえて）で出す（確認。ダイアログは開かない。`Esc` でやめる）。レビューが未実施・指摘ありのときは、その行を失敗の弱い色で示し、「マージする」も塗りつぶさず弱い見た目にする（押せる。`docs/design.md`）。「マージする」を押したらPRをマージする。押した時点でマージできない状態に変わっていたら（CIが始まった・レビュー中になったなど）、エラーを出さずに確認を閉じて画面をすぐ取り直す（行の段階が変わり、ボタンは消える） |

- 操作のAPIは、ログイン中かつ許可リストのユーザーで、対象リポジトリが `WATCHED_REPOS` に入っているときだけ受け付ける
- 押したら100ms以内に目に見える反応（ボタンの見た目が変わり、`〜中…` になる）。成功したら、結果（`〜しました`）を2.4秒見せてから、今の1件を片づけて次の1件に替え、`ほかに N件` は結果を出し始めた時点で1つ減る（取り直しを待たない。「あなたの番」の「押したあとの手応え」）。取り直しで片づけた1件が消える。8秒たっても段階が変わらない・失敗したときは、元の1件と件数に戻す
- 失敗したら、理由をその行に出す
- サーバーの操作の呼び出しそのものが失敗したとき（通信が切れた、公開し直したあとの古い画面のまま押した、など。サーバーの処理まで届いていない）も、画面全体をエラーの表示に替えず、同じ場所に理由 `サーバーに届きませんでした。ページを読み込み直して、もう一度試してください` を出す（見た目は、ほかの失敗の理由と同じ。書きかけの答え・メモ・設定は消さない）。「あなたの番」のボタン（`runOperation`）、Issueを作る（`createNewIssue`）、設定の保存（監視するリポジトリ・新しいサービスを自動で足す・通知）で同じ。手で押す「同期」が届かなかったときは、文は出さず、同期の時刻を進めない（最後に取り直せた時刻のまま）。呼び出しは `src/lib/actionCall.ts` の `callAction` を通す

## セキュリティ

- GitHubのトークンはサーバー側（Auth.jsのセッション）だけで扱い、クライアントのコードやレスポンスに含めない
- 許可リスト外のユーザーはログインさせない
- 監視リポジトリ以外への操作は拒否する
- Issueに付ける画像は、サーバー側だけで GitHub に上げる（トークンはクライアントに渡さない。種類・大きさ・枚数もサーバーで確かめ直す）
- OAuthのスコープは、監視リポジトリ（`WATCHED_REPOS`・`SETTINGS_REPO`）が全部公開なら `read:user public_repo`、そうでなければPrivateリポジトリの読み書きのため `read:user repo`（「ログインで頼む権限」の節。後でGitHub Appに置き換えるのが改善候補）
